A function that calls a name gives a wrong value when that name was a number for a while and is a function again: the call stays a product by the name.

## Witness

Run on main at `a56ceaa265cbd9e3aeb66af8ba46b5cc3742b192` (LaTeX, each line parsed and evaluated in order):

```
f(t) := a(t+1)
a = 3              (ce.assign('a', 3))
f(1)               // 6: with a number, a(t+1) is the product 3·(1+1)
a(x) := x^2
f(1)               // 2a, where it must be 4
h(t) := a(t+1)     // the same body, defined now
h(1)               // 4
```

A notebook reaches it: one cell gives `a` a number, a later cell makes `a` a
function.

## What it must give

`f(1)` is `4` after `a(x) := x^2`: the reading of `a(t+1)` follows the
definition of `a`, in both directions, as `h` shows.

## Cause and options

When `a` gets the number, the body of `f` is derived again and reads
`a(t+1)` as a product (`repairProvisionalDependents`, `function-utils.ts`).
The literal of that reading notes no name it waits for (its `heads` set is
empty: a name is noted only when it has no definition, or a guessed one), so
`f` is no longer registered under `a`, and the later definition of `a` as a
function derives nothing again.

Option: a literal notes every name whose reading as a product or as an
application was decided from the definition of the name, whichever reading
was chosen (`noteProvisionalApplication`, `boxed-expression/invisible-operator.ts`),
or a literal that is derived again keeps the names it was derived for. The
spec for stored function bodies as units
(`~/dev/compute-engine-recovery/stored-bodies/`) takes the first form as its
rule; this issue stands if that spec is not built.
