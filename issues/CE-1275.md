In an Epsil program, a second assignment to an undeclared name is reported at the top level and is not reported inside a loop body.

## Witness

CE 0.188.0 from the npm package, the number of `assignment-to-undeclared-variable` diagnostics of `checkEpsil`:

| Program | Diagnostics |
| --- | --- |
| `t = 1` / `u = 2` / `t = 3` | 3 (each assignment) |
| `for k in 1..3 { t = 1; u = 2; t = 3 }` | 2 (the first assignment of `t`, and `u`) |

The instrument prints both counts and `CE-1275: READY` when they are equal.

## What it must give

One rule for both places: each assignment, or the first one of each name. Tycho has no preference; each assignment gives a host more to work with.

## Why Tycho reports it

Tycho offers the `let` fix on one assignment of a name in each scope, and its tests check which errors remain after the fix. The two behaviours made the same test program behave differently at the top level and in a loop. Tycho works with either rule.

## Cause and options

The static pass (`canonicalizationDiagnostics`, `src/epsil/static-diagnostics.ts`) kept one diagnostic per description in a statement, and a block is one statement. Fixed (session cebatch-1275, 2026-11-14) with the rule "each assignment": each assignment to an undeclared name is reported at its own range, in a block, a loop body or a function body as at the top level. The witness gives 3 and 3.

## CE answer

CE (2026-11-13, session ce-desk): P4 confirmed, in the pool; not started. The top level and a loop body should report the same set; which of the two counts is right is for the fix to decide from the rule (each undeclared assignment is reported once for each name). No workaround needed: the first diagnostic is the same in both places.
