A Tycho notebook showed ln(lcm(1, 2, …, 100)) as 233.70, with no error; the value is 94.045.

## Witness

On CE 0.201.2, each row in a fresh engine:

```epsil
N(reduce(1..100, (u, v) => lcm(u, v), 1))
```

| `ce.precision` | Value                     | Right value |
| -------------- | ------------------------- | ----------- |
| default        | `6.972037522971247716e40` | yes         |
| 30             | `6.97203752297124771645e40` | yes       |
| 15             | `3.12407341776354e101`    | no          |
| `"machine"`    | `3.12407341776354e101`    | no          |

The fold to 60 gives `3.2993539809138796e42` at machine precision; the right
value is `9690712164777231700912800` (9.69e24). The fold to 40, whose value
5342931457063200 is below 2^53, is right at every precision.

Controls, at machine precision: the exact fold bound first and `N` applied after
is right (`let L = reduce(1..100, (u, v) => lcm(u, v), 1); N(ln(L), 10)` is
94.04531123), and so is `N(lcm(12, 18))`.

Tycho runs a code cell at machine precision once a formula cell of the same
section has run, so the shape reaches a notebook as soon as it has any formula
cell before the code cell. The instrument shows that path with the real Tycho
evaluator: the code cell alone gives 94.045, after a formula cell `1+1` it gives
233.70.

## Cause and options

Probable cause, not verified in the source: under `N` at machine precision the
lambda's arguments are floating-point numbers, and once the running value is
above 2^53 the float is not the exact integer, so `lcm` (through `gcd`) finds no
common factor and multiplies. The values fit: at 60, 3.30e42 is far above the
right 9.69e24.

Options: let `N` evaluate an integer-valued fold (`lcm`, `gcd`, integer `+`
and `*`) exactly and round only the result; or let `lcm` and `gcd` of an inexact
number above 2^53 return an error or `NaN` instead of a finite wrong value.

Tycho workaround: bind the exact fold with `let` and apply `N` after it.
