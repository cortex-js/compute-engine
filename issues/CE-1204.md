After an expression that calls a user function is compiled, evaluating a related expression gives a wrong number.

## Witness

At `eac9ab939ef63e0914ba506454feb3d821c293ed`, on a new engine:

```ts
ce.declare('fs', '(real, integer) -> real');
ce.assign('fs', ce.box(['Function', ['Block',
  ['Declare', 's', { str: 'real' }, 0],
  ['Loop', ['Assign', 's', ['Add', 's', ['Divide', 'v', 'j']]],
    ['Element', 'j', ['Range', 1, 3]]],
  ['If', ['Less', 's', 0], ['Assign', 's', ['Negate', 's']]],
  ['Add', 's', 'e']],
  ['Typed', 'v', { str: 'real' }], ['Typed', 'e', { str: 'integer' }]]));

ce.box(['Log', ['fs', 1, 1], 2]).N();        // 1.5025003405291832 (right)
compile(ce.box(['Power', ['Log', ['fs', 1, 1], 2], 3])); // default options
ce.box(['Log', ['fs', 1, 1], 2]).evaluate(); // 0
ce.box(['Log', ['fs', 1, 1], 2]).N();        // ["Log", ["Add", "s", 1], 2]
```

After the compilation, `evaluate()` gives `0` where the value is
`Log(17/6, 2)`, and `N()` gives an expression that holds `s`, the local of
the function. `fs(1, 1)` alone still evaluates to `17/6`. `Ln` in place of
`Log` behaves the same; `Sin(Log(…))` and `Power(fs(1, 1), 5)` do not show it.

## Cause and options

Not investigated. A compilation with the existing compiler leaves a state in
the engine (a memo of the body of `fs` with its local unbound, or a value of
the boxed call) that a later evaluation reads. The compilation must leave the
interpreter's results unchanged. Found by the random differential tester,
which compiles and then evaluates the same programs.
