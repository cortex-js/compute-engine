A function that calls a name gives an error when that name was a function and then gets a number, where a function written after the change gives the product.

## Witness

LaTeX, each line parsed and evaluated in order:

```
a(x) := x^2
h(t) := a(t+1)
h(1)               // 4
a = 3              (ce.assign('a', 3))
h(1)               // Error(incompatible-type, "function", "3"), where it must be 6
k(t) := a(t+1)     // the same body, defined now
k(1)               // 6
```

A notebook reaches it: one cell defines `a` as a function, a later cell gives
`a` a number.

## Cause and options

The body of `h` reads `a(t+1)` as an application because `a` has a function
definition then (`canonicalInvisibleOperator`,
`boxed-expression/invisible-operator.ts`). That reading notes nothing, so
`h` does not wait on `a`, and the number given to `a` derives nothing again.
CE-1333 added the opposite note: a product read from a value of `a` waits
on `a` and is derived again when `a` becomes a function
(`noteValueProduct()`, `provisional-application.ts`).

Option: note an application read from a user function definition the same
way, and derive the literal again when the name loses its function
definition. Cost: every stored body that calls a user function by
juxtaposition then waits on that function, so the repair must skip the
literals whose reading does not change (the CE-1333 repair does this with
`resolvesToFunction()`, `function-utils.ts`) to keep a redefinition of a
function cheap.
