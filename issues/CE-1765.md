A function that calls a name gives an error when that name was a function and then gets a number, where a function written after the change gives the product.

## Witness

LaTeX, each line parsed and evaluated in order:

```
a(x) := x^2
h(t) := a(t+1)
h(1)               // 4
a = 3              (ce.assign('a', 3))
h(1)               // Error(incompatible-type, "function", "3"), where it must be 6
k(t) := a(t+1)     // the same body, defined now
k(1)               // 6
```

A notebook reaches it: one cell defines `a` as a function, a later cell gives
`a` a number.

## Cause and options

The cause is in the PARSER, not in the canonical form. When `a` has a function
definition, `ce.parse('h(t) := a(t+1)')` gives the raw form
`["Assign","h",["Function",["a",["Add","t",1]],"t"]]`: `isFunctionOperator()`
(`latex-syntax/parse.ts`) reads the call at parse time. When `a` holds a value,
the raw form is `["InvisibleOperator","a",["Delimiter",…]]`, and the canonical
form decides (`canonicalInvisibleOperator`). The CE-1333 repair derives a
stored literal again from its RAW operands. For `h` these already hold the
call, so a repair cannot give the product. The user guide states this limit:
"If a host discovers types after an initial parse, it should reparse the
authored source under the final declarations. Reboxing an already chosen
MathJSON structure cannot recover the original ambiguity."
(`cortexjs.io/docs/compute-engine/07-guide-latex-syntax.md`, "Symbol Types and
Ambiguous Applications").

(a) Keep the documented rule (recommended). A host that gives a number to a
name that was a function parses again the cells that use the name. Add one
sentence and this example to the guide section above, and remove this issue.
Cost: none in the engine.

(b) The parser defers the reading for a user function. For a head whose
function reading comes from a user definition (not a library operator and not
a `resolveSymbol` answer), the parser gives
`["InvisibleOperator","a",["Delimiter",…]]`, and the canonical form reads the
call. The canonical half is written and verified (see "State of the work"):
with the raw form of (b), `h(1)` gives `4`, then `6` after `ce.assign('a', 3)`,
then `8` after `a(x) := x^3`. Cost: the raw form of every call of a user
function changes (`ce.parse('f(x)', {form: 'raw'})` after `f(x) := …`); the
tests that pin it change; the parse-time logic that tests for the application
node (postfix `f(x)'`, `f(x)(y)`, the `juxtaposition-as-multiply` and
`ambiguous-*` diagnostics, `ApplicationPolicy`) must accept the deferred form;
the guide sentence above changes. Size M to L. Example: today
`a(x) := x^2; ce.parse('a(t+1)', {form:'raw'}).json` is `["a",["Add","t",1]]`;
with (b) it is `["InvisibleOperator","a",["Delimiter",["Add","t",1]]]`, and the
canonical form is `["a",["Add","t",1]]` in both.

(c) Keep the raw form, and the parser marks the call nodes it read from a user
function (a side table from the raw node to its source reading). The boxing
carries the mark to the stored raw operands, and the repair rewrites only the
marked nodes to the juxtaposition form before it derives the literal again.
Cost: a new channel from the parser to the boxed raw operands that every copy
of a raw form must keep (JSON round trips, `reboxFunctionLiteral`); a copy
that loses the mark silently keeps the old reading. Not recommended.
