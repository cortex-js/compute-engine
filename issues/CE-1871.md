A program whose input is declared with a named type of several numbers (`P2`, a point of two reals) does not compile, on JavaScript or in a shader.

## Witness

At commit `74595f4c6168d444a223289f7b370e8a045300f4`, after `executeEpsil()` of

```
type P2 = tuple<x: real, y: real>
function norm2(p: P2) { p.x * p.x + p.y * p.y }
```

and `ce.declare('n', 'P2')`:

| Program | `javascript` | `glsl` |
| --- | --- | --- |
| `n.x` | declines: `n: the input n of type P2` | the same |
| `norm2(n)` | declines: `n: the input n of type P2` | the same |

`norm2(P2(x, y))`, with `x` and `y` declared `real`, compiles on JavaScript:
a record that the program builds compiles (CE-1652), and one that the host
supplies does not.

Workaround: an input declared with an unnamed tuple type and read by
position (`ce.declare('u', 'tuple<real, real>')`, `u[1]`), which compiles on
both targets, or one input for each field.

## Cause and options

The entry of compiled code has no form for a record input: the check of the
inputs refuses a declared nominal type (`lower.ts`, `inputType()`).

Option on JavaScript: the host passes the engine's value or an array of the
fields, and the entry reads each field once into a record of the code. It
needs a decision on the form that the host passes (`run()` takes plain
JavaScript values for every other input).

Option on GLSL, for a nominal tuple type of two to four numbers of one lane:
a uniform `vec2` to `vec4`, reported in `freeSymbolTypes` as a list input of
a fixed length is. It follows CE-1870.
