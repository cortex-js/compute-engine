For some user functions, the GLSL compiler checks one form of the function body and writes another form.

## Witness

`step(i) := (i + 1, i * 2)` and a function `g(k)` whose body holds
`(v, j) := step(j)` in a loop, compiled to `glsl`. The fragment pass types
the body with the call `step(j)`; the `define` hook of
`src/compute-engine/compilation/gpu-shader-target.ts` calls
`shaderFunctionBody()` a second time and compiles `(j + 1, 2j)`, a new copy
that the pass did not type. The code it writes is correct today: the GLSL
tests pass and the WebGL 2 lane compiles it. But the annotation does not hold
the nodes that emission walks in a function body, so a later reader of the
annotation (step 5 of `docs/plans/2026-11-08-compile-targets-implementation-plan.md`)
would find no facts for them. A run of the GLSL tests that recorded each node
compiled without facts counted 220 such subtrees in 957 function bodies.

## Cause and options

The `define` hook prepares the body again instead of reading the prepared
body of the annotation entry. Making it read that body broke the
common-subexpression pass inside function bodies (4 tests), because that pass
expects a fresh copy.

- (a) The hook compiles the body of the annotation entry, and the
  common-subexpression session is opened on that tree. Size M.
- (b) The pass types the copy that the hook makes, at the hook, with the
  scope of the entry. It types each body twice.

Other places that compile nodes the pass did not type (folded literal tuples
in `compile-folding.ts`, `Assign` statements in `compile-blocks.ts` and
`compile-conditions.ts`, the value of an assigned symbol in
`compile-folded-values.ts`) are listed in the phase D report; they matter only
when step 5 moves the emitter to read the annotation.
