The existing JavaScript compiler does not follow the documented rule of the
`iterationBudget` option (`CompilationOptions.iterationBudget` in
`src/compute-engine/compilation/types.ts`) in three cases: a closed `Sum`
over the budget, a fractional budget, and a `Loop` in a user function.

## Witness

At `7576ecde0f22d8464122c34e4b78da066c528da9`, `new ComputeEngine()`,
`compile(ce.box(…), { iterationBudget })`, default compiler (no profile):

| Program | Budget | Result | The option's doc |
| --- | --- | --- | --- |
| `Sum(Sin(k), Limits(k, 1, 20))` | 3 | `0.9982218844197819` | `NaN` (20 passes over the budget) |
| `Sum(k, Limits(k, 1, n))`, `n` declared `integer`, at n = 4 | 3.5 | `10` | `NaN`: "A finite value is floored" (budget 3, 4 passes); with budget 3 the same code gives `NaN` |
| `g(16)`, with `g := Function(Block(Declare(s, integer, 0), Loop(Assign(s, s + 1), Element(j, Range(1, m))), s), m)` | 3 | `16` | throws `CancellationError` (`iteration-limit-exceeded`): "including … the loops in the bodies of user functions" |

The same `Loop` written inline (`Block(Declare(s, integer, 0), Loop(…,
Element(j, Range(1, 16))), s)`) with budget 3 throws as documented.

## Cause and options

1. The closed `Sum` is folded at compile time by the engine (constant
   folding), so no capped loop is emitted. Option: do not fold a `Sum` or a
   `Product` whose count of terms is over the budget (or fold it to `NaN`).
2. The `Sum` guard compares with the budget as given
   (`compile-loops.ts`, near the comment "Iteration-budget guard":
   `!((upper) - counter < budget)`), while `countLoopPass` uses
   `Math.floor(budget)`. Option: floor it there too.
3. The `Loop` in the body of a user function that the compiled code calls is
   emitted without the pass count. Option: emit `countLoopPass` in the bodies
   of user functions, as the doc says.

Alternatively, change the doc to the behaviour. Size S each.
