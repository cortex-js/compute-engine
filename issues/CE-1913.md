The spread copy `{...f, kind -> "x"}` of a value of a declared record type gives an `incompatible-type` error in the interpreter instead of the copy.

## Witness

```epsil
type Fig = record{__tag: string, kind: string, geom: tuple<real, real>}
function Fig(kind: string, x: real, y: real) { {__tag -> "Figure", kind -> kind, geom -> (x, y)} }
function sp(t: real) { let f = Fig("dot", t, 0); {...f, kind -> "x"} }
```

On main `e13fc32df`, `sp(2)` evaluates to
`Error(ErrorCode("incompatible-type", "tuple<string, unknown>", "Fig"), "Fig({…})")`.
The control, the same spread of a dictionary literal with no declared type
(`let f = {__tag -> "Figure", kind -> "dot", geom -> (2, 0)}; {...f, kind -> "x"}`),
gives the copy. `src/epsil/docs/types.md`, "Records and dictionaries", says
that a new value for a field of a record is a copy made with the spread, and
makes no exception for a declared record type.

The expected value is the copy. Whether the copy keeps the type `Fig` or is
a plain record is part of the fix: the constructor function of `Fig` is the
one place that makes a `Fig`, so the copy is a plain record unless it is
passed to `Fig` again.

## Workaround

Rebuild the value with the constructor function:
`Fig(f.kind, f.geom[1], f.geom[2])`.

## Cause

A value of a declared record type is the tagged application
`Fig(Dictionary(…))` of its constructor. The `Dictionary` literal with a
spread lowers to `DictionaryFrom(Join(ListFrom(f), List(("kind", "x"))))`
(`canonical` of `Dictionary`, `library/collections.ts`). `ListFrom` of
the tagged value `Fig(…)` gives the list `[Fig(…)]`, not its entries, and
`DictionaryFrom` refuses that element: `incompatible-type`, expected
`tuple<string, unknown>`.

## Options

The two documents disagree for this case. `src/epsil/docs/types.md`,
"Records and dictionaries", says that a new value for a field is a copy
made with the spread. The same file, "Values of a new type are opaque",
says that the operations that take a value of a declared type apart do not
reach inside it, and that the `.` accessor "does not make the value a
collection". Probe at `e94195c5e1669607e2b94d453caec68e0e69e528`, with the
witness's `Fig` and `let f = Fig("dot", t, 0)`: `f.kind` gives `"dot"`;
`f["kind"]` and `deleteAt(f, "kind")` are refused (the call stays
unevaluated), as the opacity section says. Each fix of the spread changes
one of the two statements.

- **A. The spread of a value of a declared record type gives a plain
  record.** `{...f, kind -> "x"}` gives
  `{__tag -> "Figure", kind -> "x", geom -> (2, 0)}`, of type
  `record{__tag: string, kind: string, geom: tuple<real, real>}`, not
  `Fig`. `Fig(copy)` (the raw-payload arm) checks it and tags it again.
  The change: the spread segment reads the payload of a tagged value whose
  type is a declared record type (through `innerNominalValue()`, as
  `Field` does), and the opacity section lists the spread next to `.` as a
  way in. It makes no `Fig` without the constructor, because the copy is
  untyped; it reads only the named fields that `.` already reads. Compiled
  code keeps its decline of this spread (a decline is not a defect) until a
  `corpus` or `plausible` witness asks for it there.
- **B. The spread keeps refusing, with an error that names the reason.**
  `{...f, kind -> "x"}` gives an error such as
  `spread-declared-type` with `Fig`, in place of the `incompatible-type`
  with `tuple<string, unknown>`. The records section adds the exception:
  a value of a declared record type is copied with its constructor
  function (`Fig(f.kind, f.geom[1], f.geom[2])`, the workaround above).
- C (rejected): the copy keeps the type `Fig`. It skips the constructor
  function, so it makes a `Fig` that a smart constructor did not
  normalize or check (`frac` in "Constructor functions").

Recommendation: A. A Tycho prelude built on a declared `Figure` record
(the source of this issue) updates one field in many places, and A gives
that idiom with no new way to forge a value of the type; B keeps the
contract but leaves the copy by hand in each place.
