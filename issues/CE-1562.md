A piecewise formula over lists whose branches compute a list is computed point by point instead of by compiled code, so it draws slower.

## Witness

1. `L: list<real>`, `i: list<real>`:
   `Which(Equal(Mod(i, 2), 1), Map(Function(Multiply(2, w), w), At(L, i)), True, 0)`.
2. `N: real`: `Which(Equal(Mod(Range(1, N), 3), 1), Range(1, N), Equal(Mod(Range(1, N), 3), 2), Range(0, N - 1), True, 0)`.

0.194.3: both decline, "a selection at each position whose arms or later
conditions are not pure". The interpreter gives `[10, 0, 14]` and
`[1, 1, 0, 4, 4, 0]`; 0.186.0 compiled the same values. Controls: the same
selections with `Multiply(2, L)` as the arm, and with one condition only,
compile. `Map` of a pure function and `Range` are pure.

Found by the Tycho codegen audit of 2026-11-19: the same MathJSON, with the same options, compiled to JavaScript on CE 0.186.0 and declines on 0.194.3 and on the CE main build of 2026-11-19 16:57, in the document context and on a bare engine. Tycho's instrument `scripts/repros/2026-11-19-ce1560-js-decline-regressions.mts` prints one READY / NOT READY line per issue (READY on 0.186.0, NOT READY on 0.194.3).

## Cause and options

The purity test of the per-position selection does not accept `Map` (with a
`Function`) or a `Range` in an arm or in a second condition. Option: use the
`isPure` of the operands; a `Map` whose function and source are pure is pure.

## CE answer

CE (2026-11-19): fixed after 1610c044ab98d71f2bd8569442cc88565f7cbaa2. A
`Range` arm is read at each position and never built; an arm that builds a
list (`Map`, `At` of a list of indexes) of the length of the first condition
is built before the selection, and so is a later condition of its own length
with no scalar condition before it. Both witnesses compile and give the
interpreter's values. An arm that builds a list of another length still
declines: the interpreter does not evaluate an arm that no position selects.
