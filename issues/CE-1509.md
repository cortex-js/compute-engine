A Tycho user who sets a breakpoint in a `parallel for` loop may never see it stop, and does not know how slow a debug run will be.

## Witness

Tycho's Epsil debugger (spec in Tycho
`requirements/todo/EPSIL_EDITOR_AND_DEBUGGER.md`, phases 3 to 5) builds on the
debug hooks of `executeEpsilAsync` that ship after 0.194.1
(`src/epsil/docs/implementation.md`, "Debugging"). That section lists the
statements that call the hooks (function body, loop body, `if` branch, `do`
block) and the ones that do not (lazy collections, `for` domains). It does not
name `parallel for`.

The `step` function of Tycho's `buddhabrot` showcase entry loops over its
samples with a `parallel for` whose body accumulates (`L[c] += 1`). A user
debugs it from an action that calls `step`.

## Questions

1. On the asynchronous route with debug hooks installed, does the body of a
   `parallel for` call `beforeStatement` and `afterStatement`? If yes, do its
   iterations run in order on the calling thread (no kernel pool)? If no, the
   section should say so, as it does for lazy collections.
2. How much slower is a loop on the asynchronous route with hooks installed
   than the same loop on `executeEpsil`? Tycho shows a warning before a long
   debug run and needs the order of magnitude (the section says only "slower").

The instrument prints, for the installed release: the hooked lines of a
`for` control, the hooked lines of a `parallel for`, and the time of 200,000
loop passes on both routes. Against 0.193.0 the control reports no hooks (the
release has none).

## Cause and options

Documentation, size S: one sentence for each answer in the Debugging section.
If a `parallel for` body calls no hook, Tycho marks its lines "not reachable"
as it does for lazy collections; a request to run it in order with hooks would
be a separate item.

## Answer

CE, 2026-11-19. Both answers are in `src/epsil/docs/implementation.md`,
"Debugging", and in Tycho `docs/COMPUTE_ENGINE.md`, "Debugging Epsil cells".

1. Yes, from the commit that sets `fixed-in` (the release after 0.194.1). With
   debug hooks installed, the body of a `parallel for` calls `beforeStatement`
   and `afterStatement` at each pass, and a hook's pending promise pauses the
   pass. The interpreter runs the passes in order, on the calling thread, with
   no kernel pool, debugger or not. The instrument, run against the source:
   `parallel for: hooked lines [1,2,3,3,3,3,5] (body calls: 4 of 4)`. Before
   that commit the body called no hook. A loop body inside
   `withRandomSeed(seed, …)` still calls none: `withRandomSeed` evaluates its
   body on the synchronous route.
2. About 1.5 times slower. The instrument's 200,000 passes, two runs:
   `executeEpsil 7354 ms, executeEpsilAsync with hooks 11136 ms (1.5x)` and
   `7607 ms, 10296 ms (1.4x)`. A hook that does more work per statement adds
   its own time.
