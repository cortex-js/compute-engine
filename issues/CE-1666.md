A formula that the compiler cannot handle gives no value when it reads a row
that depends on a slider, although the same formula gives the value when it
compiles.

## Witness

```js
const ce = new ComputeEngine();
const imports = createDocumentEnvironment(ce, () => {}).createImports(
  (input) => input('Q', 'real')
);
const rev = imports.prepare([{ id: 'g', latex: 'g' }], syntax);
// syntax: recognize gives the value row g with bodyJson ['Add', 'Q', 1]
ce.pushScope(rev.scope);
compile(ce.box(['Add', 'g', 0])).run({ Q: 4 }); // 5 (compiled)
compile(ce.box(['Expand', ['Add', 'g', 0]])).run({ Q: 4 }); // null (fallback)
ce.withValues({ Q: 4 }, () => ce.box(['Expand', ['Add', 'g', 0]]).evaluate());
// 5
```

Checked on `cc6a51391`, with the probe
the program above. `g` is not
constant (`isConstant` is false). `Expand` makes the compilation decline, so
`run()` is the interpreter fallback (`compilation/interpreter-fallback.ts`).
The fallback's value differs from the interpreter's own value (`withValues`
gives `5`), so this is a wrong value, not a caveat of compiled code.

Probability `medium`: it needs a declined compilation of an expression that
reads a Document row that reads a declared input, which is the usual shape of
a row that reads a slider.

## Cause and options

Not traced. `namesRead()` follows the value of a non-constant definition, and
`g` is not constant, so the cause is elsewhere: perhaps how the fallback binds
the run values (`withBindingValuesFn`) when the read goes through a published
row's value, or the revision's value pass. Start from `fallbackRun` and compare
with `ce.withValues`, which gives the right value.

The known-limitations line of `docs/COMPILATION-MODEL.md` about a free run
input read through a published row names this issue: declaring the name as an
input should be its remedy once this is fixed.
