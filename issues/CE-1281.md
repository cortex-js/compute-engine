In a run of the whole test suite on the development machine, a test file sometimes stops for many seconds, so a test fails or the run takes longer, with no change to the code.

## Witness

- The full run of the release 0.188.1 at `4251e2473`: in
  `flatmap-unknown-finiteness-all-consumers.test.ts`, an evaluation that takes
  0.5 ms alone reached a time limit of 5 s (`Timeout exceeded (0ms)`: the
  deadline had passed when the walk started). The file took 48 s; alone it
  takes about 1 s. The same log says "A worker process has failed to exit
  gracefully". The 5-minute load average was 17.9 on 18 cores at the end.
- The nightly run at the same commit, ten minutes later: Jest's timing cache
  records `declare-spread-override.test.ts` at 89.8 s and
  `logic-failed-operand-order.test.ts` at 56.2 s. Alone they take 0.6 s and
  about 1 s, and in the 23 earlier full runs in the cache, 0 to 5 s and 0 to
  2 s.

The tests now allow for this: a time bound that runs in every run is at least
30 s (`CODING-STYLEGUIDE.md`, the paragraph on performance regressions). The
stall still makes a run longer, and a stall longer than 30 s can still fail a
test.

## Cause and options

Not found. The size of the stalls (a 10,000-fold slowdown of one evaluation)
rules out the sharing of the cores. Candidates:

- Memory: 12 workers, each of which can hold about 3 GB
  (`docs/COMPUTE-ENGINE-BOX-SPECIFICS.md` §2), plus the other sessions, can
  make the machine swap, and a worker whose pages are out stops. To check:
  record `vm_stat` (pageouts, swapouts) and `sysctl vm.swapusage` before and
  after each nightly run, in `scripts/ci-nightly.sh`, and compare the runs
  with stalls.
- A garbage collection of a large heap in a worker that has run many files.
  To check: Jest's `workerIdleMemoryLimit` (restart a worker above a heap
  size) and compare the durations of the slowest files.
- Option, once the cause is known: fewer workers, or `workerIdleMemoryLimit`
  in `config/jest.config.cjs` (a Jest configuration change: dual review).
