In an Epsil program, a sum whose index has the name of a program variable used in its range is not computed when it is written as a statement.

## Witness

On main `18d2f404ea7965409d87378b1452f69f1c4615f3`, with `executeEpsil()` on
a new engine:

```
let n = 3
sum(n, n in 1..n)
```

gives the unevaluated `Sum(n, Element(n, Range(1, n, 1)))`. It must give
`6`. `product(n, n in 1..n)`, `1 + sum(n, n in 1..n)`,
`do { sum(n, n in 1..n) }` and `Sum(n, Limits(n, 1, n))` stay unevaluated in
the same way.

These forms give `6`:

- the value of a declaration: `let r = sum(n, n in 1..n)`, then `r`;
- another index name: `sum(j, j in 1..n)`;
- a variable of the engine in place of the program variable:
  `ce.assign('n', 3)`, then `executeEpsil(ce, 'sum(n, n in 1..n)')`;
- MathJSON: `ce.box(['Sum', 'n', ['Element', 'n', ['Range', 1, 'n', 1]]])`
  with `ce.assign('n', 3)`.

The impact is `minor`: the result is an unevaluated form, not a wrong value,
and the user has a workaround (another index name). The witness is
`crafted`: a user rarely gives the index the name of its own bound.

## Cause and options

The cause is not known. The bound of a clause of `Sum` and `Product` is
outside the scope of its own index (`OWN_INDEX_OUTSIDE_BINDERS`,
`src/compute-engine/boxed-expression/binding-sites.ts`), and the MathJSON
route follows that rule. The difference is between a statement of the
program and the value of a `let`, with a variable that the program declares.
A first place to read is how the statement route of `executeEpsil()` binds
the names of a statement to the program variables
(`src/epsil/execute-epsil.ts`, the program environment), and whether it
rebinds the `n` of the range to the index. `Loop` and `Comprehension` do not
have this defect after CE-1827: `let n = 3`, then `[n for n in 1..n]` gives
`[1, 2, 3]`.
