A Desmos list filter whose condition is shorter or longer than the list must keep the matching elements, as Desmos does.

## Request

A library operator for a masked read: the elements of a base list at the
positions where a condition list is defined and true, read up to the shorter
of the two lists. The name and the form are CE's choice; the instrument
expects a builder `(base, condition) => [<name>, base, condition]` in its
`OPERATORS.mask`.

Why: by the user decision of 2026-11-14, the new compiler has no hook for a
host to change how an operator compiles. Where today's operators cannot
express a rule, the engine gets a library operator with that meaning, and the
host rewrites its tree to it before it compiles. Tycho now does this rule in
an `evaluate` and a `compile` handler that it attaches to `At` for documents
imported from Desmos. The new compiler declines a definition with a host
`compile` handler, so each such row falls back to the interpreter.

## Meaning

`L = [1,2,3,4,5]`, `K = [1,0,1]`, `D = [1,0,1]`, `M = [1,5,3,4,5]`. The
comparisons are those of CE-1321 (by position, up to the shorter list).

| Desmos | condition | result |
| --- | --- | --- |
| `L[K=1]` | `[T,F,T]`, shorter than the base | `[1,3]` |
| `K[L>2]` | `[F,F,T,T,T]`, longer than the base | `[1]` |
| `L[L>D]` | `[F,T,T]` | `[2,3]` |
| `L[L=M]` | `[T,F,T,T,T]` | `[1,3,4,5]` |

Ground truth: official Desmos API, 2026-10-03 (Tycho
`scripts/repros/2026-10-03-positional-list-comparison-probe.mts`).

Edge cases for CE to decide and document. Desmos keeps only positions where
the condition is defined and true, so a hole (`NaN`, `Missing`) in the
condition drops that position; an empty base or an empty condition gives an
empty list. A point list as base keeps whole points.

Expected on each route: the interpreter and the `javascript` target give the
list above. On GLSL, a result whose length depends on values cannot be a
fixed-size array: a decline is acceptable.

## Today (0.190.0)

`At(L, mask)` with a mask of a length other than the base's is an error in
the interpreter and `NaN` compiled. With the comparisons of CE-1321 as stock
relations, `L[L=M]` is `At(L, False)`.

## Can existing operators express it?

Not that Tycho found: `Filter` takes a predicate of the element, not of its
position, and `At` with a boolean list needs equal lengths. A form like
`Filter(Range(1, Min(Length(L), Length(C))), i -> At(C, i))` mapped through
`At(L, …)` would work on the interpreter, but it reads `C` by index in a loop,
and it changes the tree a user sees in a serialized row. If CE finds a form
with existing operators that compiles well on both targets, Tycho will use
it and this request can close.

History: CE declined the Desmos reading as the DEFAULT of `At` on 2026-10-04
(Tycho ledger row 365). This request is for a separate operator, so the
default stays.

## CE answer

CE (2026-11-14): P3 confirmed. Disposition: no new operator is proposed when
the condition is a comparison; the rewrite to existing operators gives the
table. Probed at `08ef3106ecbce52e702f1f06451ebf3bb330c926`, with the lists
of the issue and `n = Min` of the lengths of the base and of the lists of the
condition:

| Desmos | Form | Interpreter (materialized) | `profile: 'ir'` | Existing compiler |
| --- | --- | --- | --- | --- |
| `L[L>D]` | `Map(i ↦ At(L, i), Filter(Range(1, n), i ↦ Greater(At(L, i), At(D, i))))` | `[2, 3]` | `[2, 3]` | `[2, 3]` |
| `L[L=M]` | the same with `Equal` and `M` | `[1, 3, 4, 5]` | the same | the same |
| `K[L>2]` | `Map(i ↦ At(K, i), Filter(Range(1, n), i ↦ Greater(At(L, i), 2)))` | (not probed) | `[1]` | `[1]` |
| `L[C]`, `C` a list of booleans | `Map(i ↦ At(L, i), Filter(Range(1, n), i ↦ At(C, i)))` | `[1, 3]` | declines | `[1, 3]` |

The condition is written inside the predicate of the `Filter`, element by
element, so no list of booleans is built and CE-1321's form is not needed
here. The last row declines on the new compiler: a read of a list of
booleans at an index that it cannot prove in range declines ("an index that
can be out of range, of a list of booleans"), although `n` bounds it. That
decline is a limit of the new compiler, not of the form; it is removed only
if Tycho's corpus has such a row (a mask that is a list variable and not a
comparison): say how many. A hole in the condition drops the position (a
comparison with `NaN` is false). GLSL declines a result whose length depends
on values, as the issue accepts. Workaround, which is also the proposed
answer: Tycho rewrites to these forms at compile time, and evaluates the same
rewritten tree in the interpreter, so that both routes read one tree. If
Tycho's instrument confirms the tables with this builder, this issue can
close.

CE (2026-11-14): Tycho's instrument reads READY with the builder of the
answer above, 4 of 4 cases on 0.190.0, interpreter and compiled JavaScript
(Tycho `8f99844d313b32f02b91eee153f945bdd0e195ca`). Tycho counted its corpus
(a codegen audit of 779 documents, 22,505 compile calls): 23 masks that are
comparisons, in 4 documents, and no mask that is a list variable of booleans.
So the decline of the new compiler for a read of a list of booleans at an
index it cannot prove in range stays. Closed with no change in the engine.
