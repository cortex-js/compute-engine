The derivative of a variable that holds a formula is 0 instead of the derivative of the formula.

## Witness

Epsil: `let G = sin(x); D(G, x)` prints `0`; it must print `cos(x)`. The same
with `ce.assign('G', ce.box(['Sin', 'x']))` then
`ce.box(['D', 'G', 'x']).evaluate()`, and with `2 G` in place of `G`.
`ce.box('G').evaluate()` gives `Sin(x)`. The report used
`let F = cdf(normalDistribution(0, 1), x)`. Main (a28dd290f) and 0.186.0 give 0.

## Cause and options

`D` holds its operand and treats a symbol other than the variable as a
constant; it does not read the symbol's value. Option (a): before
differentiating, replace each symbol that holds a value (not a library constant,
not the variable) by its value, as `withAssignedValues` in
`library/calculus.ts` does for `NIntegrate`. Check first whether a documented
rule says that `D` does not read values (`docs/SCOPING-MODEL.md`) and how
CE-1219 (compiled `D(f, x)` when `x` holds a value) interacts. `Integrate`
probably has the same defect: check it in the same change.

## Question for the board

A fix changes a documented contract. `docs/SCOPING-MODEL.md` ("Ruled
2026-09-21 — the LEXICAL reading of a binder") says that a binder does not
capture a stored value's free name: with `a := n + 1`, `Σ_{n=1}^{3} a` is
`3n + 3`, not `9`. The same document lists the variable of `D` and of
`Integrate` as binder variables. With `G := sin(x)`, the `x` in the value of
`G` is the global `x`, not the variable of `D`, so the current result `0` is
what that rule gives. The other calculus binders follow the rule in the same
way at `6d09b2f1e5d1c6649be6c6cc1339d5ceda4bfe2d`:

```
G := sin(x)
D(G, x)                       0
D(2G, x), D(G^2, x)           0
Integrate(G, x)               G·x
Integrate(G, Limits(x, 0, 1)) sin(x)
lim_{x→0} G                   sin(x)
Σ_{x=1}^{3} G                 3 sin(x)
H := y sin(x); D(H, y)        0
```

One exception exists already (CE-157, `calculus.ts`, the `D` evaluate
handler, `parameterValueVariesWith`): a parameter of the running call whose
value contains the variable is read, so with `g(f) := D(f, x)`, `g(x^2)` is
`2x`. That exception is not in `docs/SCOPING-MODEL.md`.

A workaround exists for both options: a function in place of a formula.
`G(x) := sin(x)`, then `D(G, x)` is `cos(x)`, `D(2 G(x), x)` is `2cos(x)`
and `Integrate(G(x), x)` is `-cos(x)`.

Options:

- (a) Recommended. `D`, `Integrate`, `Limit` and `Series` (the operators
  whose variable is a variable of a formula, not an iteration index) read
  the value of each free symbol that holds a value and is not a constant,
  before they work, as CE-157 does for a parameter. An occurrence of the
  variable's name in that value denotes the variable. `D(G, x)` is
  `cos(x)`, `D(2G, x)` is `2cos(x)`, `Integrate(G, x)` is `-cos(x)`,
  `lim_{x→0} G` is `0`, `D(H, y)` is `sin(x)`. `Sum`, `Product` and the
  comprehensions keep the 2026-09-21 rule (`3n + 3`). The rule and the
  CE-157 exception are written in `docs/SCOPING-MODEL.md`. This is what a
  user of a computer algebra system expects (the Epsil witness
  `let F = cdf(normalDistribution(0, 1), x); D(F, x)`), and what the Epsil
  library reference was going to show.
- (b) Keep the rule for every binder. The current values stay; the rule and
  the workaround (a function in place of a formula) are written in
  `docs/SCOPING-MODEL.md` and in the Epsil reference for `D` and
  `Integrate`, and the issue is closed as "by design". The CE-157 exception
  stays and is documented as the one exception.
- (c) Option (a) for every binder, `Sum` included (`Σ_{n=1}^{3} a` is `9`):
  this reverses the 2026-09-21 ruling.

The implementation of (a) is a substitution before the work, as
`withAssignedValues()` in `library/calculus.ts` does for `NIntegrate`, with
the variable's name excluded from the shield for the substituted value; it
is in the evaluate handlers of four operators and needs a dual review.
