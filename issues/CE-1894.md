A slider change can redraw a polygon collection through the slower path when its polygons vary in vertex count.

## Witness

CE 0.202.0 declines JavaScript compilation of both valid MathJSON expressions
below with “the operator Polygon is not supported by the compiler.” Declare
`n` as `integer`, compile with `symbolic: ["n"]` and `optimize: false`, and pass
`n` at runtime.

```json
["Comprehension",
  ["Polygon", ["Tuple", "k", 0], ["Tuple", "k", "n"], ["Tuple", 0, "n"]],
  ["Element", "k", ["List", 1, 2]]]
```

```json
["Comprehension",
  ["Polygon", ["Take",
    ["List", ["Tuple", 1, 1], ["Tuple", 2, 4], ["Tuple", 3, 9],
      ["Tuple", 4, 16], ["Tuple", 5, 25]],
    ["Add", "k", "n"]]],
  ["Element", "k", ["List", 1, 2]]]
```

The instrument confirms that the real Tycho materializer draws both expressions.
In the second, it returns two polygons with 3 and 4 vertices at `n = 2`, and 4
and 5 at `n = 3`, in source order. A flat tuple comprehension compiles, as does
one `Take` of runtime length. Stripping only the `Polygon` tag from the second
witness still declines with “a list of lists of run-time length.”

## Cause and options

The built-in `Polygon` head is an opaque geometry tag with no compiler
lowering. Tycho D-266 currently compiles a batch of flat vertex tuples when
the arity is known and interprets the variable-arity witness. The latter case
motivates the request and is less common than fixed-vertex polygon plots.

Please support geometry output on JavaScript, including a list or comprehension
of polygons. A flat vertex buffer plus polygon offsets would fit Tycho's use
and avoid boxing each point. A nested result with equivalent boundaries would
also suffice if it handles runtime lengths. Preserve member order, vertex
order, and the positions of undefined vertices that the host uses to split
paths. Tycho owns rendering and point-in-polygon behavior stays outside the
request. GLSL and interval JavaScript are outside its scope.

Tycho half on adoption: verify the agreed result layout against both witnesses
at both input values, then compare parity and redraw time with the current
materializer. The instrument reports REVIEW if both expressions start
compiling before the result layout has been agreed and asserted.

## Decision

User decision 2026-11-27: return polygon values with an explicit `kind`
field, following the `Figure` convention. The JavaScript result for one
polygon is `{ kind: "polygon", geom: [x1, y1, x2, y2, ...] }`. A
comprehension returns these records in source order. Preserve empty records
and undefined vertex positions. This specifies the result shape and leaves
the compiler lowering to CE.

On installed CE 0.202.0, a named-tuple model compiled a single polygon and
an explicit list of fixed-size polygons. A fixed-size comprehension
declined with “a record made in a build, a filter or a random frame.”
A single record with a runtime-sized `geom` and the variable-size
comprehension both declined with “a record with a field of a run-time
length.” A standalone `Take` of the same runtime length compiled.

```epsil
type PolygonValue = tuple<kind: string, geom: list<real>>
let single = (n: integer) => PolygonValue("polygon", [1, 0, 1, n, 0, n])
let batch = (n: integer) =>
  [PolygonValue("polygon", [k, 0, k, n, 0, n]) for k in [1, 2]]
let variable = (n: integer) =>
  PolygonValue("polygon", Take([1, 1, 2, 4, 3, 9], 2*n))
```

Compile each function value to JavaScript with optimization disabled, then
run it at `n = 2` and `n = 3`. Prefer assembling the records at the
JavaScript result boundary if the existing record lowering cannot carry
the variable-length geometry through a comprehension.

Updated result layout, 2026-11-27. Preserve the operator as
`__tag: "Polygon"`. The built-in result has the fields `__tag` and `geom`.
A comprehension returns an array of these records in source order. When
emitting a tagged record, reject a declared field named `__tag` rather than
overwriting it. Adding tags to existing named-record results is a separate
compatibility decision.

User decision 2026-11-27: Approved design with tagged records and arrays of tagged record for lists and comprehensions

## CE answer

The board raised this to P1 and approved tagged results. The JavaScript
implementation is in `113675abb`. Until adoption, Tycho can keep
compiling the flattened fixed-arity vertices and interpreting
variable-arity members.

Ran the Tycho instrument against the implementation. Both polygon forms
compiled, both controls compiled, and the host materializer returned the
expected polygons at `n = 2` and `n = 3`. CE's regression tests assert
the tag, coordinates, and member order at both inputs. The current
instrument reports `REVIEW` when both forms compile. Tycho can now add
result assertions and measure redraw time at adoption.

For example, `Polygon((1,2), (3,4), (5,6))` would return
`{ __tag: "Polygon", geom: [1, 2, 3, 4, 5, 6] }`. A polygon
comprehension would return an array of those records in comprehension
order. The variable-arity witness would have geometry arrays of lengths
6 and 8 at `n = 2`, then 8 and 10 at `n = 3`. Keep every vertex slot and
let Tycho split paths at pairs containing a non-finite coordinate. An empty
polygon keeps its record with `geom: []`.

The compiler builds flat numeric rows and attaches the statically known
polygon tag at the JavaScript return site. This supports direct polygon
results, literal lists of polygons, and comprehensions with a polygon
body. A single coordinates buffer with offsets is an alternative if
redraw measurement shows that per-polygon allocation is costly.
