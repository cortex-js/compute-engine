No user-visible symptom: Graph Paper keeps four hooks that rewrite a row before it is classified, and their code duplicates what the Document API may already know.

## Witness

Tycho classifies each row of a plot document (`plot-core/classify-formula.ts`)
with options that the document manager supplies:

- `threadMacroRefs` (`classify-formula.ts`, line 6064), served by
  `threadMacroRefsForRow` (`graph/document-ce-manager.ts`, line 6633): it
  writes out `with` bodies, free-name bodies and the calls that reach an
  axis;
- two `expandFunctionRefsBoxed` hooks (`modes/document/initialization.ts`,
  lines 1384 and 1463): one threads, one expands classification snapshots;
- `expandFunctionRefsStructural` and `shadowedParamsFor`.

Since the CE Document port (CE 0.200.0), Tycho also reads each row's prepared
form (`preparedRow`, `initialization.ts` line 1358), but the hooks above are
still needed: nothing in Tycho shows that the prepared revision gives the
same trees.

## Cause and options

The question for CE: for a row of a prepared revision, does CE expose (or
could it expose) the row's expression with document-function bodies, `with`
bindings and free-name bodies written out, and the names that a function
parameter shadows? For each hook, Tycho would like one of: "the prepared
revision gives this already (where)", "CE could add it", or "this stays a
host concern".

Workaround: the hooks, which work today.
Tycho half on adoption: remove each hook that the prepared revision answers
(`threadMacroRefsForRow` in `src/graph-paper/graph/document-ce-manager.ts`,
the two `expandFunctionRefsBoxed` hooks of
`src/graph-paper/modes/document/initialization.ts`), and read the row from
the prepared revision instead.
