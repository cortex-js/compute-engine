Simplifying the definitions used by Voronoi plots currently requires keeping an early scalar-versus-list decision in Tycho.

## Witness

Desmos `sum(i=d..d, {d=m:10^9,d})` replaces the minimum element of `d` before taking another minimum. Tycho lowers a proven list to `Map`, otherwise to the scalar one-term identity. The decision reads registration/collection machinery that the macro migration would otherwise simplify.

One raw lowering could be:

```text
Min(Apply(Function(Which(k=m, 10^9, True, k), k), d))
```

The instrument uses runtime `x: real`, `m: real`; `d` is `x^2` or the literal list `[x^2,(x-1)^2,(x-2)^2]`. Fresh engine per target/shape. On installed CE 0.192.0:

| Form | JS | interval-js | GLSL |
| --- | --- | --- | --- |
| scalar Apply | passes, correct value | passes | declines Apply |
| fixed-list Apply | passes, correct value | declines List | declines Apply |
| fixed-list Map control | passes, correct value | passes | passes |

The request preserves Apply's existing scalar/list broadcasting semantics. It does not request parameterized macros or a Desmos-specific primitive. Fixed-width lists suffice for the shader request. G12 of the compiler plan already records scalar Apply support on the IR route and deliberate refusal of list arguments after a wrong whole-list binding; this request asks for the missing mapping behavior, not removal of that safety refusal without a lowering.

## Options

Preferred: support function-literal Apply with scalar or mapped fixed-list arguments on the required targets, or provide a portable equivalent. Then Tycho can lower the equal-bound idiom once on the raw tree before declaring macros, without asking its carrier registry for the branch. Run the instrument (READY requires all Apply cases) and the actual Voronoi render/snapshot tests before replacing the oracle in `collection-bigop-lowering.ts` and its manager caller.

Workaround: retain the current Map/scalar split and its collection oracle; macro migration is still possible with a staged lowering pass. This is a simplification request, not a newly discovered shipped wrong-value regression. No GPU execution claim is made by the compile-only instrument.

Tycho half on adoption: replace the collection-oracle split in `src/graph-paper/graph/collection-bigop-lowering.ts` only after the portable Apply instrument and all five actual Voronoi/snapshot witnesses pass; remove the manager oracle dependency if no remaining caller needs it.

## CE answer

CE (2026-11-15): P3 confirmed, witness `corpus` (`neyret/62urmx2dcm`).
Disposition: pool, as work of the `ir` compiler (`compilation/ir/lower.ts`).
Workaround: the one the issue states (keep Tycho's Map/scalar split).

- **Today.** The instrument, run against the source at
  `3592da6cbad8f3c51dd3c7208ad9689466c804a8`, gives the table of the issue,
  unchanged. Scalar `Apply` compiles on JS and interval-js and declines on
  GLSL. List `Apply` compiles on JS with the mapped value (0.49) and declines
  on interval-js and GLSL. The `Map` control compiles on all three. The JS
  pass is on the instrument's default profile. With `profile: 'ir'`, list
  `Apply` declines on JS too, with the same message (`ce-interval`, on
  `3592da6cb`).
- **Why the change is sound.** The shape of `Apply(Function(body, k), d)`
  comes from the static type of `d`, so it is settled at compile time
  (`docs/COMPILATION-MODEL.md`, R1 to R6). In the interpreter, a literal
  with one untyped parameter applied to a list maps over the leaves
  (`applyLiteralMaps()`, `library/core.ts`). For a flat list, this is
  `Map(Function(body, k), d)`.
- **The fix.** In the `Apply` case of `lower.ts`, a literal of one parameter
  whose argument is a flat list, on the route that `applyLiteralMaps()`
  maps, lowers through `lists.build()`, the path of `Map`. Today that case
  declines every list or tuple argument. A deeper list (the interpreter maps
  to the leaves), a tuple, a generic literal and a literal of several
  parameters with a list argument still decline. This removes the list
  decline with no new handler.
- **Correction (`ce-compiler`, measured on main plus G17 with
  `profile: 'ir'`).** The instrument calls `compile(expr, { to })`, the
  default route, where the existing compilers answer. "GLSL declines" at
  `3592da6cb` is the existing GLSL target, which is to be deleted and is
  not changed. On the profile:
  - Scalar `Apply` compiles on JS and GLSL. The scalar case declines on
    all three targets because of `Min` of one operand ("Min with 1
    operands"). Fix: `Min(v)` and `Max(v)` of one scalar are `v`.
  - GLSL declines every `Map` on the profile ("the region build (a Map, a
    Filter or a Range) on glsl"), also over a list of stated length. The
    list case therefore also needs a `Map` over a list of constant length
    on GLSL, the larger part of the work.
- **Plan.** `ce-compiler` does JS and GLSL as batch G18, after G17:
  the one-operand `Min`/`Max`, the `Apply` hunk above, and `Map` of constant
  length on GLSL. `ce-interval` adds the interval containment tests. Order
  (user, 2026-11-15): Tycho's joint audit of the build on `3592da6cb` comes
  first; CE-1344 follows in a later build, which `ce-compiler` makes and
  announces here.
- **For Tycho.** After G18, the instrument is READY only with
  `profile: 'ir'` in its `compile()` call, or once the profile is the
  default. Tycho's adoption must compile through the profile at that seam.
- **Tests owed with the fix:** the instrument's six `Apply` cases. The JS
  values match the interpreter for the scalar and the flat list, and a
  nested list and a tuple argument still decline.
