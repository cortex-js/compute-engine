A list that holds a range prints the range as `Range(1, 2)`, while the range alone prints its elements.

## Witness

```ts
const ce = new ComputeEngine();
executeEpsil(ce, '1..3').value.toString();          // "[1,2,3]"
executeEpsil(ce, '[1..2, 1..3]').value.toString();  // "[Range(1, 2),Range(1, 3)]"
executeEpsil(ce, '(1..3, 2)').value.toString();     // "(Range(1, 3), 2)"
executeEpsil(ce, '{1..3}').value.toString();        // "Set(Range(1, 3))"
```

The Epsil CLI prints the same text (`epsilValueText`, `src/cli/format.ts`).
The LaTeX of the list is `\bigl\lbrack1..2, 1..3\bigr\rbrack`, which reads
well. A user reads `Range(1, 2)` as a call that was not evaluated.

Since CE-1601, the value of a program that ends with a `map` whose callback
gives a range is such a list, so `function upTo(n) { 1..n }` then
`map(upTo, [2, 3])` prints `[Range(1, 2),Range(1, 3)]`. Before CE-1601 that
program printed `[[1,2],[1,2,3]]`, because its value was the lazy `Map`,
and the text of a lazy collection previews its elements at every depth. A
comprehension `[upTo(u) for u in [2, 3]]` printed `[Range(1, 2),Range(1, 3)]`
before CE-1601 too.

## Cause and options

`toString()` previews a lazy collection only when the expression itself is
one (`abstract-boxed-expression.ts`, the `DISPLAY_MATERIALIZATION` branch of
`toString()`). An element of a `List`, a `Tuple` or a `Set` is written by
the text serializer (`toAsciiMath`), which writes a `Range` as a call. A
`Range` element stays a range in a literal by a user decision (2026-10-25,
ROADMAP CE-39.3), so the value is correct: only its text is in question.

(a) Recommended: the text serializer writes a `Range` element as Epsil
writes it, `1..2` (`[1..2, 1..3]`), which reads back as the value. Size S.

(b) The text of a literal previews each lazy element, as the top level does
(`[[1,2],[1,2,3]]`). The text then does not show that the element is a
range.
