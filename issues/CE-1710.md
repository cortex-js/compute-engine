At machine precision, a fraction times a short list of floats differs from the scalar products in the last digit: `(2/3)·[81.67574227865587, 2.5]` gives `54.450494852437245` where `(2/3)·81.67574227865587` gives `54.45049485243725`.

## Witness

At `3f0a22cee9716930aa6ca0403c17645eec421cfd` with the CE-1653 change in the
working tree:

```js
ce.precision = 'machine';
ce.box(['Multiply', ['Rational', 2, 3], ['List', 81.67574227865587, 2.5]]).N().json;
// ["List", 54.450494852437245, 1.6666666666666665]
ce.box(['Multiply', ['Rational', 2, 3], 81.67574227865587]).N().json;
// 54.45049485243725 (and 1.6666666666666667 for 2.5)
```

The scalar product computes `(x·2)/3`, the list `x·(2/3)`, with `2/3`
rounded first. Of 180 random cells (a fraction times a list of three
floats, 60 fractions), 52 differ in the last digit. The same list at 21 and
50 digits agrees with the scalar products since the CE-1653 fix.

## Cause and options

Not confirmed. `mulTensors()` (`boxed-expression/arithmetic-mul-div.ts`)
rounds an exact scalar beside a tensor of floats at machine precision
(`multiply(...scalars)`, the condition "Beside tensors of floats only, the
scalar is floated"), so the cell products multiply by the rounded fraction.
The machine kernel `machineBroadcast()` (`machine-broadcast.ts`) already
computes `(x·p)/q` for an exact rational scalar, but it is not reached for
this list. The fix: keep the scalar exact at machine precision too and let
the machine kernel take it, checking that a long list of floats divided by
3 keeps its speed (the reason the scalar is floated).
