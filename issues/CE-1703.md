A function written in place and applied to a list at a parameter declared as a number gives a type error, while the same function given a name maps over the list.

## Witness

At `9fd1134ca90185437d1f6b88846ab6fd9992e5f3`:

```js
const lit = ['Function', ['Add', 'k', 'x'], 'k', ['Typed', 'x', "'real'"]];
ce.assign('kx', lit);
ce.box(['kx', ['List', 1, 2], ['List', 10, 20]]).evaluate().json;
// ["List", 11, 22]
ce.box(['Apply', lit, ['List', 1, 2], ['List', 10, 20]]).evaluate().json;
// ["Error", ["ErrorCode", "'incompatible-type'", "'real'", "'vector<integer^2>'"], …]
ce.box(['Apply', lit, 1, ['List', 10, 20]]).evaluate().json;  // the same error
```

With the CE-1697 fix, the signature `(L, k, x: real)` where `L` binds whole
splits the same way: `three([1,2,6], [1,2], [10,20])` is `[14, 25]`, and
`Apply` of the literal is the same `incompatible-type` error at `x`.

Workaround: assign the literal to a name and call it.

## Cause and options

Reported by the review, not confirmed: on the `Apply` route the
validation signature relaxes `unknown` to `any`
(`pinnedValidationSignature`, `boxed-expression/box.ts`), so the check of
the arguments (`threadableGate`) does not see a mapped slot and checks the
list against `real`. The fix: check a list at a declared scalar parameter
element by element on the `Apply` route, as the named route does.
