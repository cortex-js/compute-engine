Compiled code ignores the range of a declared type, so an input declared non-negative still pays for complex arithmetic and for domain guards.

## Witness

On main (`8682f4f1c2dba20e87cbd0dd0d34dbbe498ebb24`), `new ComputeEngine()`, `compile(expr, { fallback: false })`:

```ts
ce.declare('k', 'real<0..5>');
ce.declare('x', 'real<1..9>');
```

| Expression | Target | Code today | Code the range allows |
| --- | --- | --- | --- |
| `Sqrt(k)` | javascript, `mode: 'complex'` | `_SYS.ir.csqrt(_SYS.ir.cplx(_.k))` | `Math.sqrt(_.k)` |
| `Ln(x)` | glsl | `(x > 0.0 ? log(x) : uintBitsToFloat(0x7fc00000u))` | `log(x)` |
| `Abs(k)` | javascript, glsl | `Math.abs(_.k)`, `abs(k)` | `_.k`, `k` |
| `Sqrt(Square(k))` | javascript | `Math.sqrt((_.k * _.k))` | `_.k` |
| `Abs(Subtract(x, 1))` | javascript | `Math.abs((_.x + (-1)))` | `(_.x + (-1))` |

`simplify()` already uses the range: it gives `k`, `k` and `x - 1` for the
last three rows. The deleted JavaScript compiler dropped `Abs` of a value
proved non-negative (`identityPassthrough` in `javascript-target.ts`, in the
tree before `e16216680ad989db8c278027e4e9c18e86a9e86f`).

The largest gains are the first two rows: the complex lane of a radicand,
logarithm or power base declared non-negative, and the GLSL guards of `log`,
`sqrt` and `pow`. Dropping `Abs` saves one instruction.

## Cause and options

The IR reads no input type to prove a sign (`ir/README.md`, the complex mode
paragraph: "The type of an input is not read"). Its reason is that today
`ce.assume(s >= 0)` narrows the type of `s` to `real<0..>` and `forget()`
widens it again, so the code would keep a fact that no longer holds. The user
ruled on 2026-11-19 that an assumption must not change a type (that behaviour
is a defect, to be fixed separately). With that fixed, the range of a type is a
declaration, and using it is sound: a value outside its declared type gives an
unspecified result (AGENTS.md, compiled-code caveats;
`docs/COMPILATION-MODEL.md` already says a GPU target may drop `|x|` for
`x: real<0..5>`).

Fix: derive the sign of a leaf (an input, a parameter, a local) from the range
of its declared type, and use it where the IR already uses a proved sign: the
real lane in the complex mode (the rule that admits `Abs`, `Exp` and even
powers), the builtin `pow()` of a base known `>= 0`, the GLSL domain guards,
and `Abs` / `Sqrt(Square(…))` of a non-negative value. Until the assumption
defect is fixed, read the declared type of the definition, not the current
type, or wait for that fix. Update the `ir/README.md` paragraph and the
COMPILATION-MODEL caveat line to state that a declared range is used on every
target.
