A function with a typed parameter that calls a second function, which the same block defines after it, is applied to each element of a list argument and gives errors in place of its value.

## Witness

Checked 2026-11-08 at `009e6b12c7e063190406459007eb8825f3140195` with the
fix of CE-1089 applied:

```
Block(Assign(q, (n: number, a) ↦ n + h(a)), Assign(h, t ↦ Count(t)), q(1, [1, 2]))
  → [Error(incompatible-type, collection, 1, "while applying 'q' element-wise …"),
     Error(incompatible-type, collection, 2, …)]
  expected: 3
```

With the two `Assign` in the other order, the value is `3`. The same
difference occurs when the `Assign` of `h` is not a statement of the same
list as the `Assign` of `q`, for example inside an `If` or a nested `Block`.

## Cause and options

The fix of CE-1089 (`afterFunctionAssignment()`, `function-utils.ts`)
derives again the signature of an earlier function of the same statement
list when the `Assign` of a function that it calls runs. It does this only
for a definition with an inferred signature. A literal with an annotated
parameter gets a signature derived from the type of the literal when it is
assigned (`_derivedSignature`, `assignValueAsOperatorDef()` in
`engine-declarations.ts`), and `_update({ evaluate })` does not derive that
signature again. The bare slot of `a` stays a scalar slot.

Option: for a `_derivedSignature` definition, compute again the definition
that `assignValueAsOperatorDef()` gives for the literal (the signature, the
`broadcastable` flag and the validation signature) and install it. For the
`Assign` in a nested statement, keep the list of assigned functions on the
run of the enclosing list. Workaround: assign `h` before `q`.
