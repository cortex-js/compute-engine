The numeric value of a number times a list of fractions has a wrong last digit: `3·[1/3, 2/3]` gives `0.999…9` for the first element, not `1`.

## Witness

At the default 21 digits:

```ts
const ce = new ComputeEngine();
ce.box(['Multiply', 3, ['List', ['Rational', 1, 3], ['Rational', 2, 3]]]).N().json;
// ['List', {num: '0.999999999999999999999'}, {num: '2.000000000000000000001'}]
ce.box(['Multiply', 3, ['Rational', 1, 3]]).N().json; // 1
```

The elements should be `1` and `2`, as the scalar products give. The same
error is in a matrix of fractions times a number, in a list of fractions
times a list (`[1/3, 2/3]·[3, 3]`), and in a fraction times a point:
`Multiply(Rational(1, 3), Tuple(3, 6)).N()` is
`(0.999…9, 1.999…98)`, through `mulTuples()`, which approximates the
fraction before it multiplies each component.

Above machine precision, a fraction times a list of floats only has the
same error: `Multiply(Rational(1, 3), List(1.5, 2.5)).N()` is
`[0.4999999999999999999995, 0.8333333333333333333325]`, where
`Multiply(Rational(1, 3), 1.5).N()` is `0.5`. `mulTensors()` approximates
the fraction when no cell is exact, so that the big-decimal kernel
(`bigFloatBroadcast()`) applies; that kernel declines an exact rational.
At machine precision the same list gives `0.5`.

## Cause and options

The `Multiply` handler (`mulEvaluatedOperands()` in
`src/compute-engine/library/arithmetic.ts`) evaluates a list operand under
`.N()` before the product, so each fraction is rounded first, and the tensor
kernel (`mulTensors()` in `boxed-expression/arithmetic-mul-div.ts`) then
multiplies the rounded cells. CE-1634 fixed the other side: an exact scalar
factor now stays exact in that kernel, and `[1, 2, 3]/3` is `[0.333…, 0.666…7, 1]`.

The fix: under `.N()`, keep the exact integer and rational cells of a list
literal exact until the cell product, as `mulN` does for a scalar product, and
round the product. The machine kernels (`scaleMachineVector()`,
`bigFloatBroadcast()`) decline an exact rational, so the cost is in the
boxed-cell route only. For the list of floats, give `bigFloatBroadcast()` an
exact rational operand, computed as the scalar product computes it
(`mulNEvaluated()`: `(x·p)/q`, the numerator first); keeping the fraction
exact without that kernel made `L/3` for 10,000 floats about four times
slower at 21 digits (measured while fixing CE-1634).
