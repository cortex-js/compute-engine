With the experimental compiler profile `'ir'`, a function that takes a list, called with a number, is refused with the message of an internal error, where the message should name the argument.

## Witness

On `861a453f35f7fabfde7a19314827ad07d532a30b`:

```ts
const ce = new ComputeEngine();
ce.declare('x', 'real');
ce.declare('f', '(unknown) -> unknown');
ce.assign('f', ce.box(['Function', ['Sum', 'p'], ['Typed', 'p', "'list<real>'"]]));
compile(ce.box(['f', 'x']), { profile: 'ir', fallback: false });
// Could not compile with the profile 'ir': internal error:
// Cannot read properties of undefined (reading 'v')
```

The same on `to: 'glsl'` and `to: 'interval-js'`. The interpreter gives an
`incompatible-type` error for `f(x)`, and the existing compiler declines
with a message that names the parameter (`… the type list<real> of the
parameter p …`). With the fallback (the default), `compile()` returns the
result of the fallback, so no wrong value is given; only the message is
wrong.

## Cause and options

Not read. A `TypeError` in the lowering of the call (a scalar argument at a
parameter that the literal annotates as a list, under a declared signature
of `unknown`) reaches the adapter, which reports it as an internal error.
Fix: decline at that argument with a message ("an argument of f that is not
list<real>"), as the neighbouring checks of `ir/lower-functions.ts` do.
