In Tycho's code editor most valid completions show dimmed as "may not fit", and `determinant(tr` suggests `true`.

## Witness

CE 0.198.0, `epsilCompletions(ce, source, source.length)`:

- `let x = 2` then `let y = sin(` (expected `complex | quantity`):
  match 98, maybe 372, never 125, no `fit` 5. The document's own `x`
  (`number`) is `maybe`, and so is `abs` (`(complex | infinity | quantity) -> number`).
- `let m = [[1, 2], [3, 4]]` then `let d = determinant(` (expected `matrix`):
  match 10, maybe 314, never 271, no `fit` 4. `abs` (`-> number`) is `maybe`;
  `true` and `false` have no `fit`.

Tycho (CE-1661, adopted) hides `never`, dims `maybe`, and offers only
`match` as the inline suggestion. With these values the dimming marks
nearly every entry, including the valid `x` at `sin(`, and at
`determinant(tr` the first entry that is not dimmed is `true` (a value
with no `fit`), so the inline suggestion is `true` where a matrix is
expected.

## Expected

1. A `number` where a numeric type is expected (`complex | quantity`,
   `real`, …) is `match`. If the reason for `maybe` is that `number`
   includes infinities or NaN that `complex` does not, the editor's user
   cannot act on that difference; `match` is what a person expects.
2. A result type that cannot be the expected type is `never`: `-> number`
   where `matrix` is expected.
3. A keyword or a literal value (`true`, `false`, `0`) has a `fit` when
   `expectedType` is set: `true` and `false` are `never` where a matrix is
   expected. Keywords that start an expression of any type (`if`, `match`)
   can stay without one, or be `maybe`.

Tycho keeps dimming `maybe` (user decision 2026-11-21: it is a useful
signal), so the fix is the precision of the values, not a new field.

Not covered by ROADMAP CE-1664: its items are for positions with no
expected type, the order of names that fit (CE-1664.9), a match on the
description, inferred types and LaTeX commands. This issue is the `fit`
values where `expectedType` is set (CE-1661's field).

## Instrument

`node scripts/repros/2026-11-21-ce1694-fit-precision.mjs` (Tycho) prints
the counts at `sin(` and `determinant(` and checks: at `sin(`, `x` and
`abs` are `match`; at `determinant(`, `abs` is `never` and `true` and
`false` are `never` or absent. Prints `CE-1694: READY` when all hold. On
0.198.0: `CE-1694: NOT READY` (all five checks fail).

Tycho half on adoption: none expected; the instrument reading and a look at
the menu at `sin(` and `determinant(` close it.

## Decision

User decision 2026-11-21: (b). The non-finite arms of a numeric type
(NaN, infinities) do not count against `match`, so `let x = 2` is `match`
at `sin(`. `abs` stays `maybe` at `determinant(` (it maps over a matrix,
so `determinant(abs(A))` is valid). No Tycho stopgap for values with no
`fit`: CE adds `fit` to value items. The instrument checks `abs` at
`determinant(` as `maybe`.

## CE answer

CE (2026-11-21): P2 confirmed. The three readings, checked on CE main:

1. `true`, `false` and the other literal values (and keywords) have no
   `fit`: a gap, excluded on purpose in CE-1661. Fix: give every value item
   a `fit` when `expectedType` is set (`true` is `never` at `determinant(`).
   No decision needed; pool, next completion change.
2. `abs` at `determinant(` is `maybe` on purpose: `abs` maps over a list,
   and `determinant(abs(A))` is valid (`-2`, no diagnostic). A `never` there
   would hide a valid call. Not a defect. `isPrime` is `never` (a matrix of
   booleans).
3. `x` after `let x = 2` is `maybe` at `sin(` for a reason: a `let` has the
   type `number` (it may later hold `0/0`), `number` includes NaN and the
   infinities, and `sin` declares `complex | quantity`: `checkEpsil` rejects
   `sin(x)` when `x` is NaN. With `let x: real = 2` or `const x = 2`, `x` is
   `match`. Most of the 372 `maybe` come from result types `number` (which
   include NaN) at an argument declared `complex` or `real`. The contract
   says `match` means "always of that type", so this is exact today; making
   them `match` changes that contract, so it waits for the board:
   (a) keep it exact; (b) recommended: the non-finite arms (`nan`,
   infinities) of a numeric candidate do not count against `match` when the
   expected type is numeric, since the checker does not flag them (they
   overlap) and they propagate as values; `match` then reads "of that type,
   apart from non-finite values". With (b), `x` and `sqrt` are `match` at
   `sin(`.

Workaround until then: when `expectedType` is set, do not use an item with
no `fit` as the inline suggestion (that removes `true` at `determinant(tr`).
