The type of the negation of a value of a recursive alias type with a ranged number arm does not include the value when the number is nested two lists deep.

## Witness

At commit `f61580d4d0434c9187b14650d0771e61b3ee3525`, and after the fix of
CE-1873:

```js
ce.declareType('J', 'list<J> | integer<0..5>', { alias: true });
ce.declare('j', 'J');
ce.box(['Negate', 'j']).type;
// before CE-1873: J | integer<-5..0> | list<J | integer<-5..0>>
// after CE-1873:  integer<-5..0> | list<J> | list<integer<-5..0> | list<J>>
ce.box(['Negate', ['List', ['List', 3]]]).evaluate();   // [[-3]]
```

`[[-3]]` is in neither type: `[-3]` is not a `J`, since `-3` is not in
`integer<0..5>`. The value is right; only the type is wrong. No effect on a
result was found. The impact is `minor`: the type is wrong in a case that
no program was shown to reach.

## Cause and options

`negateNumericType()` (`src/common/type/utils.ts`) reflects a transparent
alias through its definition and stops at an alias it has already entered
(`seen`): the inner occurrence keeps its name, and so its range.

Option: at the repeat, return the definition with its numeric ranges
removed (`stripNumericRanges()`), applied through the inner references, so
that the result claims no range for the nested values. A recursive alias has
no finite reflected form otherwise.
