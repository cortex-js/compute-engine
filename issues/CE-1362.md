A second engine with another precision changes the number of digits that the first engine computes.

## Witness

From GitHub #556 (the probability is `medium`, not the `high` of a `corpus`
witness: it needs two engines with different precisions in one program):

```ts
const f = (e: ComputeEngine) => e.expr(['Sqrt', 2]).N().toString();
const a = new ComputeEngine(); a.precision = 30;
f(a);                                   // 1.41421356237309504880168872421
const b = new ComputeEngine(); b.precision = 'machine';
a.precision = 30;                       // already 30: nothing is restored
f(a);                                   // 1.4142135623731   (a.precision still reads 30)
```

Workaround: set the engine's precision to another value and back before using
it, or use one engine per program (the guide says so:
cortexjs.io `12-guide-numerical-evaluations.md`, "Use one engine per program").

## Cause and options

`BigDecimal.precision` (`src/big-decimal/big-decimal.ts`) is one static
field. The engine constructor and `setPrecision`
(`src/compute-engine/engine-numeric-configuration.ts`) write it, so the last
engine that wrote it wins. Every operation of `BigDecimal` that rounds or
bounds a result reads it:

- `div`, `sqrt`, `inv`, `pow` with a negative exponent, and the
  transcendentals (`transcendentals.ts` raises it for guard digits and
  restores it in a `finally`);
- `mulBounded`, `roundToProductBound` (`maxProductDigits()` is
  `2·precision + 20`), `addBounded`, `subBounded` and the gap limits of `add`
  and `sub` (`maxExactGap()` is `max(10,000, 4·precision + 100)`).

`mul` is exact and does not read it.

Options considered:

- (a) Set the static at every entry point of the engine (PR #607). Not taken:
  the arithmetic methods of `Expression` (`div`, `pow`, `sqrt`, `inv`) stayed
  at the ambient precision (a regression: a 100-digit engine made after a
  default one got about 21 digits); a call from engine B into engine A ran at
  B's precision; and it added a wrapper to `ce.number`, `ce.function` and
  `ce.expr`, which run on every box, with no benchmark.
- (b) Each `BigDecimal` carries its precision. Not taken: it is significance
  arithmetic, a different model of numbers (what precision has `a.div(b)`, an
  exact integer, a cached constant?), and the guard digits of the
  transcendentals still need a context.
- (c) An explicit precision argument on each operation that rounds or bounds,
  defaulting to `BigDecimal.precision`, as in MPFR or Python's `decimal`
  with a context. The engine passes `ce.precision`; guard digits become
  `prec + 10` passed as an argument, which removes the save, raise and
  restore blocks. No per-value memory, no wrapper on hot paths, re-entry is
  right by construction.

## Decision

User decision 2026-11-16: option (c). Stages: (1) give the rounding and
bounded operations of `BigDecimal` an optional precision argument; (2) convert
the engine area by area, first `.N()` and the arithmetic methods of
`Expression` (the witness), with the static as the fallback throughout; (3)
when `src/compute-engine` no longer reads `BigDecimal.precision`, the engine
stops writing it. `src/` reads it 353 times (a grep count, 2026-11-16). Each
stage is measured against main on the benchmarks (`benchmarks/README.md`). The
guide's "Use one engine per program" warning is removed with stage 3.
