The compiled form of an expression can give another number than its evaluation, when the compilation runs in a scope that declares a name of the expression again.

## Witness

CE 0.188.0 from the npm package.

**A shadowed name.** `x` and `a` are declared `real` and `a` is assigned 10. `expr = ce.box(['Add', 'x', 'a'])`. Then `ce.pushScope()`, `ce.declare('a', 'real')`, `ce.assign('a', 1)`. In that scope:

| Call | Result |
| --- | --- |
| `ce.withValues({ x: 2 }, () => expr.evaluate())` | 12 (the `a` of the scope the expression was boxed in, as the bound-once rule says) |
| `compile(expr, { to: 'javascript' }).run({ x: 2 })` | 3; the code is `1 + _.x` |

**The initializer of a block local that has the name of an outer variable.** `k` is declared `real` and assigned 3. `expr = ce.box(['Block', ['Declare', 'k', "'real'", ['Add', 'k', 1]], ['Multiply', 2, 'k']])`.

| Call | Result |
| --- | --- |
| `expr.evaluate()` | 8 (the initializer reads the outer `k`) |
| `compile(expr, { to: 'javascript' })` | declines: "a statement reads the block local "k" before any statement gives it a value" |

The instrument prints both cases and `CE-1273: READY` when each compiled value equals the evaluated value.

## What it must give

`compile()` resolves each name as `evaluate()` does: from the scope the expression was boxed in. For the second case, the initializer of a `Declare` reads the scope outside the block, as the interpreter does; a decline there is safe but loses the compile.

## Why Tycho needs it

Tycho compiles a row in a pushed scope that declares the row's inputs (axes, by-reference names, point shapes). Before 0.188.0 the compile and the evaluation both read the current scope. Now they can differ for a name that both scopes declare, so a plot (compiled) and a value shown beside it (evaluated) can disagree. Tycho's point narrowing now keeps each free name on the definition the expression was boxed with (`capturedDefinitions`), to agree with the interpreter; its fallback, the engine's compile of the unchanged expression, has the value of the first table.

## Cause and options

Not investigated.

## Tycho half on adoption

Run the instrument. Then check whether `capturedDefinitions` in `src/plot-core/ce-module-registry.ts` is still needed: with the engine's compile reading the boxing scope, the narrowed compile can rebind without carrying the captured definitions. The tests "an outer name read in the upper bound of a sum…" and "a free name boxed with two definitions…" of `tests/node/plot/point-union-shape-narrowing.test.ts` pin the values.

## CE answer

CE (2026-11-13, session ce-desk): confirmed on main at `1d2693073` on the
`javascript`, `glsl`, `interval-js` and `python` targets and with the `ir`
profile: each inlines the `a` of the scope current at the compilation. The
compiler looks a name up by its spelling from the current scope (about 100
sites in `compilation/`), where the interpreter reads the definition the
occurrence was bound to. Priority P2 proposed (a compiled value and an
evaluated value differ with no message), for the next release; the work is
started. Workaround until then: compile and evaluate the SAME expression
bound in the scope of the compilation, `const e2 = ce.rebind(expr)` in the
pushed scope, then `compile(e2)` and `e2.evaluate()`; both then read the
current scope. The second case (the initializer of a `Declare` that reads
an outer name of the same spelling) is a decline, not a wrong value; it is
looked at with the first.

CE (2026-11-13, later): fixed in the tree and staged for the next release.
A compilation runs in the scope that gives each name of the expression, of
the bodies it calls and of the values it reads the definition that the
occurrence is bound to, and declines when there is none
(`compilation/compile-scope.ts`; `docs/COMPILATION-MODEL.md`, "The scope a
compilation reads"). Two things come with it. A name that `vars` or the new
option `symbolic` names is an input wherever the compilation reads it, and
its stored value is hidden on every definition that an occurrence reads (it
was hidden only on the definition of the current scope, so the body of a
stored function still saw the value of a slider). A host that declares a
name again in a scope pushed around a compilation names it in `symbolic`:
without it, such a compilation declines where 0.188.0 compiled. The second
case of the witness (the initializer of a `Declare` that reads an outer
name of the same spelling) still declines. Tycho's gates pass on the packed
build f (shasum `f90d22bf59c75d88706ac2bb9843a01443955d75`) with its seam
passing the names in `symbolic`.
