The constructor of a named tuple type that has a field of tuple type accepts a list at another field, with no diagnostic, so a value that breaks its declared type is built.

## Witness

Main at `0246c8a7cf332ece59856c61cb79273f0a1be9b4` (and CE 0.200.1), Epsil:

```
type F = tuple<m: tuple<real, real>, q: string>
let a = F((1, 0), [1, 2])     // ["F", ["Tuple", 1, 0], ["List", 1, 2]], no diagnostic
```

The same with `q: real`, and with the tuple field after `q`
(`type F = tuple<q: string, m: tuple<real, real>>`, `F([1, 2], (1, 0))`).
Controls on the same commit, each `incompatible-type` as expected:

```
F((1, 0), 5)                                         // q: string, a scalar
type G = tuple<m: real, q: string>; G(1, [1, 2])     // no field of tuple type
type H = tuple<k: string, q: string | color | nothing>; H("x", [1, 2])
```

Tycho's `Figure` has `matrix: tuple<real, real, real, real, real, real>`, so
`Figure(…, Nothing, [1, 2], …)` was accepted at `fillPaint` and `strokePaint`
(`string | color | nothing`). Tycho's prelude version 24 checks the argument
before the constructor (`c is string || c is color`), so Tycho does not depend
on a fix.

Impact `minor`: the result is a value of the wrong type with no error, in a
program that is itself wrong, and the host has a workaround (check the
argument). Probability `medium`: it needs a type with a tuple field and a list
given at another field.

## Cause and options

Not investigated. A guess to check first: a list argument at a constructor
whose signature has a tuple parameter is read as a broadcast (the constructor
mapped over the list), which skips the check of that argument against its
field type. Expected: the same `incompatible-type` as without the tuple field.
Compiled code is not affected: the compiler declines an operand whose static
type does not prove its field's type (CE-1652, `lower-records.ts`).
