After the type of a variable changes, a function that reads it still reports a result type computed with the old type.

## Witness

```ts
ce.declare('k', 'integer');
ce.declare('f', { value: ce.box(['Function',
  ['Block', ['Declare', 'c', 'unknown', ['Add', 't', 'k']], ['Tuple', 'c', 'k']],
  't']) });
ce.box(['f', 2]).type;        // tuple<integer, integer>
ce.symbol('k').type = 'string';
ce.box(['f', 2]).type;        // tuple<number, integer>
```

A new engine that declares `k` as `string` gives `tuple<error, string>`.
Both components are wrong after the retype: the second one still reads the
old type of `k`. Reproduced on the main tree at `5c97853cc` (2026-11-06).

## Cause

Traced on 2026-11-07 at `b84d7ea7df0492873852eb509df052718b3e5123`. Two
records keep the types of the time of definition:

1. The binding `f` has no declared type, so it records the signature of the
   literal when it is assigned, and `_reviseInferredType()`
   (`boxed-value-definition.ts`) never revises it for a `Function` literal
   (only its effects). A call is typed from the body under the result of that
   signature (`callResultType()`, `call-result-type.ts`). This gives the
   second component `integer`.
2. The type of the block local `c` is the type of its initial value when the
   block was canonicalized (`recordInitializerEvidence()`,
   `library/core.ts`). This gives the first component `number`. A block that
   is not in a function shows it too:
   `Block(Declare(c, "unknown", 1 + k), (c, k))` keeps `tuple<integer, …>`.

The values are not wrong. After the retype, `f(2)` and `h(2)` (with
`h := t ↦ (t, k)`) evaluate to an `incompatible-type` error, and so does the
block. This is the rule of the CE-473 decision (user decision 2026-10-25,
option (c), `test/compute-engine/ce-473-captured-free-symbol.test.ts`): a
call whose stored signature no longer holds the type of the literal is an
`incompatible-type` error. So the stored signature is kept on purpose, and the
static type is the one of the stored signature, which every error value
satisfies.

## Options

Example: `ce.declare('k', 'integer')`, `h := t ↦ (t, k)`, then
`ce.symbol('k').type = 'string'`.

- **(a) Close: no change (recommended).** `h(2).type` stays
  `tuple<unknown, integer>`, and `h(2)` evaluates to the `incompatible-type`
  error. This is the decided rule; the static type is not more precise than
  it must be.
- **(b) The signature follows the retype.** `h(2).type` is
  `tuple<integer, string>` and `h(2)` evaluates to `(2, k)` with no error.
  This reverses CE-473 (c) for this case: the Epsil program
  `let g = (x) => [-x, y]; y = "abc"; g(3)` gives `[-3, "abc"]` in place of
  the error. An implementation is in the worktree
  `/tmp/wt-cebatch-1015` (`_reviseLiteralSignature()`, with a test file),
  reviewed by two reviewers in two rounds. It fails
  `ce-473-captured-free-symbol.test.ts`. It also makes the type of a
  recursive literal after a retype too narrow:
  `R := (n: integer) ↦ If(n = 0, k, (R(n − 1), 1))` types `R(1)` without
  `tuple<string, …>`. Size M.
- **(c) Keep the stored signature, and type the call `error`.** When the
  stored signature no longer holds the type of the literal, the static type
  of the call is `error`, the type of its value. `h(2).type` is `error`.
  This adds a comparison of the two signatures to each call type, and the
  block local `c` still needs its own change. Size M.

If nothing is decided, the behavior of (a) stays.

## Decision

User decision 2026-11-07: (a)
