The cosine or the sine of a very large number is a wrong number.

## Witness

At `c976f546435060f6e5ef8399a18058ce6f54762f`, with `ce.box(['Cos', v]).N().re`
(`evaluate()` gives the same):

| Program | The engine gives | `Math.cos` / `Math.sin` |
| --- | --- | --- |
| `Cos(1e300)` | `-0.16821444437424507` | `-0.5753861119575491` |
| `Sin(-1e300)` | `0.985750425160377` | `0.8178819121159085` |
| `Cos(1e30)` | `-0.9959311944053957` | `-0.9999564608959665` |
| `Cos(1e22)`, `Cos(1e17)`, `Sin(1e16)` | equal to `Math` | |

A computation with 400 digits (mpmath, run by the agent that found the case)
gives `-0.5753861119…` for `cos(1e300)`, the value of `Math.cos`. Over the
powers of ten from `1e20` in steps of `1e10`, `1e30` is the first where the
engine differs from `Math.cos`. Compiled JavaScript writes `Math.cos` and gives
the right value, so the interpreter and compiled code differ here.

The witness is `crafted`: no document was found that takes the cosine of a
number above `1e22`.

## Cause and options

Not investigated. The machine-precision evaluation of `Cos` and `Sin` does not
give the value of `Math.cos` and `Math.sin` for a large argument, so it reduces
the argument in another way (probably with a value of π of limited precision).
Option: for a machine number, call `Math.cos` and `Math.sin` directly, which
reduce the argument exactly. The tests of
`test/compute-engine/compile-javascript-structured-power.test.ts` keep `±1e300`
out of their trigonometric bases because of this issue.
