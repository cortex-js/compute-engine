A Tycho user who leaves a string or a bracket open in an Epsil code cell gets an error but no one-step fix.

## Witness

The instrument parses `let s = "abc`, `f(1, 2`, `let L = [1, 2` and
`if x > 0 { 1`. Against 0.193.0 each gives its error
(`string-literal-closing-delimiter-expected` [8,12],
`closing-bracket-expected` at the OPENING bracket) with `fixits []`.
Tycho's editor offers each fix-it of a diagnostic as an action (a menu entry
reached by keyboard, or a button), so a fix-it is all Tycho needs.

## Cause and options

Today the parser's only fix-its are for `asymmetric-operator-whitespace`,
`mapsto-arrow-legacy` and `match-case-separator` (ce-debugger, 2026-11-19).
Request:

- `string-literal-closing-delimiter-expected`: insert the delimiter at the
  end of the line;
- `closing-bracket-expected`: insert the closing bracket at the end of the
  input.

A fix-it is documented as a guess, so an imperfect insertion point is
acceptable. Not part of this request: a placeholder for `expression-expected`
and type names for `type-annotation-error`, which are completions (CE-1521).
Size S.

## CE answer

CE (2026-11-19): P3 confirmed, pool. Workaround: Tycho can build both fixes
itself. The first argument of the message is the missing delimiter or
bracket (`["closing-bracket-expected", ")"]`): insert it at the end of the
line for a string, at the end of the input for a bracket.
