A prelude that changes a `for` loop into a `parallel for` falls back to the interpreter when the loop body ends with an inner loop, so the picture takes seconds instead of milliseconds.

## Witness

On 0.184.0, through Tycho's prelude runner (parse, compile to JavaScript,
the interpreter when the compile declines), the instrument:

```epsil
function f(H: list<integer>, n: integer) -> list<integer> {
  let L = H
  parallel for k in 1..n {
    if k > 0 {
      for m in 1..3 { L[m] += 1 }
    }
  }
  L
}
const R = f([0, 0, 0, 0], 5)
```

```
parallel for, inner loop last:   route=interpreted
  Could not compile "Loop({AddTo(At(L, m), 1)}, Element(m, Range(1, 3)))":
  the value of this `Loop` is used. A loop that ends with no `Break` …
for, inner loop last (control):  route=compiled   value=[5, 5, 5, 0]
parallel for, then `0` after the inner loop (workaround): route=compiled
```

The same body under a plain `for` (with `L = replaceAt(L, m, L[m] + 1)`)
compiles. The values are the same on both routes.

## Cause and options

The JavaScript target lowers `ParallelLoop` to `Loop` and `AddTo` to
`Assign` before the other rewrites (`parallel-lowering.ts`); the rebuilt
inner loop then counts as a loop whose value is used, where the original
`for` body treats the last inner loop as a statement. Option: the lowering
keeps the statement position of the body's last expression (or the value
check treats the body of a lowered `ParallelLoop` as the body of a `Loop`).
Size S. The documentation of CE-1093 says a program changes a `for` into a
`parallel for` by adding the keyword; this case breaks that promise.

Workaround: end the body with a statement after the inner loop (`0`).
Tycho's `buddhabrot` step will carry it until the fix.

READY (the instrument's reading): the form above compiles.

## CE answer

Fixed, not yet released (the next release after 0.184.0). Priority P4.
The cause was not the lowering: the check of a used loop value reads the
user-function body as the engine stores it, before the lowering, and it
read the body of a `ParallelLoop` as a value. So the inner loop, the last
statement of the `if` branch, counted as a used value. Commit
`97c1699262ba6fded5443410a4c581c764373a23` (CE-1075) made the body of a
`ParallelLoop` a statement list in that check (`operandUse()` in
`src/compute-engine/compilation/compile-admission.ts`), as the body of a
`Loop`. On the 0.184.0 source the witness declines with the message above;
on the current source it compiles and gives `[5, 5, 5, 0]`, as the
interpreter. The test "a parallel loop whose body ends with an inner loop
compiles" in `test/epsil/parallel-for.test.ts` pins it. Until the release,
keep the workaround (`0` after the inner loop).
