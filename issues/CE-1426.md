A recursive function that calls itself three times on an exact value does not stop when the host's time limit expires.

## Witness

On the working tree at `9a8723f914eee82a1e3e2c7b57ec8f533af07cc1` (uncommitted
edits of other sessions, none in `isConstant` or `arithmetic.ts`), default
precision:

```js
const c = () => ['f', ['Subtract', 'k', 1]];
ce.declare('f', '(integer) -> real');
ce.assign('f', ce.box(['Function',
  ['If', ['Equal', 'k', 0], 1,
    ['Add', c(), ['Multiply', ['Sin', c()], ['Cos', c()]]]], 'k']));
ce.withTimeLimit({ ms: 500 }, () => ce.box(['f', k]).evaluate());
ce.withTimeLimit({ ms: 500 }, () => ce.box(['f', k]).N());
```

| Call | k = 15 | k = 16 | k = 18 | k = 20, 40 |
| --- | --- | --- | --- | --- |
| `evaluate()` under a 500 ms limit | returns after 1.1 s | returns after 3.0 s | | no return in 40 s |
| `N()` under a 500 ms limit | | throws after 3.1 s | throws after 27 s | |

Without a limit, `N()` takes 1.3 s at k = 10 and 10.3 s at k = 12 (about 2.8
times per level). The exact value of `f(k)` is `1 + sin(1)cos(1) + sin(...)`,
a tree with about 3^k paths from its root (not measured: how many distinct
node objects it holds).

## Cause and options

A CPU profile of the run inside `withTimeLimit` puts 48.5% of all samples
(nearly all of the time inside the span) in the getter `isConstant`
(`boxed-function.ts`): it recurses into every operand with no cache and no
visited set, so on a tree that shares operands it visits every path. Its
callers are the D2 gate of `addEvaluatedOperands()` and
`mulEvaluatedOperands()` (`library/arithmetic.ts`, `result.isConstant &&
evaluated.some(...)`), which run at each level of the recursion on the
result built so far. The walk has no deadline checkpoint, so the time limit
is seen only at the next `checkDeadlineEvery` of `evaluate()`, after the walk.

Options: (a) cache `isConstant` on the node like `_effectsOf()` (keyed on the
callable version and the lexical scope); (b) a visited set per call of the
getter; (c) a `checkDeadlineEvery` in the walk, which makes the time limit
work but leaves the cost. (a) or (b) removes the exponent; (c) alone only
bounds it. Same class as CE-1240 (exponential walks on shared trees, a
performance issue), which does not list this walk; this issue is kept apart
because the time limit does not stop it.

The corpus program that led here, `neyret/dnz1jlbvnn` program 29
(`P(k) = P(k-1) - e_0 d(P(k-1)) G_1(P(k-1))`, k in 0..40), evaluates on
floats and does not reach this walk: its time is 3^k calls of `P`, and
`withTimeLimit` stops it at the limit.
