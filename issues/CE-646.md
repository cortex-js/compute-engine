A compiled search in a list of lists (`Contains`, `Unique`) runs in the slower interpreter.

## Witness

Checked at `0d3a3aba4b2401c5bb7a03ed9bbe1b885dd087be`, with
`xss: list<list<integer>>`, on JavaScript:

```
Map(k ↦ Contains(xss, k), xss)   declines: Contains of a value that the
                                 interpreter may hold exactly
Contains(xss, [2, 3])            declines: a list where a scalar is required
Unique(xss)                      declines: xss of type list<list<integer>>
                                 other than in an element read xss[i][j] or as
                                 an argument of a parameter of that type
```

Each program evaluates in the interpreter. The first one is the program of
GitHub #499. Not a regression.

## Cause and options

The search lowering (`search`, `compilation/ir/lower-lists.ts`) reads a list
of real numbers and a real needle, and an input of a nested list type is read
by element only. The fix: lower `Contains`, `Element`, `IndexOf` and `Unique`
for a list whose elements are lists of a settled length and element type,
with an element-by-element comparison.

An element that the interpreter holds as a lazy view stays a decline (crafted):
the interpreter does not find the list `[2, 3]` in
`Map(e ↦ e, [Map(j ↦ j + 1, ys), [9]])` at `ys = [1, 2]`, and compiled code,
which holds a view as an array, would find it. The lowering admits a list of
lists that is an input, a `List` literal of the program, or a parameter of
that type.

## Decision

User decision 2026-11-25: no design document. The compiler that held
`mayMakeDistinctElement` was deleted in `e16216680` (0.194.0); the issue is the
decline of a search in a list of lists, and the lazy-view element stays a
decline.
