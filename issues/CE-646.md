A compiled search in a list of lists (`Contains`, `Unique`) runs in the slower interpreter whenever the program also holds a `Map` or `Filter` result.

## Witness

`Map(k ↦ Contains(xss, k), xss)` declines on JavaScript and evaluates in the
interpreter. Without the decline,
`Contains(Map(e ↦ e, [Map(j ↦ j + 1, ys), [9]]), [2, 3])` gave `False`, because
compiled code compares a lazy view as a plain list, and the interpreter does
not. Not a regression.

## Cause and options

`Contains`, `Element`, `Unique`, `RangeOf`, `ContainsSequence`, `StartsWith`
and `EndsWith` compare elements by value (`_SYS.eqs`). By user decision
2026-10-30 the lowering declines when the program, a value it reads or a user
function it calls holds a lazy collection or a non-literal `Range`
(`mayMakeDistinctElement`, `compilation/javascript-target.ts`). The design must
say where a lazy view can become a list element at run time, or make the
interpreter list callback results (this changes `.isSame()` results).
