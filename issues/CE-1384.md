An integral whose bounds are written with one number too many silently drops its bounds and shows as an indefinite integral.

## Witness

Epsil CLI, main a28dd290f: `integrate(x, (x, 0, 1, 2))` prints `int(x)`;
`integrate(x, (x, 0, 1))` prints `1/2`. The four-member bound must give an
error (or stay as written with its bounds), not an indefinite integral.

The same drop happens to an `in` clause: `integrate(x, x in 0..1)` prints
`integrate(x)` (main a06bedaab). `0..1` is the discrete range {0, 1}, so the
clause has no meaning as bounds, and it must give an error too.

## Cause and options

The canonical form of `Integrate` reads a limits tuple of an unexpected length
as a bare variable, and `canonicalLimitsSequence()` (`library/utils.ts`) leaves
out every operand of a shape it does not read (an `Element` clause too). Fix:
an `incompatible-type` or arity error for such an operand, as the branch for a
`Set` operand gives.
