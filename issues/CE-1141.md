In VS Code, the highlight and the rename of a `let` variable also include the index of a `sum`, or the variable of a `limit`, that has the same name.

## Witness

```
let k = 2
sum(k^2, k, 1, 3)
```

In VS Code, the cursor on the `let k` highlights the three `k` of the `sum`
too, and a rename of the `let k` changes them. The `sum` binds its own `k`:
the program gives `14`, and the outer `k` is not read. The same occurs for
`let h = 5` followed by `limit(sin(h)/h, 0)`.

The engine function that the editor uses gives the correct groups when it gets
the binder sites: `test/epsil/binder-sites-of.test.ts` ("the implicit variable
of a limit is not the outer name in a rename") shows `[[4], [20, 23]]` for the
`limit` program, and the language server gives one group, `[4, 20, 23]`.

## Cause and options

`bindingsOf()` in `vscode-epsil/src/server.ts` calls
`documentBindings(ast, text)` with no `binderSites` option. Without it, a
variable that a library call binds reads as a use of the enclosing scope (the
doc comment of the option in `src/epsil/occurrences.ts`). So the fixes of
CE-1038 and CE-1087, which change the result of `binderSitesOf()`, do not
reach the editor.

Option (a): give the option as `resolveLibraryNames()` does,
`binderSites: (node, isBound, declarationOf) => binderSitesOf(ce, node, text,
protocolFunctionMembers(ast), isBound, declarationOf)`, with the engine of
the parse. Check the cost on a long document, because `binderSitesOf()` boxes
operands. Size S.
