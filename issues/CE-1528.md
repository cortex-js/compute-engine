A record whose field name has a hyphen or another character that is not allowed in a name cannot be given a literal value: the declaration is refused.

## Witness

```epsil
let a: record{`first-name`: integer} = {"first-name" -> 0}
a
```

gives `incompatible-type`: the value `{"first-name" -> 0}` has type
`dictionary<integer>`, not compatible with `` record{`first-name`: integer} ``.
`type({"first-name" -> 0})` is `dictionary<integer>`, while
`type({"x" -> 0})` is `record{x: integer}`. `docs/TYPE-SYSTEM.md` (line 231)
says the type of a dictionary literal is the record of exactly its keys.
Keys of this kind are plausible in data read from JSON (`first-name`,
`zip code`). Workaround: keys that are plain names.

## Cause and options

`BoxedDictionary._computeType()` (`src/compute-engine/boxed-expression/boxed-dictionary.ts`,
about line 393) synthesizes a record type only when every key passes
`isRecordKey` (a plain identifier, not a type keyword), and otherwise falls
back to `dictionary<T>`. Its comment says that `typeToString` does not
backtick-escape record keys, so the record type would not round-trip. That
is no longer the case: the type parser reads `` record{`first-name`: integer} ``
and the diagnostic above prints it back with the backticks. Fix: build the
record type for every key, and check that the type of such a literal
serializes and parses back to the same type (a round-trip test with a
hyphen, a space, a keyword `true` and `__proto__`). Size S.

The completion function of CE-1521 offers no likely value for a record type
with such a key until this is fixed (`src/epsil/completion.ts`, record
branch of `valuesOfType`).
