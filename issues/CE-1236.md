Compiled code gives `NaN` for `EllipticK(m)` with `m > 1`, where the value is complex, and the `numeric-kernel` profile and the existing compiler give different shapes for it in a matrix product.

## Witness

At `99cee49c8926048d73e590a0274567b9290e8bcc`, JavaScript target, `MA: matrix`:

```ts
ce.box(['EllipticK', 10]).N(); // 0.5098987255389721 - 0.8152643095897213i
const e = ce.box(['Multiply', 'MA', ['List', ['EllipticK', 10], 1]]);
compile(e).run({ MA: [[1, 2], [3, 4]] });
// [{ re: NaN, im: NaN }, { re: NaN, im: NaN }] (code `_SYS.cmul(_.MA, [_SYS.ellipticK(10), 1])`)
compile(e, { profile: 'numeric-kernel' }).run({ MA: [[1, 2], [3, 4]] });
// [NaN, NaN] (code `_SYS.mul(_.MA, [_SYS.ellipticK(10), 1])`)
```

The interpreter gives `[2.5099 - 0.8153i, 5.5297 - 2.4458i]`. The existing
compiler types the product complex and computes it with the real kernel
`_SYS.ellipticK`, which gives `NaN` for `m > 1`; the profile types it real.
The difference of shape is in the scripts/js-profile-fuzz.ts report
(differences between the profile and the existing compiler, inputs in
type).

## Cause and options

The real kernel has no value for `m > 1`. Options: a complex kernel for
`EllipticK` of a literal or an operand that is not provably at most 1 (the
existing compiler already types the node complex there), or a decline of
`EllipticK` where its operand can exceed 1 in the `complex` mode; and the
profile reads the node type that the existing compiler reads (complex), so
both routes give the same shape.
