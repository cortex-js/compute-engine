In a notebook code cell, `for k in 1..n { … }` runs twice when `n` is 0, with `k` equal to 1 and then 0.

## Witness

On 0.195.1 (the instrument, fresh engine per program, `let n = 0`):

| Program                         | Today   | Empty range |
| ------------------------------- | ------- | ----------- |
| `for k in 1..0 { c = c + 1 }`   | `c = 2` | `c = 0`     |
| `length(1..n)`                  | `2`     | `0`         |
| `sum(1..n)`                     | `1`     | `0`         |
| `sum(k, (k, 1, n))`             | `0`     | `0`         |

Control: `length(1..3)` is 3; `length(Range(1, 0, 1))` is 0.

How it was found: a Tycho sample notebook implements the strong
probable-prime test. Its inner loop squares `x` for `r` from 1 to `s - 1`,
written `for r in 1..(s - 1)`. For every `n ≡ 3 (mod 4)`, `s` is 1, and the
loop ran twice instead of not at all. The results happened to stay correct for
the tested values, which is worse: the defect is invisible until an input
reaches it. The notebook now uses a `while` loop.

## The case for a change

The rule is deliberate (`docs/COLLECTIONS-MODEL.md`: "A `Range` with no step
counts toward its end in either direction, so it is never empty"). For a
`for` loop and for a list it costs more than it gives:

1. **`1..n` is the loop over n things.** `for i in 1..length(xs)` is the
   natural loop over a list in a 1-based language. On an empty list it reads
   `xs[1]` and `xs[0]`, and `xs[0]` is `NaN` with no error. Every loop over
   "the first n", "the remaining s - 1", "the rows after the header" has the
   same case at its smallest input.
2. **It disagrees with `sum` and with mathematics.** `sum(k, (k, 1, 0))` is
   the empty sum 0, as $\sum_{k=1}^{0}$ is in every textbook, but `sum(1..0)`
   is 1. In a notebook the author writes the LaTeX sum and the Epsil loop next
   to each other and expects them to agree.
3. **CE's own work meets the trap.** The same document must tell every rewrite
   to "write the step, or handle the case `s > K` itself". The 2026-11-08
   JS-profile audit records "Epsil 1..0 is descending [1,0]; scheduler skips
   count=0 jobs", and the 2026-11-09 annotation contract records "Host must
   skip zero; raw Range(1,0) is descending inclusive". Each is a workaround of
   the same rule, written by an author who knows the engine.
4. **Other languages give the empty range.** Python `range(1, 1)`, Julia
   `1:0`, Mathematica `Range[1, 0]` and MATLAB `1:0` are all empty. Descending
   needs an explicit step in each of them (`10:-1:1`, `Range[10, 1, -1]`).
   An author from any of them writes `1..n` expecting an empty range at 0.

Descending ranges are still useful; they cost one word: `Range(7, 4, -1)` or
`reverse(4..7)`.

## Options

- (a) **Recommended.** `a..b` and `Range(a, b)` with `a > b` are empty.
  A descending range takes a step: `Range(7, 4, -1)`. A literal descending
  range (`7..4`) gets a warning diagnostic with the fix-it
  `Range(7, 4, -1)`, so programs that relied on the old rule are found.
  `Range(0)` becomes `[]`. The compiled targets follow the interpreter (the
  `Range(0)` JS fix d96a6ac11 is reverted in the same change). Size M,
  including the migration note.
- (b) Keep `Range(a, b)` descending in MathJSON, but make the Epsil operator
  `..` ascending only. This splits one concept in two spellings; not
  recommended.
- (c) Keep the rule, and add a warning when a `for` loop iterates over `a..b`
  whose bounds are not literals and evaluate to `a > b`, plus a line in the
  Epsil card ("Watch Out For"). This catches the loop, not `length` or `sum`.

Tycho needs no change for (a): its sample notebooks do not use a descending
range without a step.

## CE answer

CE (2026-11-20): priority P3 confirmed; disposition needs-decision. CE
proposes option (b), not (a). The workaround stands: write the step,
`for r in Range(1, s - 1, 1)`.

Measured on the current source (2c0662ebd): the four witnesses reproduce.
With the step written, every one is empty: the loop over `Range(1, 0, 1)` runs
0 times, `length(Range(1, n, 1))` and `sum(Range(1, n, 1))` are 0,
`[k^2 for k in Range(1, n, 1)]` is `[]`, `xs[Range(2, 3, 1)]` is the same
slice as `xs[2..3]`, the type is the same (`range` for literal bounds), and
the compiled JavaScript loop gives 0 at `n = 0` (the loop over `Range(1, n)`
gives 1).

Three facts that the options above do not have:

1. **The rule is the Desmos rule.** Measured in the live calculator
   (2026-11-20): `[1...0]` is `[1, 0]`, `[5...1]` is `[5, 4, 3, 2, 1]`; with
   `n = 0`, `[1...n]` is `[1, 0]`, its `length` is 2, its `total` is 1,
   `[k^2 for k = [1...n]]` is `[1, 0]`, and `\sum_{k=1}^{n} k` is 0. CE parses
   `\left[1...n\right]` to `Range(1, n)`, so today an imported Desmos range
   has the Desmos value.
2. **Option (a) changes the value of imported Desmos documents**, so "Tycho
   needs no change" holds for the sample notebooks only. The corpus
   (`~/dev/tycho/_TASK/desmos/desmos-corpus`) has 2,722 two-bound ranges with
   literal bounds, none of them descending; a range whose bound reaches below
   its start at run time (`[1...length(L)]` on an empty list) cannot be
   counted by a text search. With (a), Tycho's importer must rewrite each
   Desmos range to a form that counts in both directions, and CE has no such
   form with a step (`Range(a, b, Sign(b - a))` is empty at `a = b`).
3. **Epsil's `..` already has two meanings.** As a `match` pattern, `10..1`
   is an empty range (`range-pattern-empty`, `test/epsil/match.test.ts`); as
   a value it counts down. The Epsil corpus works around the value rule twice
   (`test/epsil/corpus/language/descending-range.epsil`,
   `test/epsil/corpus/exercism/nth-prime.epsil`).

Option (b) in detail: the Epsil parser gives `a..b` the form
`Range(a, b, 1)`, and the Epsil serializer prints that form as `a..b`. The
`Range` operator, LaTeX, the compiled targets and the Desmos import do not
change. A literal `7..4` gets the warning and the fix-it of option (a).
Size S. Open sub-choice: the call `Range(a, b)` written in Epsil keeps the
operator's rule (recommended: one operator, one rule, and `Range(a, b)`
still prints as `Range(a, b)`), or becomes ascending too.

The `instrument` path is in the Tycho repo
(`~/dev/tycho/scripts/repros/2026-11-20-ce1604-empty-range-loop.mts`); it
needs no change for (b).

## Decision

User decision 2026-11-20: (b)

CE (2026-11-20): option (b) is implemented. The Epsil parser gives `a..b` the
form `Range(a, b, 1)`, so `a..b` with `a > b` is empty; a range pattern
`lo..hi` keeps its two operands. `serializeEpsil()` writes `Range(a, b, 1)` as
`a .. b` and `Range(a, b)` as a call. Two literal bounds with `a > b` (`7..4`)
give the warning `range-empty`, with the fix-it `Range(7, 4, -1)`. The call
`Range(a, b)`, MathJSON and LaTeX keep the rule of the operator. On the
working tree, the instrument's four witnesses read as the empty range: the
loop over `1..0` runs 0 times, `length(1..n)` and `sum(1..n)` are 0 at
`n = 0`, and `sum(k, (k, 1, n)) == sum(1..n)` is `True`. The fix is commit
`3453f0cb0c8d700886a5bbb4d493cb9c1b7404d5`.
