The norm of a range that ends at the length of a filtered list is wrong (1 instead of 2√310), or the formula stops with the error "Filter predicate must return True or False", because the list is counted while the type of the formula is computed.

## Witness

At 277bdef3c32b606388b9fa706a8e61acd19b781e plus the CE-1723 change.

1. Wrong value. A prepared Document whose profile declares a host predicate
   (in the `configureProfile` callback of `createDocumentEnvironment`):

   ```ts
   ce.declare('Keep', {
     signature: '(real) -> boolean',
     pure: true,
     evaluate: ([x]) => (x.re < 30.5 ? ce.True : ce.False),
   });
   ```

   with the input `w` declared `real` and the rows

   ```
   L = Map(Function(2k, k), Range(1, 40))
   P = Filter(L, Function(Keep(k), k))
   c = Norm(Range(1, Length(P)))
   ```

   `c` evaluates to `1`. `Length(P)` is 15, and `Norm(Range(1, 15))` is
   `2√310` (35.21…). `Add(Norm(Range(1, Length(P))), Length(Range(1, Length(P))))`
   evaluates to `3`.

2. Error. On the engine scope, with
   `L := Map(Function(k, k), Range(1, 4))` and
   `P := Filter(L, Function(Less(k, 2.5), k))`,
   `ce.box(['Norm', ['Range', 1, ['Length', 'P']]]).type` throws
   `Filter predicate must return "True" or "False".`

Before the CE-1723 change, `Sin`, `Add`, `Multiply`, `Negate`, `Sqrt`,
`Power`, `Less`, `Abs`, `Floor`, `Mod`, `Exp`, `Round`, `Hypot` and a call
of a function literal over `Range(1, Length(P))` had the same defect: in
case 1, `Sin(Range(1, Length(P)))` was `[Sin(1), 0]` and
`Add(Range(1, Length(P)), 1)` was `[2, 1]`. CE-1723 moved the type tests
before the test of a finite collection in the broadcast typing, so these
now read the type only and give the right value. `Norm` still reaches the
count through its own type handler.

## Cause and options

The type of `Norm` (`linear-algebra.ts`, `isPointListOperand`) reads
`isFiniteCollection` of its operand. For `Range(1, Length(P))` that reads
the count, which evaluates the bound `Length(P)` (`operandNumericValue`,
`collections.ts`). This runs inside `withStaticTypingView`, where the
parameter `k` of the `Filter` predicate reads as a symbol with no value. The
host predicate answers `False` for it, the `Less` predicate does not decide
and `Filter` throws. The wrong count is memoized on the `Filter` view, and
the evaluation reads it later.

Other type handlers that read `isFiniteCollection` or `count` of an operand
can reach the same path.

Options:

1. Do not evaluate a `Range` bound inside a type computation: a bound with
   no direct numeric value reads as unknown there, and the count stays
   `undefined`. This covers every type handler. It can change the types of
   expressions whose type now depends on a known count.
2. Do not apply a function literal inside the static typing view (the
   `Filter` count declines there), and do not memoize a count computed in
   that view.
3. Fix the `Norm` type handler alone, as CE-1723 did for the broadcast
   typing.
