A Desmos comparison of two lists must compare them element by element, up to the shorter list, as Desmos does.

## Request

A library operator that compares two lists by position: `<`, `≤`, `>`, `≥`,
`=`, `≠`, applied to the elements at the same position, up to the shorter
list, with a scalar operand broadcast. The result is a list of booleans. The
name and the form are CE's choice; the instrument expects a builder
`(relation, a, b) => [<name>, relation, a, b]` in its `OPERATORS.compare`,
with `relation` one of `Less`, `LessEqual`, `Greater`, `GreaterEqual`,
`Equal`, `NotEqual`. One operator per relation is equally good.

Why: as for CE-1320. Tycho now compiles this comparison in a `compile` handler
on `At`, only where it is the condition of an index; the new compiler declines
that handler. CE-1320's mask reads the result of this operator.

## Meaning

`L = [1,2,3,4,5]`, `D = [1,0,1]`, `M = [1,5,3,4,5]`, `K = [1,0,1]`.

| comparison | result | why |
| --- | --- | --- |
| `L > D` | `[F,T,T]` | lengths 5 and 3: compared over 3 |
| `L = M` | `[T,F,T,T,T]` | element by element |
| `L ≠ M` | `[F,T,F,F,F]` | element by element |
| `K = 1` | `[T,F,T]` | a scalar broadcasts |

Ground truth: official Desmos API, 2026-10-03, read through the filters of
CE-1320 (Tycho `scripts/repros/2026-10-03-positional-list-comparison-probe.mts`).

Edge cases for CE to decide and document: a hole in either list gives a hole
(or false) at that position; an empty list gives an empty list; two point
lists compare whole points for `=` and `≠` only.

Expected on each route: the interpreter, `javascript` and, for lists of a
length known at compile time, GLSL.

## Today (0.190.0)

`L > D` (lengths 5 and 3) is an `incompatible-dimensions` error. `L = M` and
`L ≠ M` compare the whole lists and give one boolean (`False`, `True`). A
list and a scalar (`K = 1`) already give `[T,F,T]` on both routes.

## Can existing operators express it?

At equal lengths, `Map` over the indices with the relation of the elements
does; the cut to the shorter list needs `Take` on both lists with the minimum
length. If CE judges that form (`Map(Range(1, Min(Length(a), Length(b))),
i -> Less(At(a, i), At(b, i)))`) compiles as well as an operator would on
both targets, Tycho will rewrite to it and this request can close.

History: CE declined this reading as the DEFAULT of the relations on
2026-10-04 (Tycho ledger row 365). This request is for a separate operator.

## CE answer

CE (2026-11-14): P3 confirmed. Disposition: no new operator is proposed; the
rewrite to existing operators gives the table, and by the user decision of
2026-11-14 an operator is added only where a rewrite cannot say the rule.
Probed at `08ef3106ecbce52e702f1f06451ebf3bb330c926` with
`L = [1,2,3,4,5]`, `D = [1,0,1]`, `M = [1,5,3,4,5]`:

| Form | Interpreter (materialized) | `profile: 'ir'` | Existing compiler |
| --- | --- | --- | --- |
| `Map(i ↦ Greater(At(L, i), At(D, i)), Range(1, Min(Length(L), Length(D))))` | `[False, True, True]` | `[false, true, true]` | the same |
| the same with `Equal` and `M` | `[True, False, True, True, True]` | the same | the same |

The form compiles on both JavaScript compilers as one loop over the range,
with no intermediate list. A scalar operand needs no rewrite (`K = 1` is
already `[T, F, T]`). On GLSL the lengths must be stated in the types, as for
any list there. Not probed: a hole in a list (a `NaN` element compares false
at its position on every route, which is one of the two readings the issue
allows), point lists, and GLSL. Workaround, which is also the proposed
answer: Tycho rewrites to this form at compile time. If Tycho's instrument
confirms the table with this builder, this issue can close.

CE (2026-11-14): Tycho's instrument reads READY with the builder of the
answer above, 4 of 4 cases on 0.190.0, interpreter and compiled JavaScript
(Tycho `8f99844d313b32f02b91eee153f945bdd0e195ca`). Closed with no change in
the engine: the rewrite is the answer.
