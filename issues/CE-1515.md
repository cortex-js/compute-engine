Defining three functions that call each other in a cycle never finishes and runs out of memory.

## Witness

Each head declared `function`, then assigned in order:

```
a_2(n) = {n <= 0: 1, c_2(n - 1) + b_2(n - 1)}
b_2(n) = {n <= 0: 1, c_2(n - 1) + n^2}
c_2(n) = {n <= 0: 1, a_2(n - 1)}
d_2(x) = a_2(3) + x^2
```

On 5b9f88cf5 (and 0caa86406, the parent of cbd971112) this takes about
0.5 s and `d_2(1)` is 8; from cbd971112 on, `assign('d_2')` never returns
(Tycho: about 4 GB after 5 minutes). Turning off only the early return that
cbd971112 added to `_deriveSignatureOnce` (`if (v._isTypeInFlight?.()) {
noteReentrantSignatureRead(); return … }`) restores 0.5 s and the same
values.

## Cause and options

Inferred from the code, not traced: `noteReentrantSignatureRead()` with no
owner taints every active derivation frame
(`declared-parameter-result.ts`, "Conservatively taint all active signature
derivations"), and a tainted frame stores no `_signatureMemo`. In a cycle of
three heads each derivation reaches a literal whose type is in flight, so no
head is ever memoized and each derivation derives the others again.
Options: (a) pass the owner, `noteReentrantSignatureRead(this)`, so only the
frames opened after this definition's are tainted; (b) remove the early
return. Both are in the binding workstream's code: its owner decides.

## Decision

2026-11-19, the user: (a). The early return passes its owner,
`noteReentrantSignatureRead(this)`, so only the derivations opened after
this definition's are tainted.

## Follow-up witness

The owner-only patch completes the three-head witness. A second check found
that it can publish an enclosing signature derived from a provisional result.
Declare `F` and `G` as bare `function`, then assign these bodies in order:

```
F(n) = {n <= 0: 1, G(n - 1)}
G(n) = {n <= 0: [1, 2], F(n - 1)}
```

Declare a new real, then read the stored `Function` literal's type through
`ce.lookupDefinition('F').value.storedValue.type`. Box and read `F(1)` and
`G(2)` twice. `F(1)` can narrow to `number` on the second read even though
it evaluates to `[1, 2]`. The original guard also gives that narrow type.
Tracing the owner-only patch shows a newly published provisional `F` memo.

A checked alternative keeps the conservative provisional guard for functions
with a direct self-call and uses the normal type-cell path for mutual-only
recursion. That version preserves both result shapes and passes all six
orders of the three-head example, the variant with a direct self-call,
and the Tycho scalar-parameter signature suite. This alternative awaits
a decision. Local evidence is in `/private/tmp/ce1515-review.6CtEhj` and
`/private/tmp/ce-cycle-1515.0lX6l6`.

Removing the early return outright also has a direct-recursion witness.
Declare `F` as bare `function`, create an unrelated engine object, and assign
`F(n) = {n = 0: [1, 2], 2*F(n - 1)}` as a `Function` literal. `F(m)`
reports `number | vector<2>` with the direct-only guard. The complete
removal instead reports `list<list<any> | number | tuple> | number | tuple`.
The result reproduces both with and without an assumption on a different
variable. Compare `no-guard-assumptions.log` and `direct-assumptions.log`
in the cycle evidence directory.

Revised 2026-11-19, the user chose the direct-only guard. Keep the
provisional shortcut when the literal calls its own head directly. Use the
regular reentrant type-cell path for mutual-only recursion.
