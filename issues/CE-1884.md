Compiled matrix fusion can recompute an intermediate that the same program
already stores for another result.

## Witness

Declare `M`, `A`, and `Q` as `matrix<real>`, then compile this on
JavaScript with `fallback: false`.

```ts
const B = ['Sin', ['Add', 'M', 'A']];
const expr = ce.box(['Tuple', B, ['Add', B, 'Q']]);
const result = compile(expr, { fallback: false });
```

The generated code at `478b9981d^` has one sine call site in a loop.
With `478b9981d`'s lowerers, it has two. Both versions have six array
allocation sites and four dimension checks. They agree on 300×300 inputs.
The extra sine call also appears in `MatrixMultiply(B, B + Q)`. Runtime
impact was not measured.

## Cause and options

The matrix fusion path in `ir/lower.ts` forwards an element computation
even when another consumer already needs the materialized matrix. Measure
representative kernels and consider reading the materialized value when
it already exists. Preserve fusion for intermediates that would otherwise
require a separate allocation.

## Measurement

A paired local timing used emitted JavaScript from the parent lowerers and
from the current lowerers, with the same remaining source and runtime.
The 300×300 inputs were the same on both sides. Both results matched a
direct JavaScript implementation at every element. On Node 26.13.0, after
30 warmup calls per variant, nine alternating batches of 20 runs gave
median times of 1.358 ms and 1.531 ms per run, with a median paired ratio
of 1.125. The shared box lock was held and load averaged 5.3 / 5.6 / 6.3
on 18 cores. This measures the witness and does not establish a host
workload regression or a benefit for changing the general fusion rule.
