A comparison of a pixel read from an array with a plain tuple, `px[i] == (255, 255, 255, 255)`, does not compile; in the interpreter it is `False` for every pixel, which is not what its author means.

## Witness

At commit `74595f4c6168d444a223289f7b370e8a045300f4`, after `executeEpsil()` of

```
type alias Byte = integer<0..255>
type Pixel = tuple<r: Byte, g: Byte, b: Byte, a: Byte>
let px = arrayFrom([Pixel(1, 2, 3, 4), Pixel(255, 255, 255, 255)], "Pixel")
let e1 = (i: integer) => px[i] == (255, 255, 255, 255)
let e2 = (i: integer) => px[i] == Pixel(255, 255, 255, 255)
```

| Program | Interpreter | `compile(…, { fallback: false })` on `javascript` |
| --- | --- | --- |
| `e1(1)`, `e1(2)` | `False`, `False` | declines: `Equal(At("px", i), Tuple(255, 255, 255, 255)): Equal of a tuple: its value on a tuple is not its value on a list` |
| `e2(1)`, `e2(2)` | `False`, `True` | `false`, `true` |

On `glsl`, with `src` an input declared `array<Pixel>`,
`Equal(At(src, i), Tuple(255, 255, 255, 255))` declines with the same
message. With a cell type that is an unnamed tuple
(`array<tuple<Byte, Byte, Byte, Byte>>`) the comparison with a tuple compiles
on both targets.

Workaround: compare with a value of the same type, `px[i] == Pixel(255, 255,
255, 255)`, which compiles on JavaScript and is the comparison that the
author means.

## Cause and options

A value of a nominal type and an unnamed tuple are never equal in the
interpreter: their heads differ (`Pixel` and `Tuple`). The lowering of
`Equal` has no rule for a record against a tuple and declines (`lower.ts`,
"Equal of a tuple").

1. A static diagnostic in Epsil: the comparison of a value of a nominal tuple
   type with a tuple literal is always `False` (or always `True` for `!=`).
   This tells the author what is wrong, which a compiled `false` does not.
2. Compile the comparison to the constant `false` (`true` for `NotEqual`),
   the interpreter's value, after the operands are evaluated for their
   effects.
3. Keep the decline: the code falls back to the interpreter, which gives
   `False`.

Recommended: 1, and 3 until a program in a corpus needs 2. The comparison
must not become the equality of the elements: that gives `True` where the
interpreter gives `False`.
