In Epsil, `xs |> std::take(2)` gives an error, while `xs |> take(2)` gives the first two elements.

## Witness

```
let xs = [1, 2, 3]
xs |> take(2)           // [1, 2]
xs |> std::take(2)      // Error(incompatible-type, 'Take(2, Error("missing"))')
std::take(xs, 2)        // [1, 2]
xs |> std::take(_, 2)   // [1, 2]
```

`std::` is how a program reaches a library function that one of its own
names shadows (`function take(…)` in the source), so a pipe into it is the
same program as a pipe into `take`. Run on CE main after 0.198.1 with
`executeEpsil`.

Workaround: write the placeholder (`xs |> std::take(_, 2)`) or the call
(`std::take(xs, 2)`).

## Cause and options

A `std::` call parses as `["Apply", ["Module", "take"], …]`, not as
`["Take", …]`. `pipeStageWithImplicitTopic`
(`src/compute-engine/library/core.ts`) places the piped value only in a call
whose operator is the function's name, so the `Apply` of a `Module` stage
gets no implicit topic and `Take` receives `2` as its collection.

Fix: in `pipeStageWithImplicitTopic`, treat `Apply(Module(name), …args)` as
the call `name(…args)` for the placement rule (the same slot rule), and keep
the `Module` head in the rewritten stage. Editor side: once the engine pipes
into a `std::` call, `markPipedTopic` in `src/epsil/signature-help.ts` must
match the `std::` call node (its span starts at `std`, not at the name) so
that signature help marks the piped parameter there too.
