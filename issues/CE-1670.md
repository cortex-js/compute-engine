Epsil code in Tycho's editor shows four colours and gets some strings and comments wrong.

## Today

Tycho's Epsil editor (CodeMirror 6) colours code with its own regular
expression: keyword, string, number and comment. It does not know nested
`/* */`, `"""…"""`, `#"…"#`, backtick names or LaTeX islands. The editor is a
separate bundle that may contain nothing from `@cortex-js/` (to keep the
parser out of it); the Tycho user approved an exception for a
highlighting-only CE module. The VS Code grammar
(`vscode-epsil/syntaxes/epsil.tmLanguage.json`) is not in the npm package, and
CodeMirror does not read TextMate grammars.

## Request (terms agreed with CE)

1. A new package entry `@cortex-js/compute-engine/epsil-highlight`: ESM,
   self-contained, with no runtime import from CE or from any other package.
   The character classes and keyword tables of `characters.ts`,
   `reserved-words.ts` and `operators.ts` are bundled in, so they stay the
   lexer's tables.
2. Exports, from one implementation:
   - `epsilStreamParser`: an object of CodeMirror's `StreamParser` shape
     (`startState()`, `token(stream, state)`, `copyState?`, `blankLine?`),
     with no dependency on CodeMirror (the interface is structural).
   - `epsilHighlightTokens(source: string): { start: number; end: number;
     style: string }[]`, which runs the stream parser line by line, so the
     two cannot disagree. Tycho's read-only rendering (shown before the editor
     loads) uses it.
3. Style strings: `@lezer/highlight` tag names where one exists —
   `controlKeyword`, `definitionKeyword`, `operatorKeyword`, `bool`, `atom`,
   `typeName`, `number`, `string`, `escape`, `comment`, `docComment`,
   `operator`, `paren`, `brace`, `squareBracket`, `separator`, `punctuation`,
   `variableName`, `meta`. Anything else is a plain custom name that Tycho maps
   in its own `tokenTable`: `latex` (islands), `rawString` (`#"…"#`), and
   `functionName` only if the parser reads a symbol followed by `(` as a call
   in every case (else dropped). CE exports no `tokenTable`: that would import
   `@lezer/highlight`.
4. State across lines, per `lexer.ts`: nested block comments (depth; doc or
   plain), `"""` strings (the opening `"""` ends its line; an interpolation
   inside cannot cross a line), and `$…$` islands (they do not stop at a line
   break; `\$` escapes). Single-line, no state: `#"…"#`, `"…"` and their
   interpolations, backtick names, `//` and `///` comments, `#pragma`; `#!`
   only on the first line.
5. One test checks the token boundaries of the stream parser, the TextMate
   grammar and the highlight.js mode against `tokenize()` over the ` ```epsil `
   blocks of `src/epsil/docs`. The two regex grammars are not generated from
   the new module.
6. A doc page for the entry.

Not in this request: semantic tokens (parameter, local, library function,
type) from the checked program, and a Lezer grammar (folding, structural
selection). Each would be a separate request.

## Instrument

`npx tsx scripts/repros/2026-11-21-ce1670-epsil-highlight.mts` (Tycho) loads
the entry, prints its exports and the tokens of a sample with every construct
that spans lines, and prints `CE-1670: READY` when the exports exist and
`while`, `let`, a two-line nested comment, a three-line `"""` string and a
two-line island get `controlKeyword`, `definitionKeyword`, `comment`, `string`
and `latex`. On 0.197.1: `CE-1670: NOT READY` (the entry does not exist).

## CE answer

CE (2026-11-21, compute-engine-fe): agrees to the stream parser, not a Lezer
grammar (a second parser to keep in step with `parser.ts`; highlighting needs
tokens, not a tree). Estimate: an agent session of a few hours (module,
package entry, corpus test, doc page); ships in the next CE release after it
lands.
