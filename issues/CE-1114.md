In a scope where the user defines a function with the name of a built-in function, a derivative or an integral of another built-in function can contain the user's function instead of the built-in one, and gives a wrong value.

## Witness

At commit `5408577629d05c0bd64ad5caf56aafeb47b7d322`:

```ts
ce.pushScope();
ce.declare('Sqrt', 'function');
ce.assign('Sqrt', ce.box(['Function', ['Add', 'y', 100], 'y']));
const d = ce.box(['D', ['Arcsin', 'x'], 'x']).evaluate();
d.json                      // ["Divide", 1, ["Add", ["Negate", ["Power", "x", 2]], 101]]
d.subs({ x: 0.5 }).N()      // 0.0099; must be 1.1547 (1/√(1 − x²))
ce.popScope();

ce.pushScope();
ce.declare('Sin', 'function');
ce.assign('Sin', ce.box(['Function', ['Add', 't', 100], 't']));
const r = ce.box(['Integrate', ['Cos', 'x'], 'x']).evaluate();
r.json                      // ["Sin", "x"], bound to the user Sin
r.subs({ x: 1 }).N()        // 101; must be 0.8415
ce.popScope();

// Library calls boxed before the push, differentiated in the scope of the
// user Sin above:
const s1 = ce.box(['Sin', 'x']);
const s2 = ce.box(['Power', ['Sin', 'x'], 2]);
ce.pushScope(); /* declare and assign the user Sin as above */
ce.box(['D', s1, 'x']).evaluate()
  // ["Apply", ["Derivative", ["Module", "Sin"], 1], "x"]; at x = 1 it is 1,
  // must be cos 1 = 0.5403: `Derivative` reads `Sin` by name
ce.box(['D', s2, 'x']).evaluate()
  // ["Multiply", 2, ["Sin", "x"]] with the user Sin; at x = 1 it is 202,
  // must be sin 2 = 0.9093
ce.popScope();
```

With the uncommitted CE-1109 changes (measured 2026-11-07), `D(s1, x)` in
the scope stays the unevaluated `D(Sin(x), x)` with the library `Sin`, but
its numeric value at x = 1 in the scope is still 1, and `D(s2, x)` is
`2·Sin(x)·D(Sin(x), x)` with the first `Sin` bound to the user function
(202 at x = 1); the evaluation of the product binds it again by name
(CE-1118).

`crafted`: the program defines a function with the capitalized name of a
library function and asks for the derivative or the integral of another
library function in the same scope.

## Cause and options

A library rule builds its result by name in the current scope: the
derivative of `Arcsin` names `Sqrt`, the integral of `Cos` names `Sin`, and
the evaluation of `Derivative(Sin, 1)` reads `Sin` by name
(`derivative()`, `symbolic/derivative.ts`, where it builds
`ce.function(fn.symbol, …)` and `apply(ce.symbol(fn.symbol), …)`). In a
scope where a user definition shadows such a name, the name binds to the
user function. CE-1109.2 makes the rules not apply to a call whose own name
is shadowed (`libraryRuleBlocked()`, `library-shadowing.ts`), but a rule
whose result names ANOTHER shadowed function is not covered.

Options: (a) build the results of the derivative and integral tables in a
scope where every library name that the current scope shadows is bound to
its library definition, as `simplify()` does for its rules
(`simplifyShadowedCallsMasked()`, `simplify.ts`); (b) after the rule, test
the result for a call of a shadowed library name that the rule built, and
keep the expression unevaluated (a decline). CE-1109.5 (a call bound to a
given definition without a borrowed scope) makes option (a) simpler.
