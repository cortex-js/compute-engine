A function whose parameter accepts a point of reals or a string refuses the point of two `NaN` coordinates, which the same function with the point parameter alone accepts.

## Witness

At `9603fdae19bd700388c570c4f390595b94dd1fa3` (before and after the fix of
CE-1135):

```ts
const ce = new ComputeEngine();
ce.declare('H', '(tuple<real, real>) -> unknown');
ce.parse('H(p) := p').evaluate();
ce.box(['H', ['Tuple', 'NaN', 'NaN']]).evaluate(); // (NaN, NaN)
ce.declare('F', '(tuple<real, real> | string) -> unknown');
ce.parse('F(p) := p').evaluate();
ce.box(['F', ['Tuple', 'NaN', 'NaN']]).evaluate();
// Error(ErrorCode("incompatible-type", "string | tuple<real, real>", "tuple<nan, nan>"), (NaN, NaN))
ce.box(['F', ['At', ['List', ['Tuple', 1, 2]], 5]]).evaluate(); // the same error
```

Expected: `(NaN, NaN)`, as `H` gives. The point of `NaN` coordinates is the
value of a read past the end of a list of points, so a program that reads
such a list and passes the point to `F` fails where it passes with `H`.

Workaround: declare the parameter as the point type alone, or test the point
with `IsNaN` before the call.

## Cause and options

The `NaN` point is accepted at a point parameter by `acceptsNaNArgument()`
(`src/compute-engine/boxed-expression/validate.ts`), which asks
`pointArity(param)` (`src/compute-engine/collection-utils.ts`) for the arity
of the parameter. `pointArity()` gives `undefined` for a union with an arm
that is not a point type (`tuple<real, real> | string`), so the exemption
does not apply, and the type `tuple<nan, nan>` of the point does not match the
union. Option: in `acceptsNaNArgument()`, accept the `NaN` point when a tuple
arm of the parameter has the arity of the point and numeric components, the
same test as for one point type. Add a test with `F((NaN, NaN))` to
`test/compute-engine/point-function-call-typing.test.ts`. Size S.
