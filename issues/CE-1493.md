A function whose parameter is read at indices and passed to two functions that read it at different lengths gets a parameter type that depends on the order of the calls, or that refuses every argument.

## Witness

On CE main with CE-1489 (2026-11-18), with `touches(p, q)` reading `p[1]`
to `p[3]` and `other(q) { q[1] + q[5] }`:

- `function f(p, c) { touches(c, p) && other(c) > 0 }` types `c` as
  `tuple<number, number, number, unknown, number>`;
  `function f(p, c) { other(c) > 0 && touches(c, p) }` types it as
  `tuple<number, unknown, unknown, unknown, number>`. The extension of an
  index-read tuple (`indexReadTupleExtension()`) applies only to a longer
  slot: a shorter one after it adds nothing.
- Older than CE-1489: `function f(p, c) { touches(c, p) && c[5] > 0 }`
  types `c` as `tuple<number, number, number>` although the body reads
  `c[5]`; `function f(p, c) { c[5] > 0 && touches(c, p) }` types it as
  `dictionary<any> | indexed_collection<any>`, with a return type
  `boolean | list<boolean | list<any>>`.

In each case the compiled call declines and the interpreter gives `True` on
a 5-tuple: no wrong value.

## Cause and options

An index-read slot no longer than the current index-read tuple is not merged
into its components, and a read past the length of a slot does not lengthen
the tuple. Option: merge the components that a shorter slot covers with the
`narrow(read, e.type)` rule, and lengthen the tuple to the highest index
read, keeping the index-read mark.
