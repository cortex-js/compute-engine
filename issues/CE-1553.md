A function that returns an error for a bad argument never returns anything, also for a good argument.

## Witness

On 0.193.0, `f(x: any) = if x == 1 { "one" } else { Error("bad") }` followed by
`f(1)` gives the inert call `f(1)` and the diagnostic `runtime-error: bad, in If
argument 3, in DefineFunction argument 2`; `f(2)` is also inert. Control: the
same function with `"other"` in place of `Error("bad")` gives `"one"` for
`f(1)`. The same happens with `match`.

## Cause and options

Unverified: the `Error(…)` literal is evaluated when the definition is read,
not when the branch is taken, and the failed evaluation leaves `f` without a
body. Expected: the body is held, and `f(2)` is the Error value. Workaround:
Tycho's drawing prelude returns a marker value of its own and converts it to a
warning. Tycho half on adoption: return `Error(…)` from the prelude and drop
the "invalid" figure kind.

## CE answer

CE (2026-11-19): the witness reproduces at
`3b91759b63ddd9608bfaa7f71d5166d9f0ab6e2b`, and it is the documented
behavior. `docs/ERROR-MODEL.md` §1 and the ruling of 2026-09-03 in the same
file say that a written `Error(…)` is a static diagnostic node that makes
every tree above it invalid. A function whose body contains one is never
defined. `RuntimeError(code)` is the way to return an error value at run
time; that ruling added it "instead of exempting held bodies from the
validity rule". `test/epsil/runtime-error.test.ts` ("a written `Error(…)` in
the same body still does not define the function") pins the behavior.

Workaround, verified at the same commit: write `RuntimeError("bad")` in
place of `Error("bad")`.

```
f(x: any) = if x == 1 { "one" } else { RuntimeError("bad") }
[f(1), f(2)]                       → ["one", Error("bad")], no diagnostic
f(x: any) = match x { 1 => "one"; _ => RuntimeError("bad") }
[f(1), f(2)]                       → ["one", Error("bad")], no diagnostic
```

Tycho half: return `RuntimeError(…)` from the drawing prelude and drop the
"invalid" figure kind. No CE change is necessary for that.

The fix that the issue asks for reverses the ruling, so the board must
choose:

- **(a) Keep the ruling (recommended).** Close CE-1553 with no CE change.
  Tycho uses `RuntimeError`. Cost: none. The trap stays: a written
  `Error("bad")` in a function body gives `runtime-error: bad` at the
  definition, and the calls stay unevaluated.
- **(b) An error in an operand that a selecting operator may not demand does
  not make a held body invalid.** A prototype is in the worktree
  `/tmp/wt-cebatch-1553` (patch `/tmp/cebatch-1553.patch`, and the new test
  `test/epsil/ce-1553-error-in-unselected-branch.test.ts`, which the patch
  does not hold; src +54 −4 in
  four files: `error-value.ts`, `boxed-function.ts` (the `canonical`
  getter), `boxed-operator-definition.ts` (the `Invalid function` check),
  and `MatchCase` gets `selectsOperands`). With it:
  `f(x: any) = if x == 1 { "one" } else { Error("bad") }` gives
  `["one", Error("bad")]` for `[f(1), f(2)]`; the same with `match`;
  `Block(If(True, 1, Error("bad")))` gives `1` (it gives the error at HEAD,
  while `Sin(If(True, 1, Error("bad")))` gives `sin(1)`);
  `h(x) = if x > 0 { x } else { 1 + "a" }` is defined and `h(1)` is `1`, and
  the `static-type-error` diagnostic stays. `k(x) = x + Error("bad")` is still
  not defined. Cost: the ruling and §1 of `docs/ERROR-MODEL.md` change, the
  test in `test/epsil/runtime-error.test.ts` is inverted, and `npm test` is
  not run yet. Gap: `let g = (x) => if x > 0 { x } else { Error("neg") }` is
  still not callable, because an invalid `Function` literal has the type
  `unknown`, so the call is not an application. That is a second change.
