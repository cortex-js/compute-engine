An element-wise operation on two lists whose declared lengths differ is accepted when the expression is built and fails only when it is evaluated, so the program reports the error late.

## Witness

On main `e13fc32df`:

| Program | Before evaluation | `evaluate()` |
| --- | --- | --- |
| `p: list<real^2>`, `q: list<real^3>`, `Add(p, q)` | `isValid` true, type `vector<real^2> \| vector<real^3>` | `Error("incompatible-dimensions", "2 vs 3")` |
| `Add(List(1, 2), List(1, 2, 3))` | `isValid` true, type `vector<integer^2> \| vector<integer^3>` | `Error("incompatible-dimensions", "2 vs 3")` |
| Epsil `function f(p: list<real^2>, q: list<real^3>) { p + q }` | no diagnostic | |

Both lengths are in the static types, so the mismatch is known before the
program runs. The expected behavior is a static `incompatible-dimensions`
error at the `Add` (and the result type `error`), as for other operand
errors that the types prove. The union result type is also wrong: no value
of the expression has either type.

Two lists whose lengths are not both stated (`list<real>`) are out of
scope: their lengths are known only at run time, where the interpreter and
compiled code already report `incompatible-dimensions` (compiled
JavaScript emits one `_agree` of the two lengths before the loop).
