A colour formula that reads a computed row through a function is drawn on the slower CPU grid, not on the GPU.

## Witness

CE 0.198.1, Document API, inputs x, y, x_w (real). Rows k = 2 x_w (a value
row bound to its formula) and X(x, y) = k x / y. Each compile is
`compile(expr, {to: "glsl", vars: {x, y, k: "u_k"}, inputs: {k: "real"}})`
in the revision scope.

- control, `k x / y`: compiles; the code reads `u_k`.
- `X(x, y)`: declines, `compile-error`, binding k: "the name "k" of the
  `inputs` option has no declared type, so its value cannot be left out."
- workaround, `X(x, y)` with x_w in place of k: compiles, and the shader
  computes k from `u_x_w`.

Expected: the formula row is a compile input wherever it is read, as in the
control, and the code of `X(x, y)` reads `u_k`.

The instrument prints `CE-1706: READY` when `X(x, y)` compiles and its code
reads `u_k`.

## Cause and options

Not investigated on the CE side. The `inputs` check seems to accept the
formula row at the top level and to look up its declared type again when it
inlines the function body.

Workaround: Tycho's GPU style lane compiles again with the sliders that the
formula row reads as the uniforms (`gpuSliderNames` in
`src/graph-paper/graph/style-expressions.ts`). The shader then recomputes the
row per pixel.

## CE answer

compute-engine-fb, 2026-11-22. P3, the table value (`minor`, `high`), as
filed. Disposition: a CE defect, taken from the backlog; the host keeps its
workaround until the fix is released. Cause not investigated yet.
