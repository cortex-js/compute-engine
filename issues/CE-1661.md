In the completion menu at an argument, functions whose result may be of the
expected type are ranked with the functions whose result cannot be.

## Witness

On CE 0.197.1, `epsilCompletions(ce, "determinant(", 12)` gives
`expectedType: "matrix"` and ranks 10 library functions as fitting (rank 3:
`adjugateMatrix`, `inverse`, `onesMatrix`, …). It ranks as not fitting
(rank 5, with the 584 other library names):

| Function             | Detail                                                  |
| -------------------- | ------------------------------------------------------- |
| `transpose`          | `(value, axis1: integer?, axis2: integer?) -> value`    |
| `conjugateTranspose` | `(value, axis1: integer?, axis2: integer?) -> value`    |
| `diagonal`           | `(value) -> value`                                      |
| `hadamardProduct`    | `(matrix \| vector, matrix \| vector) -> matrix \| vector` |

So at `determinant(t`, no entry fits, and `transpose` ranks with `tan`.

Tycho wants to hide, at an argument, the library names that cannot be of the
expected type (`determinant(b` offers `barnesG`, `besselJ`, … that return a
number). With today's ranks, hiding rank 5 would hide `transpose`. Tycho dims
the rank-5 entries instead, and does not use them as the inline suggestion.
The instrument prints READY when the four functions rank below 5 (exit 0);
today it prints NOT READY (exit 1).

Tycho half on adoption: in `epsilCompletionList` of
`src/graph-paper/epsil-editor/epsil-editor-slot.ts`, hide the entries marked
`mismatch` instead of dimming them (the menu and the inline suggestion in
`src/graph-paper/epsil-editor/epsil-editor.ts` read the mark).

Two more cases, from the same editor (CE 0.197.1 source, main):

```
const A : matrix = identityMatrix(4)
const another = 5
const anumber: integer = 3
inverse(a        → 2 A, 3 adjugateMatrix, 4 another (no type), 4 anumber
A |> inv         → expectedType "function":
                   3 inverseFunction (function) -> function
                   5 inverse (matrix) -> matrix
                   5 inverseHaversine (real) -> number
```

`anumber` can never be a matrix; `another` has no type in the completion, so
nothing can be said of it. At `A |> inv` the function that fits is `inverse`,
and `inverseFunction` cannot take `A`. The same holds at every argument that
expects a function: at `filter([1, 2], is` the expected type is
`(T) any -> boolean` and `isPrime` ranks 5.

## Cause and options

Investigated in CE (2026-11-21), `src/epsil/completion.ts`:

1. **Rank 3 and 2 need a subtype.** `typeMatches` (line 1499) tests
   `result <: expected`. A result broader than the expected type (`value`,
   `any`, `list`, `collection`) or a union with an arm that fits
   (`matrix | vector`) fails it, and gets the rank of a result that can never
   fit. `overlapsForDeferredValidation` is not usable instead: it says that
   `value`, `unknown` and `any` do not overlap `matrix`. The sound test is:
   match when `result <: expected`; maybe when `expected <: result`, when an
   arm of a union result is either, or for a generic `T` whose bound admits
   the expected type; never otherwise. At `determinant(` this moves about 40
   library names with a list or collection result, and the `value` results
   (`transpose`, `diagonal`), from never to maybe; 37 generic signatures
   (`sort`, `take`, `reverse`) need the bound.
2. **A name of the source has only its declared type.** `declarationDetail`
   (line 1592) reads the annotation; `const another = 5` has none. A name with
   no known type is maybe, never never; a literal initializer gives its type
   (`5` is `integer`). A general initializer stays maybe until the static
   checker gives its type.
3. **A function name at an argument that expects a function is compared by
   its result.** The completion treats a function name as a call, which is
   right where a value is expected (`inverse(…)`), and wrong where a function
   is expected: the name is passed, not called. There the candidate's
   signature is compared (each parameter admits the expected argument, the
   result fits the expected result). At the right side of `|>` the expected
   type is `(<type of the left side>) -> any`, not `function`, since
   `x |> f` is `f(x)`. A generic `T` of the expected signature is bound from
   the other arguments where they give it. This part is a wrong rank today
   and needs no change of contract; it can land first.

The contract: `EpsilCompletionItem.rank` documents 2 and 3 as "type matches"
and 4 and 5 as "other names". Hiding the names that can never fit needs a
third group:

- **(a) Recommended:** a field `fit: 'match' | 'maybe' | 'never'` on each item,
  set when `expectedType` is set. Sort maybe after match in each tier. A host
  hides `never`, for the names of the source and the library alike, and does
  not depend on the rank numbers.
- **(b)** Renumber: 4 the other names of the source, 5 library maybe, 6
  library never, 7 keywords. Fewer moving parts, but a host that compares rank
  numbers breaks without an error, and a name of the source that can never
  fit is still mixed with one that may.

Not part of this issue: a result type that depends on the arguments
(`transpose` of a matrix is a matrix), and the order among the fitting names.
A tighter declared signature for `Transpose`, `ConjugateTranspose` and
`Diagonal` (today `(value) -> value`) also helps here.

Tycho's original request follows.

The rank seems to require the declared result type to
be a subtype of the expected type. Requested: rank as fitting a function
whose result type may be the expected type: a result that overlaps it
(`matrix | vector` for `matrix`), a broad result (`value`, `any`), or a
generic result that the arguments decide (`T`). Rank 5 would then mean "can
never be of this type", which a host can hide. Two other signals would help:
a result type that depends on the argument types (`transpose` of a matrix is
a matrix), and the ranking of the fitting names among themselves.

## CE answer

CE (2026-11-21): P2 confirmed. Needs a decision on the contract, (a) a `fit`
field (recommended) or (b) new rank numbers; part 3 (a function at an
argument that expects a function, and the right side of `|>`) is a wrong rank
and can be fixed first. Workaround until then: dim rank 4 and 5 at an
argument, as Tycho does for rank 5; do not hide them. Member completion after
`.` is CE-1663.

CE (2026-11-21): implemented, option (a), staged in CE, not released.
Each item has `fit` (`match`, `maybe`, `never`) when `expectedType` is set;
hide `never`, and use only `match` for the inline suggestion. Hiding the
numeric functions at a matrix argument cannot be done soundly: most of them
broadcast over a list (`determinant(abs(A))` is valid), so at `determinant(`
`abs`, `barnesG` and `besselJ` are `maybe` (10 match, 313 maybe, 271 never).
`transpose`, `diagonal` and `hadamardProduct` are `maybe`; after `A |>`,
`expectedType` is `(matrix) -> any` and `inverse` is `match`. The ranks
keep their meaning, so the four functions still rank 5 and the instrument,
which tests `rank < 5`, stays NOT READY: change it to test
`fit !== 'never'`.

## Decision

User decision 2026-11-21: (a)
