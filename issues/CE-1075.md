A step that adds samples to a picture could take 100 times more samples per frame on the GPU, but the engine cannot compile it for the GPU.

## Witness

Goal: Tycho's `buddhabrot` prelude function, unchanged
(`src/graph-paper/onboarding/template-data.js`):

```
function step(H: list<number>, n: integer)
  for k in 1..n: iterate (a, b) := (a² − b² + p, 2ab + q) up to 500 times,
  then L = replaceAt(L, c, L[c] + 1) for each cell c the orbit crosses
```

To `wgsl` on 0.182.0: "Could not compile `Apply`: the body of the function
has more than one statement"; a list-writing loop: "a matrix/tensor-valued
local has no GPU declaration".

A handwritten compute shader (one invocation per `k`, `atomicAdd`), Metal:

```
samples   GPU + read-back   JavaScript (handwritten)
5,000     0.5 ms            0.9 ms
500,000   0.9-1.1 ms        87.5-91 ms
```

f32 changes some escapes: counts differ by 2.9 % median per cell.

## Options

Writable storage list, `replaceAt` as a store, `atomicAdd` for a
cross-invocation increment, a compute entry point, an independence proof for
the outer loop. Study: Tycho `roadmap/BUDDHABROT_CODE_STUDY.md`
§ 7.

## Decision

User decision 2026-11-07: the WGSL compute shader compiles the `parallel for`
statement and the parallel comprehension of CE-1093, not an ordinary loop
(no proof of independence). The design is
`docs/plans/2026-11-07-ce1093-parallel-for.md`; this issue is its step 2
(`WGSLTarget.compileKernel()`, integer accumulators). It starts after CE-1093.

## Fix

Commit `97c1699262ba6fded5443410a4c581c764373a23` (2026-11-08, session
cebatch-1075; the worktree of the first session was lost with `/tmp`, so the
change was made again). `WGSLTarget.compileKernel(expr, options)` compiles a
`ParallelLoop` or a `ParallelComprehension` over an integer range to a WGSL
module with a compute entry point, one invocation per pass; each `+=` is an
`atomicAdd` to a `read_write` storage buffer of `atomic<i32>` (a list with the
`len` header of a storage-buffer list, or one integer); the result gives the
bindings, the range and the parameter struct. The host hands over the loop
node of the function body: the locals of the function (`L`, `r`, `n`) are the
inputs of the kernel. The witness compiled and ran on WebGPU in Chromium with
the Metal adapter: 5,000 samples in a median of 1.1 ms per dispatch; the
counts are those of the compiled JavaScript up to the `f32` escapes (total
80,818 against 83,184). Also in the commit: a shader `Loop` reads a run-time
bound (`for m in 1..e`) before its clause, and an else-less `if` whose branch
holds a loop or a `+=` compiles as an `if` statement. Tests:
`test/compute-engine/compile-wgsl-kernel.test.ts`. The guide
`~/dev/cortexjs.io/docs/compute-engine/13-guide-compile.md` has the section
"WGSL Compute Kernels for `parallel for`".

## CE answer

CE (2026-11-08): P2 confirmed. Disposition: fixed in
`97c1699262ba6fded5443410a4c581c764373a23` (see "Fix"). Tycho declares the
counts `list<integer>`, extracts the `ParallelLoop` node of the step, calls
`compileKernel()` with `H` as the accumulator (the kernel reads the length
from the `len` header of the buffer), and keeps the statements before and
after the loop (`let L = H`, `L[90001] += n`) on the host. Until the release
that holds the commit, the step runs on the CPU.
