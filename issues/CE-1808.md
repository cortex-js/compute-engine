In a Tycho notebook, an animation whose timer callback reads a list that is empty runs interpreted instead of compiled, so it is slower.

## Witness

On CE 0.201.5, the JavaScript target declines a function that reads a
variable, defined outside it, whose value is an empty list. The same program
with a list of one element compiles (positive controls):

```epsil
let x: list<string> = []
function f(t: real) { length(x) + t }
f(2)
```

The instrument prints:

```
outer list of one element (control): interpreter 3; compiled 3
outer tuple with a list of one element (control): interpreter 3; compiled 3
outer list of one element with no stated type (control): interpreter 3; compiled 3
outer empty list: interpreter 2; compile declined {"code":"outside-profile", … "message":"Could not compile: List(): an empty list" …}
outer tuple with an empty list: interpreter 2; compile declined … "Could not compile: List(): an empty list" …
outer empty list with no stated type: interpreter 2; compile declined … "Could not compile: List(): an empty list" …
CE-1808: NOT READY
```

The three cases: a variable declared `list<string>` with the value `[]`; a
tuple `("circle", [])` read with `fig[2]`; and `let pts = []` with no stated
type.

On Tycho's production route (a `timer(16, t => do { s = length(x) + t })` in a
code cell), the tick has the note "A timer callback runs interpreted … The
reason: an empty list."

## Cause and options

Not investigated on the CE side. The compiler seems to write the value of the
outer variable as a literal, and it declines the literal `List()`, also when
the variable has a declared element type (`list<string>`).

Tycho effect: the drawing prelude keeps the option keys that a figure refused
in the field `badOptions: list<string> | nothing` of `Figure`, and stores
`nothing` for "no bad key", because with `[]` every callback that reads a
figure made outside it runs interpreted. The same decline is expected for a
user's callback that reads a list which starts empty (a trail of points that
the callback grows); that case is not measured on the production route.

Options: compile an empty list whose variable has a declared or inferred
element type as an empty array of that type; or read the outer variable by
reference when its value is a list.

## Fix

On `javascript`, a `[]` in the value of a variable that a compiled function
reads takes the type of its place: the declared type of the variable when
that is a list of integers, reals, booleans or strings of no stated length
(`let x: list<string> = []`), the type of its position in a tuple
(`fig[2]` of `("circle", [])`), or the type of its field in a value of a
named tuple type (`Figure("circle", [])`). With no stated element type
(`let pts = []`) it is an empty list of integers. The three cases of the
witness compile and give the interpreter's value
(`test/compute-engine/compile-outer-empty-list.test.ts`).

These still decline: an empty list of points
(`let x: list<tuple<real, real>> = []`); a `[]` at a union type, so the
field `badOptions: list<string> | nothing` must become `list<string>`; a
`[]` that the program writes as an argument of a function; GLSL and
`interval-js`. A record with a field that is a list of strings, passed
whole to a function or returned, declines with or without an empty list
(`docs/COMPILATION-MODEL.md`, "a list of strings in a field"): Tycho must
measure its production route after the change of the prelude.

Workaround: `nothing` in place of `[]`, with a test `x is nothing` at the
read.

Tycho half on adoption: in `src/graph-paper/notebook/drawing/prelude.ts`, let
`badOptions` of `Figure` be `[]` when no key is bad (type `list<string>`), and
remove the `nothing` tests of `figureOption`.
