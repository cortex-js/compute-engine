In a notebook code cell, `1e-11 > 1e-12` is false and `1.6e-19 > 0` is false, so a loop or a test on small numbers silently does the wrong thing.

## Witness

On 0.195.1 (the instrument, fresh engine per program):

| Program                        | Today   | Exact ordering |
| ------------------------------ | ------- | -------------- |
| `9.5e-11 <= 0`                 | `True`  | `False`        |
| `9.5e-11 > 0`                  | `False` | `True`         |
| `1e-300 > 0`                   | `False` | `True`         |
| `-1e-11 < 0`                   | `False` | `True`         |
| `1e-11 > 1e-12`                | `False` | `True`         |
| `sign(9.5e-11)`                | `1`     | `1`            |

Control: `0.001 > 0` is `True`, `-0.001 >= 0` is `False`.

How it was found: a Tycho sample notebook finds the zeros of the Riemann zeta
function by bisection, with the test `if fa * fm <= 0 { b = m } else { a = m }`.
Near a zero both values are about 1e-5, their product is under 1e-10, the test
is true on the wrong side, and the first zero came out as 14.1347127 instead of
14.1347251. The program has no error and no diagnostic; the wrong digits are
visible only to a reader who knows the answer. The notebook now compares
`sign(fa)` and `sign(fm)`.

## The case for a change

The rule is deliberate: `ComputeEngine.tolerance` is "the absolute tolerance
of the comparisons that involve a float" (`src/api.md`). It suits `==`, where
`0.1 + 0.2 == 0.3` must be true. For the order operators it costs more than it
gives:

1. **It depends on the units.** An absolute 1e-10 is large next to many real
   quantities: the charge of an electron (1.6e-19 C), Planck's constant
   (6.6e-34), a wavelength in metres (5e-7 is fine, 5e-11 is not). In a
   physics notebook every one of them is "not greater than 0".
2. **It breaks precision loops.** `while err > 1e-12 { … }` stops as soon as
   `err` is under about 1e-10: the requested precision is not reached, and no
   message says so. Any threshold under the tolerance cannot be written.
3. **It disagrees with `sign`.** `sign(x) == 1` and `x > 0` give different
   answers for the same `x`. A reader who knows one cannot predict the other.
4. **It breaks the usual algorithms.** Bisection, Newton with a stop test,
   the sort comparator `(a, b) => a < b` (a tolerant order is not transitive),
   `max` written by hand. These are the programs that notebooks hold.
5. **Other languages compare exactly.** Python, JavaScript and Julia order
   floats exactly; Mathematica's tolerance is relative (the last seven binary
   digits) and applies to `Equal`. An author who comes from any of them writes
   these tests without a second thought.

The cost of an exact order is small for the author: two floats that "should"
be equal are tested with `==` or `abs(a - b) < eps`, which Epsil already has.

## Options

- (a) **Recommended.** `Less`, `LessEqual`, `Greater`, `GreaterEqual` on two
  values of which one is a float compare exactly in Epsil and in `evaluate()`.
  `Equal` keeps the tolerance. Internal checks that need a tolerant order
  (simplification, solve, `.is()`) keep their own `tolerance` argument. A
  migration note lists the change. Size M: the comparison handlers and the
  internal callers that rely on the operators.
- (b) Make the tolerance relative to the size of the operands, for all
  comparisons. `1e-11 > 1e-12` is then true, but `x > 0` for a tiny `x` stays
  undecided by design, which keeps witness 1–3.
- (c) Keep the rule, and add a warning diagnostic when a float literal under
  the tolerance appears in an order comparison, plus a line in the Epsil card
  ("Watch Out For"). This catches `err > 1e-12`, not `fa * fm <= 0`.

Tycho needs no change for (a) or (b): its notebooks will give the exact answer.

## Decision

User decision 2026-11-20: tolerance should only apply to chop, is and numerical algorithms

## CE answer

CE (2026-11-20): implemented as the user decided (see Decision): the six
comparison operators and the comparison methods have no tolerance;
`ce.tolerance` is read by `Chop`, `ApproxEqual`, `.is()` and the numeric
algorithms. `9.5e-11 <= 0` is `False`, `1e-11 > 1e-12` and `1e-300 > 0` are
`True`. Not committed yet. Tycho needs no change; the notebook's
`sign(fa)`/`sign(fm)` workaround can go back to `fa * fm <= 0`.
