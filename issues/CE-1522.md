A Tycho user sees errors for code that is merely unfinished while they type it, such as a string not yet closed.

## Witness

Tycho delays the display of a diagnostic on the line being typed. To keep
real errors visible at once, it needs to know which diagnostics only mean
"the input ended too soon". The instrument prints every field of the
diagnostics of six sources beyond the documented ones. Against 0.193.0 there
is no such flag. The range cannot replace it: `closing-bracket-expected`
points at the opening bracket, and `let a = 1 +\nlet b = 2` reports
`unexpected-symbol` "b" at [16,17]. (An undocumented `origin.offset` is
present; Tycho does not rely on it.)

## Cause and options

Request: a flag on the diagnostic (for example `incomplete: true`), set by
the parser when it reached the end of the input before the construct was
complete. Workaround: Tycho treats `string-literal-closing-delimiter-expected`,
`closing-bracket-expected`, `expression-expected`, and `unexpected-symbol`
whose range ends at the end of the source, as "maybe incomplete"
(ce-debugger, 2026-11-19). Size S.

## CE answer

CE (2026-11-19): P3 confirmed, pool. Workaround as stated: the code list and
the end-of-source test.

CE (2026-11-20): fixed. A diagnostic of `parseEpsil()` (and so of
`executeEpsil()`) has `incomplete: true` when the parser reached the end of
the input before the construct was complete (`"abc`, `f(1`, `let a = 1 +`,
`if x`, `let x: list<`). `let a = 1 +\nlet b = 2` does not have it: the input
continues after the construct. Neither does an error that more text cannot
remove (`1 )`, `let a = *`). Test: `test/epsil/incomplete-diagnostics.test.ts`.
