Reading a field of a value whose type is declared as another named type
gives the wrapped value instead of the field, with no error.

## Witness

```
type Circle = tuple<r: number>
type Wrapped = Circle
const w: Wrapped = Wrapped(Circle(2))
w.r + 1
```

On main (0.197.1 plus `59a569caf`), `checkEpsil` gives no diagnostic, so
`w.r` is accepted as a field read, and `executeEpsil` gives `1 + Circle(2)`.
With `const c: Circle = Circle(2)`, `c.r` gives `2`. `Wrapped(2)` is refused
(`expected Circle, got 2`), so `Wrapped(Circle(2))` is the constructor form.
Expected: either `w.r` reads through to `2` (and the program gives `3`), or
the checker refuses `w.r` because `Wrapped` has no field `r`.

## Cause and options

Not investigated. The static view lets the field layout of `Circle` show
through the nominal `Wrapped` (completion's CE-1663 code lists `r` for `w.`
for the same reason), while the run-time `Field` reads the first element of
`Wrapped(…)`, which is the whole `Circle`. The fix chooses one rule for both
sides: (a) a nominal type over a nominal type exposes the inner type's fields
(read through both layers at run time), or (b) it exposes none (the checker
refuses `w.r`, and completion lists nothing for `w.`). The rule for a nominal
type over a record or tuple layout is in `docs/TYPE-SYSTEM.md` (nominal
types); check it before choosing.

Impact: `major` if the read is an error the user sees later, `critical` if a
host computes with the unevaluated `1 + Circle(2)` as a number; set
`needs-review` for that choice.
