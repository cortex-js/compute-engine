With the experimental compiler profile `'ir'`, a function called with a list where the engine applies it to each element can be applied to the whole list instead, and gives another result with no error.

## Witness

On `c0e55ae7fbb878ed9e1f3215bd1a1d3185f753a4`, with
`compile(e, { profile: 'ir', fallback: false })`:

```ts
// A. a name declared `function`, a parameter typed as a point
const ce = new ComputeEngine();
ce.declare('g', 'function');
ce.assign('g', ce.box(['Function', ['Add', ['At', 'p', 1], ['At', 'p', 2]],
  ['Typed', 'p', "'tuple<real, real>'"]]));
ce.declare('B', 'list<tuple<real, real>>');
// g(B) at B = [(1, 2), (3, 4)]
//   interpreter [3, 7]; existing compiler [3, 7]; profile ir [4, 6]

// B. a point parameter and an untyped parameter
const ce2 = new ComputeEngine();
ce2.assign('k', ce2.box(['Function', 42,
  ['Typed', 'p', "'tuple<number, number>'"], 'x']));
// k(Tuple(1, 2), List(3, 4))
//   interpreter [42, 42]; existing compiler [42, 42]; profile ir 42
```

In A the profile reads `p` as the whole list (`At(B, 1) + At(B, 2)` is the
sum of the first two points); in B it binds the list to `x`. The tests that
hold both are `ce-448-point-function-tensor-argument.test.ts` ("a user
function declared `function`, argument …, maps over the points") and
`compile-list-argument-specialization.test.ts` ("a declared point parameter
maps a list at an untyped parameter"); they fail when the profile is tried
first (`CE_JS_PROFILE_PUBLIC=ir`).

The witness is `plausible`: a function of a point applied to a list of
points is what Tycho's requests CE-412 to CE-448 were about. No program of
Tycho's corpus dump shows a value difference (the replay compares every
compiled program with the existing compiler at six points).

## Cause and options

Not confirmed. In `compilation/ir/lower-functions.ts` an argument is mapped
only when the parameter is a scalar by the profile's reading of the
signature and the function maps (`fn.maps`); a tuple argument is checked
against a tuple parameter. In A the annotation of the parameter of a
function declared with the bare type `function` seems not to be read, so
the parameter takes the argument's shape; in B the untyped parameter takes
the list whole, where the interpreter's rule (`literalParamsMap()`,
user decision of 2026-10-24) maps.

- (a) Decline in the profile when the interpreter maps the function over an
  argument that the profile would bind whole: the simple, sound version.
  Recommended first.
- (b) Map as the interpreter does (a build of calls, as for a list argument
  of a function of scalars), where the shapes are settled.
