A formula that contains the same inner selection six times computes it six times.

## Witness

The body of Tycho document `s8ishknvhe` holds the same inner `Which` six times
(Tycho expands the document functions `S`, `f` and `N` in place). One inner
`Which` costs 130–190 ms at 500 points. With it evaluated once and bound to a
symbol, the body takes 0.2–0.3 s instead of 0.9–1.2 s.

## Cause and options

Share the value of identical sub-expressions within one `evaluate()`, keyed
by `expr.digest` (CE-536 option (a)). Calling `S`,
`f`, `N` by reference instead of expanding them is not value-safe: a named
function with an untyped parameter maps over a list argument
(`g(L) = L - mean(L)` gives `[0, 0, 0, 0]` by reference and
`[-1.5, -0.5, 0.5, 1.5]` expanded). A symbol assigned an unevaluated
expression is evaluated at each read, by definition.

Tycho half on adoption: remove `sharedSubexpressionPlan`.

## CE answer

CE (2026-11-07): fixed for the next release after 0.182.0. In one
`evaluate()`, a copy of a sub-expression (same operators, numbers and
symbols bound to the same definitions) reads the value of the first copy:
six copies cost two evaluations. A copy that holds a local scope (`Block`,
`Function`, `Sum`, `Map` with a lambda), a call of a user function or an
impure operator is still computed at each place. Measured on a `Which` over
500 numbers copied nine times: about 170 ms before, about 80 ms after.
Verify with the instrument; then remove `sharedSubexpressionPlan` and delete
this file.

CE (2026-11-07), on the Tycho reading below: the reading is correct, and
it reproduces on a plain engine at commit
`acf5a9183437fa0eb3337ccacec4793384b36f48`: the body of `C_cf` evaluates
its inner `Which` 13 times. The body holds 6 copies of a large `Which`, each with
one copy of a small `Which`, under one outer `Which`. With full sharing it
costs 5 evaluations. Two causes stop the sharing:

- **(a) The options of a handler.** `Which` evaluates its arms with the
  options object it received as a handler. That object always holds
  `engine`, `expression` and `effects`, so `memoizableEvaluateOptions()`
  (`shared-evaluation-memo.ts`) refuses it, and no node under the arm is read
  from the memo or kept in it. `evaluate()` does not read these fields, and
  the memo entry already compares the precision and the effects of the
  engine, so the test can ignore `engine`, `expression`, `precision` and
  `effects`. Witness: `Which(PointX(C_c) > 0, Tuple(Abs(W), Abs(W),
  Abs(W)), True, 0)` evaluates `W` 3 times; with `Add` in place of `Tuple`,
  2 times. Fix: about 3 lines.
- **(b) The narrowing of a parameter of a new function literal.** An
  element-wise operator over a list whose elements are `number` (`Abs`,
  `Power`, `Real` over a copy of `W`) builds a function literal for its lazy
  `Map` (`lazyBroadcastMap()`, `collection-utils.ts`). Boxing its body
  narrows the parameter `_1` from `number` to `complex | infinity`. This
  inference, and the deferred `inference-settled` event that follows it,
  advance the evaluation version (`noteStateEvent()`,
  `engine-configuration-lifecycle.ts`). The memo then drops every entry
  kept before, and the node that built the literal is not kept, because the
  persistent version moved during its evaluation. The parameter lives in the
  literal's own scope, which no frame below reads. The declaration of the
  same parameter already advances no version (the `parameter` flag of the
  `declare` event). Fix: an inference that narrows such a parameter, and the
  `inference-settled` event, do not advance the evaluation version (the
  inference event that widens or narrows any other binding still does, at
  the write). Open point for the design: an entry kept in the frame that is
  pushed to box the literal's body, and that read the type of the parameter
  before the narrowing, must be dropped. Fix: about 20 lines and tests.

Measured on a prototype of both fixes (source build, one process, median of
7 runs; 0.183.0 is the release build, so compare the ratios, not the times):

| Build                | Evaluations of `Which` | Expanded / shared |
| -------------------- | ---------------------- | ----------------- |
| 0.183.0              | 13                     | 2.64              |
| (a) only             | 9                      | 2.29              |
| (a) and (b)          | 5                      | 1.34              |

The materialized value of the body is the same on 0.183.0 and on the
prototype, and the 146 tests of six memo and inference test files pass on
it. A ratio of 1.34 is still above the 1.25 of Tycho's READY test: the
remaining cost is the lazy `Map` nodes that each copy builds again. Tycho
keeps `sharedSubexpressionPlan` until a release with the fix reads READY.

## Tycho reading on 0.183.0 (2026-11-07, not verified)

The new instrument measures the form that Tycho's `sharedSubexpressionPlan`
protects (the earlier one copied a call of a host operator that is not
`pure`, which CE computes at each place by design):
`CE-882: NOT READY on 0.183.0 (Which evaluated 13 times for 13 copies of 3
structure(s); expanded 165 ms vs shared 104 ms, ratio 1.58; …)`. Six
standalone copies of the inner `Which` are shared, and so are copies of a
numeric `Which` (2 evaluations for 6). In the witness the copies sit under

costs 6 evaluations where `Add(Abs(W), Abs(W), Abs(W))` costs 4. Tycho keeps
`sharedSubexpressionPlan`.
