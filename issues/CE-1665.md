A code cell with `$\sqrt5$` shows the error "Latex parsing unavailable" on
that line and its run fails, although the engine of the cell parses LaTeX.

## Witness

On 0.197.1, with `ce = new ComputeEngine()` (the full entry, so
`ce.latexSyntax` is defined) and the program

```
const b = $\sqrt5$
const c = $\frac{1}{2}$ + 1
b^2 + c
```

- `checkEpsil(ce, source)` gives `latex-parsing-unavailable` twice.
- `executeEpsil(ce, source)` gives the same two errors and two
  `runtime-error`s; the value is `c + b^2`.
- Positive control: with `{ parseLatex: (l) => ce.latexSyntax.parse(l) }`,
  both give no diagnostic and the value is `13/2`.

`epsilDebugStatements`, `epsilCompletions` and `epsilSignatureHelp` take no
`parseLatex` option, so a host cannot give them the parser.

## Cause and options

The Epsil functions that take an engine read islands only with an injected
`parseLatex`; they do not fall back to `ce.latexSyntax`.

Requested:

1. When `parseLatex` is absent and `ce.latexSyntax` is defined, the functions
   that take `ce` (`checkEpsil`, `executeEpsil`, `executeEpsilAsync`,
   `epsilDebugStatements`, `epsilCompletions`, `epsilSignatureHelp`) read
   islands with `ce.latexSyntax.parse`. `latex-parsing-unavailable` then
   means "this engine has no LaTeX syntax", which is what its text says.
2. If (1) is not wanted: a `parseLatex` option on `epsilDebugStatements`,
   `epsilCompletions` and `epsilSignatureHelp`, as on the others.

Tycho's workaround on 0.197.1: it passes `parseLatex` to `parseEpsil`,
`checkEpsil` and `executeEpsil(Async)`. A cell with an island still has no
completions or debug statement sites read through its islands.

Tycho half on adoption: with option (1), remove the `latexIslands` option in
`src/graph-paper/notebook/ce-notebook-evaluator.ts` and
`src/plot-core/prelude-runner.ts`; keep `EPSIL_LATEX_ISLANDS`
(`src/graph-paper/notebook/epsil-latex-islands.ts`), which the calls of
`parseEpsil` without an engine use, unless `parseEpsil` also falls back to a
LaTeX parser by itself.
