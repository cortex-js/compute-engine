A piecewise formula whose condition compares a variable with a word, such as `m = \text{cubic}`, always takes that branch, whatever the value of the variable.

## Witness

```latex
\begin{cases} x^3 & m = \text{cubic} \\ x & \text{otherwise} \end{cases}
```

With `m` declared `string`, this parses as
`["Which", ["Equal", "m"], ["Power", "x", 3], "True", "x"]`: the string
operand of the condition is gone. The raw parse (`form: 'raw'`) gives the same
tree, so the operand is lost in the parser, not in canonicalization. With
`x = 2` and `m = "lin"`, the formula evaluates to `8` and not `2`. A
one-operand `Equal` is true. The compilers decline it ("Equal with 1
operands"). `\text{if } m = \text{cubic}` and `(m = \text{cubic})` give the
same tree. Outside `cases`, `m = \text{cubic}` parses as
`["Equal", "m", "'cubic'"]`. In a `cases` condition, `m = 1` and
`m = \mathrm{cubic}` keep their right operand.

## Cause and options

Not investigated. A likely place is the handling of `\text{…}` in a `cases`
row (`definitions-core.ts`, `CASES_ENVIRONMENTS`): a text run in the condition
column is read as an annotation (`\text{if}`, `\text{otherwise}`) and dropped,
also when it is an operand of a relation. Whatever the fix, a relation must
not lose an operand silently. An `Equal` with one operand should be a parse
error, not `True`.

## Hosts

Tycho, ROADMAP row NL (`requirements/todo/VARIABLE_CONTROLS.md`, a draft spec,
not approved, 2026-11-20): in a notebook, a control's value is the string
itself, bound as `ce.box({str})`. A notebook equation cell with a `cases`
condition on such a variable needs this fix. An Epsil code cell does not
(`if m == "cubic"` gives the right values). Plot documents keep a number, so no
string reaches GLSL or interval-js. Not flagged `blocker` while the spec is a
draft.
