Writing a sum, a quotient or a sine of a list whose length is computed from another list computes that other list five times before anything is evaluated, so a document that builds the list by a long recursion freezes when the expression is created.

## Witness

Corpus state `art/s8ishknvhe` with Tycho's rewrite of row MK: `C_c = F(0)`,
with `F` a recursion that joins one point per level and `D = 10000` levels.
Tycho reports that boxing

```json
["Divide", 1, ["Map", ["Function", ["Block", ["At", ["PointX", "C_c"], "j"]], "j"],
  ["Range", 1, ["Length", ["PointX", "C_c"]], 1]]]
```

throws `RangeError: Maximum call stack size exceeded`. The `RangeError` did
not reproduce in node (three attempts: the default `ce.iterationLimit`,
`ce.iterationLimit = 1e6`, machine precision with `ce.recursionLimit = 1e5`).
What reproduces is the evaluation of `C_c` inside `ce.box()`, measured on the
working tree of main at `3b0b23f414e90ada33e633cb641cd9a8fb3c8ef6` with `F`
of the dump `t12-javascript-glsl-document-definitions.json`, `C_c` declared
with the value `F(0)` and `ce.iterationLimit = 1e6`:

| `D` | `C_c.evaluate()` | `ce.box(Divide(1, Map(…)))` | `ce.box(Divide(1, PointX(C_c)))` |
| --- | --- | --- | --- |
| 200 | 260 ms | 899 ms | under 1 ms |
| 400 | 360 ms | 1,611 ms | under 1 ms |
| 800 | 719 ms | 3,312 ms | under 1 ms |
| 10,000 | 5.6 s | 36.4 s | 0.8 ms |

The smallest program, with an operator that counts its evaluations:

```ts
const ce = new ComputeEngine();
let calls = 0;
ce.declare('Spy', { signature: '(list<number>) -> list<number>',
  evaluate: (ops) => { calls++; return ops[0].evaluate(); } });
ce.declare('C', { type: 'list<number>', value: ce.box(['Spy', ['List', 7, 8, 9]]) });
ce.box(['Add', 1, ['Range', 1, ['Length', 'C']]]);   // calls === 5
ce.box(['Sin', ['Map', ['Function', ['At', 'C', 'j'], 'j'], ['Range', 1, ['Length', 'C'], 1]]]); // 10 more
ce.box(['Range', 1, ['Length', 'C']]);               // 0 more
ce.box(['Less', 2, ['Range', 1, ['Length', 'C']]]);  // 0 more
ce.box(['Add', 1, 'C']);                             // 0 more
```

`Add`, `Multiply`, `Negate` and `Divide` evaluate `C` five times, `Sin` ten
times. A `Map` whose source is a list expression (`Divide(1, Map(f,
PointX(C)))`) evaluates `C` two times in `ce.box()`.

## Cause and options

The canonical form of a numeric operator asks whether each operand is a
finite list that can be walked (`inferNumericArgs()` in
`boxed-expression/validate.ts`, through `isFiniteIndexedCollection()`). For a
`Range`, the `count` and `isEnumerable` handlers read the bounds with
`operandNumericValue()` (`library/collections.ts`), which calls `.N()` on a
bound that is not a number literal and has no unknown. `Length(C)` has no
unknown, so `C` is evaluated: twice in `hasSymbolicRangeBounds()`, once in
`range()`, once in `rangeElementCount()` and once more for `isEnumerable`.
Nothing keeps the value between these reads. A `Map` over that `Range` reads
the same facets of its source (`mapSource()`).

The documentation allows a count read to evaluate
(`docs/COLLECTIONS-MODEL.md`, "The shape of an unevaluated application": the
count of a lazy view over an eager source evaluates that source). So this is
a cost, not a wrong result. Two things are not as documented: the comment of
`isWalkableFiniteCollection()` (`collection-utils.ts`) says the predicate
"never evaluates", and `inferNumericArgs()` skips a lazy operand (`if
(x.isLazyCollection) continue`) only after it has paid for the test.

Options, none chosen:

- (a) `inferNumericArgs()` tests `isLazyCollection` first and does not ask a
  lazy operand whether it is finite. It must keep the inference that the
  `else` branch makes for a lazy operand of unknown length. Size S; removes
  the evaluation for arithmetic, not for other readers of the count.
- (b) The `Range` handlers read each bound once per facet read and keep the
  value for the other facets of the same state of the engine. Five
  evaluations become one. Size M.
- (c) A `Range` bound that is not a number literal or an exact constant
  (`50π`) is not evaluated by a facet read: the count is unknown until the
  `Range` is evaluated. `Range(1, Length(L))` then has no count before
  evaluation, which changes what `staticShape` and the display preview
  answer for it. Size M, changes a documented answer.

## CE answer

CE (`ce-compiler`, 2026-11-16): P3 (a slow case with a workaround). Disposition:
backlog. The `RangeError` that Tycho saw is not reproduced; if Tycho can give
the stack, add it here: an error thrown by a facet read during `ce.box()`
would be a defect of its own.

Workaround, on 0.192.0: write the selection as an eager list, so that the
operand of the arithmetic is not a lazy view. `ce.box(['Divide', 1,
['ListFrom', ['Map', …]]])` takes 5 ms at `D = 400` (1,611 ms without
`ListFrom`) and evaluates nothing. With the lists as sources of the `Map`
(`ListFrom(Map(xj ↦ xj, PointX(C_c)))`, see CE-1358 and CE-1365), box and
evaluate together take 423 ms at `D = 400`, against 404 ms for
`Divide(1, PointX(C_c))`. The form of row MK, evaluated, takes 81.9 s at
`D = 400`, because the callback evaluates `PointX(C_c)` at each index
(CE-1358).
