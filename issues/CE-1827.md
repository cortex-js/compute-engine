A `for` loop whose variable has the name of a variable used in its range does not run, and gives no error.

## Witness

On main `39ffe2d9a71016554c924475f29f82ed35a66538`, with `executeEpsil()` on
a new engine:

```
let n = 3
let s = 0
for n in 1..n { s += n }
s
```

gives `0`. With the loop variable renamed (`for j in 1..n { s += j }`) it
gives `6`. In the same way, `[n for n in 1..n]` stays the unevaluated
`Comprehension(n, Element(n, Range(1, n, 1)))`, where `[j for j in 1..n]`
gives `[1, 2, 3]`. A big operator reads the outer variable:
`sum(n, n in 1..n)` gives `6`.

The witness is `crafted`: a user rarely gives the loop variable the name of
its own bound.

## Cause and options

The interpreter resolves the name in the collection of the `for` clause to
the loop variable, which has no value there. The editor's scope walk
(`documentBindings()`, `src/epsil/occurrences.ts`, the `hidden` range of a
`for` binding) reads the collection outside the loop, so a rename and the
hover name the outer variable at that site, and `resolveLibraryNames()`
treats a library spelling there as free. `epsilProgramSites()` follows the
interpreter (the `engineRules` option of the walk, and the test "the
collection of a `for` clause is read in the scope of the loop" of
`test/epsil/program-sites.test.ts`); option (a) changes both.

Option (a), recommended: the interpreter canonicalizes the collection of a
`Loop` and of a `Comprehension` clause in the scope around the loop, as the
big operators do. Option (b): the loop gives an error value and a diagnostic
(`read-before-declaration`) for a collection that names its own variable,
and the scope walk resolves the site to the loop variable.
