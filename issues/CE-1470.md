A sum whose terms are lists, such as a count per element of a list, is computed by the interpreter instead of compiled code, so the plot is slower.

## Witness

From Tycho documents (the records named above), target `javascript`:

```
Sum(Which(Equal(C, At(U, i)), i, True, 0), Limits(i, 1, 20))
Sum(Which(Equal(Range(1, u), At(A, j)), 1, True, 0), Limits(j, 1, N))
Sum(2 Mod(10000 Sin(10000 (X + i)), 1) - 1, Limits(i, 1, 40))
```

with `C`, `U`, `A`, `X` declared `list<nan | real | signed_infinity>`. The
term of each sum is a list (a `Which` of a list condition, or an operation
of the list `X`), and the interpreter adds the lists element by element:
the CE-1464 implementer's probe gave `[3, 2, 1]` for the first form. On CE
main with the CE-1464 change, the `Which` of each term compiles alone, and
the sum declines because `Sum` takes a scalar term ("a list where a scalar
is required"). Whether 0.193.0 compiled these forms is not checked.

## Cause and options

`Sum` (and `Product`) in the IR lower a scalar term only. Option: a term of
a settled list shape (the length of the first list it reads, as the
element-wise operations of lists settle it) accumulates element by element,
with the decline of lists of two stated lengths that differ. Workaround: the
interpreter route (fallback), as today.
