A recursive Epsil function written with `match` gives an error instead of its value, and a function written with `match` has a wrong static type.

## Witness

```
function fac(n) { match n { == 0 => n + 1; _ => n * fac(n - 1) } }
fac(3)
  → Error(incompatible-type, number, nothing) at Multiply      expected: 6

function half(s: string, t: real) { match s { == "a" => t / 2; _ => 0 } }
  the signature is (s: string, t: real) -> integer;  half("a", 3) is 3/2
```

## Cause and options

The `type` handler of `Match` (`library/control-structures.ts`) joins the
types of the case bodies with `widen()`. The bodies are held raw, so a body
that is not a literal has the type `unknown`, and `widen()` drops it: the
`Match` of `half` is typed by its literal case `0` alone, `integer`. When no
body is a literal (`fac`), the `Match` is `unknown`, the inferred result of the
function is `unknown`, and a call of it is typed `nothing`
(`boxed-function.ts`, the type of an application); `n * fac(n - 1)` is then an
`incompatible-type` error.

- (a) Join with `joinUnresolvedArm()` (an `unknown` body keeps the `Match`
  `unknown`), and make a call of a function whose inferred result is
  `unknown` have the type `unknown`, not `nothing`. The first change alone
  turns `match n { == 0 => 1; _ => n * fac(n - 1) }` (which works today,
  `match-dispatch.test.ts`, "recursive results are not stale") into the
  error of the witness, so both are needed together.
- (b) Type each case body in the scope of its case (the function literal of
  `buildCaseClosure()`), as the interpreter makes it canonical, and join
  those types.

The compiler does not read these types: a function whose inferred result
comes from a body that holds a `Match` takes its result from the lowered
body, and `MatchesType` of a subject whose type comes from a `Match`
declines (`typedByMatch()`, `compilation/ir/lower-match.ts`, CE-1652 step 1).
Remove both when this is fixed.
