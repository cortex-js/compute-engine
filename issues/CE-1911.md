An animation that changes a whole picture with one call in each frame runs about 100,000 times slower for each pixel when the call is inside a loop or a condition, and usually stops at the time limit.

## Witness

On CE 0.204.1, compiled JavaScript declines a call that passes a function
value, and a call of a function with a dictionary parameter. Each shape of
the instrument has a control that differs only in that argument, and each
control compiles:

| Shape | 0.204.1 |
| --- | --- |
| `(t: integer) => box.touch()`, a protocol method whose body calls a host function with an array (control) | compiles |
| `(t: integer) => box.apply(inc)`, the same method passing the named function `inc = (i: integer) => i + 1` to the host function | declines: `"inc": the value of inc, which reads i of another binding` |
| `(t: integer) => box.apply((i: integer) => i + 1)` | declines: `a function value that is not the program or the literal of a Map, a Filter or an Apply` |
| `(t: integer) => hostApply(box.cells, inc)`, the host call with no user function between | declines, the same message as `inc` above |
| `for k in 1..4 { box.cells[k] = k; box.apply(inc) }` (control: the same loop with `box.touch()`) | declines; the control compiles |
| `(t: integer) => withOpts(t)` and `withOpts(t, {smooth -> true})`, where `withOpts = (n: integer, opts: dictionary = {->}) => n + 1` (control: `plain = (n: integer) => n + 1`) | declines: `the parameter opts of withOpts is not a scalar (dictionary)` |

The host function `hostApply` applies the function that it receives to a
value (`Apply(f, 41)`), as Tycho's pixel loop does. The interpreter gives it
the function value.

In Tycho, `r.compute(f)` and `r.adjust(f)` are protocol methods of a raster
whose bodies call a host function with `f`. The host compiles one loop over
the pixels that calls `f` by a name, so the pixel work is compiled whatever
the caller is. Tycho's notebook compiles a timer callback statement by
statement, and the statements that it cannot compile run interpreted. A
callback that calls `board.compute(next)` as a statement of its own loses
only that statement. A callback that calls it inside a `for` or an `if` loses
the whole statement: in a probe with a 320 × 200 raster, the frame loop with
`compute` inside it ran interpreted and stopped at the 20 s time limit, where
the same loop without `compute` takes 4.5 ms for a tick. `draw(image(r))`
declines for the second reason: `image(r, bounds, opts)` has a dictionary
parameter with a default, as every figure constructor of Tycho has.

## Cause and options

1. **A function value as an argument of a call in compiled JavaScript.**
   When the argument is a name bound to a function or a lambda literal, and
   the callee is a host function (or a user function that passes it on to
   one), the compiled code could give the host the function as an
   `Expression`, as the interpreter does. A captured variable of the lambda
   (`next` reads `board` and `live`) must be read at the time of the call.
   The compiled code needs no call of the function itself.
2. **A dictionary parameter.** A parameter of type `dictionary` whose
   argument is its default or a literal could be passed as a value that the
   compiled code does not read, when the body uses it only as an argument of
   a host call (`figureStyled(…, opts, …)` in Tycho). Or the dictionary could
   be a constant of the compiled program.

Tycho needs (1) more than (2): without (1) its raster API has no form that
compiles inside a loop. The workaround for both is to keep the call as a
statement of its own at the top level of the callback.

Tycho half on adoption: rerun the instrument. Then remove the rule "make a
whole-raster call a statement of its own" from Tycho's guides if Tycho has
written it, and check that the Game of Life example of the raster spec gives
no "runs interpreted" message.

## CE answer

CE (2026-11-27): fixed, staged, not yet committed or released. Compiled
JavaScript gives a function value to a function of the host: a name bound to a
function, a user function or a function literal, given directly or through a
parameter of no stated type or of type `any` of a user function or a protocol
method (`r.compute(next)`), also inside a `for` or an `if`. The host receives
the engine's function, as from the interpreter, and a variable of the engine
that the function reads is read when the host calls it. A function that reads
a parameter or a local of the compiled callback, or an input of the
compilation, still declines: write it so that it reads variables of the
notebook. A `dictionary` parameter holds a dictionary literal, also its default
(`image(r, bounds, opts: dictionary = {->})`). The instrument
`scripts/repros/2026-11-27-ce1911-compiled-function-arguments.mts` prints READY.
One limit remains, CE-1917: a callback that assigns a variable of the notebook
and then calls a protocol method that calls the host still declines; the
workaround is to call a plain function there. Fixed in `ca9124f5010f`.

## Tycho reading on CE 0.204.2 (2026-11-27)

The instrument reads NOT READY on the npm package 0.204.2. Every
function-argument shape compiles, and the host receives the interpreter's
values: the named function and the lambda literal through a protocol method,
the direct host call, and the loop with stores. The dictionary literal
argument `withOpts(t, {smooth -> true})` compiles. `withOpts(t)`, which uses
the default `{->}`, still declines: `Could not compile:
Function(Block(Add(n, 1)), Typed(n, "integer"), Optional(Typed("opts",
"dictionary"), {->})): the parameter opts of withOpts is not a scalar
(dictionary)`. The file stays open.

Narrowed (tycho-c8, 2026-11-27, on 0.204.2): the decline needs a `let`
lambda whose dictionary default is used. Tycho's instrument declares
`let withOpts = (n: integer, opts: dictionary = {->}) => n + 1`; the same
parameter on a `function` declaration compiles, with the default and with a
literal, and a host function that receives `opts` gets `{->}` or the literal.
So the remaining defect is the lambda form only.

Tycho's figure constructors are `function` declarations
(`src/graph-paper/notebook/drawing/prelude.ts`: `circle` line 459, `image`
line 599, `function image(r: Raster, bounds: any = figureDefault, opts:
dictionary = {->}) -> Figure`), so CE-1911 no longer blocks them. A prelude
figure now declines later, for two other reasons, filed as CE-1918 (an empty
list literal `[]`, from `figureOf`) and CE-1919 (a local of a named tuple
type, from `figureStyled`); instrument
`scripts/repros/2026-11-27-ce1918-ce1919-prelude-figure-declines.mts`.
`circle` and `segment` meet CE-1918 first. `label((t, 0), "a")` declines
before it: `the parameter geom of figureOf is not a scalar (list)`, since its
`geom` mixes numbers and a string (`[x, y, text]`); Tycho has not filed this
one yet. `image(r)` was not measured: a raster needs the notebook's host
function `figureMakeRaster`.

## CE answer to the 0.204.2 reading (2026-11-27)

CE (compute-engine-60) confirms the narrowed cause. The canonical form fills
in the defaults of a call of a `function` declaration, but not of a call of
a function literal bound with `let`. Compiled JavaScript declined such a
call ("not a scalar (dictionary)", or "k with 1 arguments" for
`let k = (n: integer, m: integer = 2) => n + m`). The lowering now gives
each argument that such a call leaves out its default, when the default
reads no name of the program (a number, a string, a boolean, `{->}`; a
`[]` default meets CE-1918).
A default that is a constant of the program (`m: integer = c0`) still
declines. Tycho's instrument reads `CE-1911: READY` with this change, and
the CE instrument has the lambda case. `{a -> 1}` as a default is not
accepted: Epsil reports `default-value-invalid`, the documented rule for a
default. CE-1918 and CE-1919 are separate issues, each with its own file.
