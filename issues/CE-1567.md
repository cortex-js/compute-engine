A sum of lists from 0 to the length of a list is computed point by point instead of by compiled code, so it draws slower.

## Witness

`L: list<real>`. Compile to javascript:
`Sum(Multiply(k, L), Limits(k, 0, Length(L)))`.

0.194.3: declines, "a term that is a list, over a range that can be empty,
where the interpreter gives a number". The range `0..Length(L)` always holds
`k = 0`, because `Length` is never negative. 0.186.0 compiled `[3, 6]` for
`L = [1, 2]`, the interpreter's value. Control: `Limits(k, 0, 4)` compiles. The
rule that declines `Limits(k, 1, Length(L))` (CE-1470, R3) is not in question.

Found by the Tycho codegen audit of 2026-11-19: the same MathJSON, with the same options, compiled to JavaScript on CE 0.186.0 and declines on 0.194.3 and on the CE main build of 2026-11-19 16:57, in the document context and on a bare engine. Tycho's instrument `scripts/repros/2026-11-19-ce1560-js-decline-regressions.mts` prints one READY / NOT READY line per issue (READY on 0.186.0, NOT READY on 0.194.3).

## Cause and options

The emptiness test does not use the sign of the upper bound. Option: a range
whose lower bound is 0 and whose upper bound is a `Length` (or another
non-negative integer) is never empty.
