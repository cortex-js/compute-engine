In the interpreter, each write of an element of a long list in a loop still costs a time in proportion to the length of the list: 2000 writes to a list of 20 000 elements take 2.5 seconds.

## Witness

With the fix of CE-1796, `executeEpsil()` on a new engine with no time limit,
measured in the process (the start of the process is not counted):

```
let fb: list<integer> = [0 for k in 1..20000]
for k in 1..2000 { fb[k] = k % 256 }
fb[2000]
```

| List length | Writes | Result | Elapsed |
| ----------- | ------ | ------ | ------- |
| 5 000       | 2 000  | `208`  | 1.1 s   |
| 20 000      | 2 000  | `208`  | 2.5 s   |
| 64 000      | 2 000  | `208`  | 6.6 s   |
| 64 000      | 20 000 | `32`   | 88 s    |

The values are correct. The same program compiled gives the value with no
measurable run time, so a host that compiles the program has a workaround.

`plausible`: a sieve, a histogram or a grid of cells filled by a loop is such a
program.

## Cause and options

`fb[k] = v` is `Assign(fb, ReplaceAt(fb, k, v))`. For a list of more than 100
elements, the value that the variable holds is a chain of at most 32 lazy
`ReplaceAt` views over a `List` (`eagerElementsOf()` in
`library/collections.ts`). A CPU profile of the witness (20 000 elements, 2000
writes, 2.6 s in the loop) shows that each read of the variable walks the whole
stored value, the list included:

- `rewriteWithBinders()` from `ownBindingEnvironment()` and
  `evaluateInOwnBindings()` (`boxed-expression/binders.ts`), from the read of
  the symbol (`_dereference()` in `boxed-symbol.ts`): 0.95 s.
- `readsActivatedName()` from `recordLazyViewContext()`
  (`boxed-expression/lazy-view-context.ts`): 0.57 s. It keeps only a `true`
  answer, so a view that reads no such name is walked at each read.
- `hasConstantValue()` (`boxed-function.ts`): 0.2 s.

Option A: each of these walks keeps its answer for a node that holds no symbol
and no scope (a `List` of numbers), as `namesIn()` in `library/core.ts` does
for `readsVariable()`; the fact does not change, so the answer stays correct.

Option B: the interpreter owns the array of a list variable, and a write whose
variable holds the only reference to the list changes the array in place, as
the JavaScript target does for a block local (`docs/COMPILATION-MODEL.md`,
"List updates"). This removes the views and the copy of the list at each 32
writes, and it needs a rule for when a second name holds the list.
