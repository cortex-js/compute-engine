Compiling an expression that reuses one subexpression in both branches of nested conditions takes many seconds.

## Witness

At `29ee7c0f7aa216b3c5bf05b125393ef6b4a5828c`, JavaScript target, default
options. `e_0 = Sin(x)`, `e_k = If(x > k, e_(k-1) + 1, 2·e_(k-1))`, with the
same node object `e_(k-1)` in both branches:

| Depth | Default options | `cse: false` |
| --- | --- | --- |
| 10 | 0.17 s | 0.06 s |
| 12 | 1.9 s | 0.19 s |
| 14 | 41.5 s | 0.6 s |

The emitted code has the same size in both columns (606,206 characters at
depth 14), so the time of the first column is spent before the emission. The
measure is in the table of
`docs/plans/2026-11-11-structured-shared-subexpressions.md`.

A second cost in the same family, before any compiler: with
`ce.angularUnit = 'deg'`, `rewriteAngularUnit()` rebuilds the changed nodes
in canonical form, which flattens a sum that shares its operands:
`e_k = Add(e_(k-1), e_(k-1))` over `Sin(x)` has 65,536 operands at depth 16.

## Cause and options

Not investigated beyond the measure. The time grows 12 to 21 times per two
levels with CSE on and about 3 times with it off, so the search for repeated
subexpressions (`compile-cse.ts`) visits a shared node once per path, or more.
Option: a memo per node object in that search. The witness is `crafted`: no
document with such a shape is known.
