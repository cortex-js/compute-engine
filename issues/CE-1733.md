A colour formula that reads a document value such as `k = \max(y_w, 0.01)` through a function cannot be drawn on the GPU when the host sends `k` as a `real` uniform, while the same value read directly, or a value typed `real`, can.

## Witness

CE 0.200.1, a prepared Document (`createDocumentEnvironment`, `imports.prepare`)
with the inputs `x`, `y`, `x_w`, `y_w` (`real`) and the rows `k` and
`X(x, y) = k x / y`. Each compile is
`compile(expr, { to: "glsl", vars: { x: "x", y: "y", k: "u_k" }, inputs: { k: "real" } })`
in the revision's scope.

- `k = \max(y_w, 0.01)` (inferred type `real<0.01..>`), expression `X(x, y)`:
  declines, "the name "k" of the `inputs` option has no declared type, so its
  value cannot be left out".
- Controls: `k = 2 x_w` (inferred `real`), `X(x, y)`: compiles and reads
  `u_k` (CE-1706). `k = \max(y_w, 0.01)`, expression `k x` (direct read):
  compiles. `k = \max(y_w, 0.01)`, `X(x, y)`, `inputs: { k: "real<0.01..>" }`:
  compiles.

Tycho's workaround: a compile input for a published row gets the row's
inferred type when it is a subtype of `real` (`publishedRowRealType` in
`src/plot-core/ce-module-registry.ts`). Tycho half on adoption: remove
`publishedRowRealType` and its call in `withByReferenceScope`, and run
`heatmap-formula-gpu.spec.ts` (the `cie-chromaticity` case) on the GPU.

## Cause and options

The CE-1706 path that accepts a formula row as an input when a function body
reads it seems to require the input type to equal the row's inferred type,
while the direct read accepts the wider `real`. Related: CE-1706 (the read
through a function body, fixed for a row typed `real`) and CE-1707 (closed:
the interpreter fallback of the same `inputs` path). Option: accept an input type
that contains the inferred type (a `real` input for a `real<0.01..>` row), as
the direct read does.
