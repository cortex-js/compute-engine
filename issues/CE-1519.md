A Tycho user who types in an Epsil code cell reads messages such as "type-annotation-error: Expected a type", with the engine's code in them.

## Witness

Tycho shows the diagnostics of `parseEpsil` and `checkEpsil` in its Epsil
editor (the notebook code cell and the plot prelude). It receives
`ParsingDiagnostic.message` as a `[code, ...args]` tuple and has no public
way to turn it into the text that the CLI, the MCP `check` tool and the VS
Code server show. The instrument prints, for four sources, the tuple Tycho
receives and the text of an exported formatter when there is one; against
0.193.0 it prints `exported formatter: none`.

## Cause and options

The formatter exists: `diagnosticToJson(d, source)` in `src/cli/format.ts`
returns a readable `message` (CE session ce-debugger, 2026-11-19). It is not
exported from `@cortex-js/compute-engine/epsil` (`src/epsil.ts`).

Request: export a function that returns the display text of a diagnostic
without the code prefix. For `type-annotation-error` the current text itself
starts with "type annotation error: "; that prefix should not appear either.
Localization is not asked for now. Workaround: Tycho formats the tuple
itself (it drops the code and shows the arguments). Size S.

Tycho half on adoption: map the diagnostics of the notebook code cell
through the exported function, and remove Tycho's own formatting of the
message tuple.

## CE answer

CE (2026-11-19): P3 confirmed, pool. The change is an export from
`src/epsil.ts` of a function that returns the text of `diagnosticMessage()`
(`src/cli/format.ts`) without the code, the `type-annotation-error` prefix
included. Workaround as stated: Tycho formats the tuple itself.

Fixed (CE, 2026-11-19): `epsilDiagnosticMessage(diagnostic)` is exported from
`@cortex-js/compute-engine/epsil`. For `let x: notatype = 1` it gives
`Unknown type "notatype"`; the CLI, the MCP server and the VS Code extension
show the same text.
