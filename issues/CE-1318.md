Compiled code for a function that adds the first and second element of its argument, applied to a list of points, throws when it runs; the interpreter gives the sum of the two points.

## Witness

Run on main at `3927b6c89ac284a5088a752718937455ac3c8a23` and on the build of
rule 7, same output.

```js
ce.declare('L', 'list<tuple<real, real>>');
const e = ce.box(['Apply',
  ['Function', ['Add', ['At', 'v', 1], ['At', 'v', 2]], 'v'], 'L']);
const r = compile(e, { to: 'javascript' });
r.success;   // true
r.code;      // (((v) => _SYS.atNumeric(v, 1, "number") + _SYS.atNumeric(v, 2, "number")))(_.L)
r.run({ L: [[1, 2], [3, 4]] });
// throws: Could not compile `At`: the element read is a list at run time,
// but its static element type is `number` …
e.evaluate();   // (4, 6), with L assigned [(1, 2), (3, 4)]
```

The same function assigned to a name (`h := v ↦ v[1] + v[2]`, `h(L)`)
compiles to a copy made for the list type and gives `[4, 6]`.

## Cause and options

The literal applied in place is inlined with the parameter read as the point
that its index reads infer (`tuple<number, number>`), so each `At` is
compiled as a read of a number, and the run-time guard of `atNumeric`
refuses the row it gets. The argument is a list of points, which the
parameter takes whole. Options: compile the inlined literal for the type of
its argument, as the assigned route does (`trySpecializedUserCall`,
`compilation/compile-user-functions.ts`), or decline at compile time when
the argument is a list whose elements are not numbers at such a parameter
(the decline that the assigned route has since rule 7, point 2).

Workaround: assign the function to a name, or write the parameter type.
