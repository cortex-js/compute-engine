The GPU animation needs a private board because author code could otherwise read or overwrite an earlier generation.

Tycho half on adoption: rerun the instrument. The texture backend marks a
raster stale after each GPU generation, with a fetch that reads the texture
back. Then `rasterTimer` (`figureRasterTimer` in
`src/graph-paper/notebook/ce-notebook-evaluator.ts`) no longer needs its
private copy of the seed raster, and author code can read the board between
generations.

## Witness

Tycho's Life timer uploads a seed once and alternates two GPU textures.
When another Epsil callback reads or edits the board, it needs the latest
generation. The witness simulates a device publication with a separate
byte buffer on installed CE 0.202.0. An interpreted read through an alias
and a precompiled JavaScript reader with an array parameter both return
the old value, 10. Both return 30 after the host copies the device bytes
into `board.cells` and calls `noteStore()`. The generated reader loads
`a0._cells` directly. This is a design limitation with separate storage,
consistent with CE's current one-storage contract.

## Requested contract

Give a host a public way to associate synchronization with a mutable
array's identity and invalidate cached computations when external storage
publishes a new version. Before CPU code observes or partially overwrites
the cells, let the host materialize the latest bytes into the same array.
Cover interpreted reads and stores, public host access to cells, aliases
and record fields, and compiled JavaScript access. If a compiled function
calls back into the host and that call can publish new device data, cover
the first subsequent access too.

Prefer a guard at an access boundary or a compiled entry when sufficient.
An access that sees an already-current CPU copy should trigger no copy.
Ordinary CPU arrays should retain their current fast path, and successive
GPU generations should need no readback. A host-managed storage contract
or a bulk synchronization boundary with explicit compiler support could
meet these requirements. Tycho owns WebGL and the transfer in either case.

Acceptance: after a device update, read the new first cell through an
interpreted alias and a precompiled reader. Then write one cell from the
CPU and check that the other cell retains the device value. Neither the
alias nor the compiled reader needs rebuilding. Keep an ordinary array as
the no-hook control. CE-1892 covers compiling author-facing reads to GLSL.

## Decision

User decision 2026-11-27: a host marks an array stale with a fetch function,
and the engine runs the fetch once, at the next access of the cells. Not
taken: a test at each cell access in compiled code, which costs the fast
path of every array.

The contract that the fix implements:

- **The host interface.** `array.markStale(fetch)` records that the cells
  are out of date, increments `version` and registers the state event (so a
  cached computation that read the array is invalid, as after a store).
  `array.stale` is `true` until the fetch runs. A second `markStale` before
  the fetch replaces the pending fetch.
- **The fetch.** At the next access of the cells, the engine clears the mark
  and calls `fetch(array)` once. The fetch writes the latest bytes into
  `array.cells`, or gives new storage with `swapCells()`; it does not
  increment `version` again. A `swapCells()` while the array is stale clears
  the mark without calling the fetch: the host gave the cells.
- **The access points.** In the interpreter, every read, store, exchange
  (`swap`), `listFrom`, a slice and the serialization of the cells; on the
  host side, the `cells` getter. In compiled JavaScript, each array that the
  code reads or stores (a parameter, a name of `arrays`, an array held by a
  captured value) is synchronized when `run()` starts and after each call of
  a function of the host, which are the points where the code already reads
  its arrays again. No test runs inside a loop.
- **The limit.** A `markStale()` from code that runs while compiled code is
  between two of those points (another thread, a timer) is unspecified.
- **The fast path.** An array that was never marked pays one field test at
  an interpreted access and one at each synchronization point of compiled
  code.
- Acceptance is the one stated above: after a device update, an
  interpreted alias and a precompiled reader read the new first cell; a CPU
  store of one cell keeps the device value of the other; neither is rebuilt;
  an ordinary array is the control.

## Fix

`array.markStale(fetch)` and `array.stale`, as in the decision, with these
rules that the implementation settled:

- The engine keeps the set of its stale arrays. Compiled code checks it when
  `run()` starts, after each host call and after each construction of an
  array; when it is empty, that check is the whole cost. It fetches each
  stale array that it can reach: a parameter, a name of `arrays`, an
  assigned name, an array that a captured value holds, an array the call
  made, and an array that an assigned name gives after a host call. A stale
  array that the code cannot reach is not read back.
- A fetch that throws leaves the array stale. `markStale()` on an array of
  expression cells throws a `TypeError`. A `noteStore()` or `swapCells()`
  inside the fetch adds no version. `swap(a, b)` fetches both arrays first.
