A debugger command that stops a program is ignored when the program is stopped inside the function of a `map` that a list literal spreads.

## Witness

```ts
import { setDebugStatementHook } from 'src/common/debug-hook';
const stop = new Error('debugger: stop');
setDebugStatementHook((statement) => {
  if (statement.operator === 'Declare' && String(statement.json).includes('w'))
    throw stop;
});
executeEpsil(ce, 'let ys = [5, 6]\n[...map(v => do { let w = v; w }, ys), 9]\n7');
// returns the value 7; the hook threw once
```

The hook throws at `let w = v`, which is how a debugger unwinds the
evaluation (the VS Code debugger throws its `TerminatedError` from this
hook). The run must end with that exception, as it does when the same `map`
is the value of the program (`let ys = [5, 6]` then
`map(v => do { let w = v; w }, ys)` throws `stop` to the host since
CE-1601).

## Cause and options

`snapshotListJoin()` (`src/compute-engine/library/collections.ts`, the
`catch` after the walk of the spread operands) throws again only a
`CancellationError` that is not an iteration limit. For every other
exception it returns `undefined`, which keeps the lazy view, so the
exception of a debugger hook (`isDebugHookFailure()`,
`src/common/debug-hook.ts`) is discarded and the evaluation continues. The
statement loop of the engine never turns such an exception into a result
(`evaluateStatements()`, `src/compute-engine/function-utils.ts`).

Fix: add `if (isDebugHookFailure(e)) throw e;` to that `catch`, as
`listedElement()` (`boxed-expression/listed-element.ts`) has since CE-1601,
with a test that runs the witness. Size S. Search the other `catch` blocks
of `collections.ts` that keep a view after a walk for the same case.
