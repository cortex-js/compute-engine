The numeric value of the exact remainder of `Mod` by an irrational divisor loses every digit when the dividend is large: `evaluate()` gives the exact form `a - k·√2`, and `.N()` of that form cancels at the working precision, which gives a number far outside `[0, √2)`. `.N()` of the `Mod` itself gives the right value.

## Witness

At `154153fe307c9084587b86fb0f9dc364c040cc8c`, on a fresh engine (precision 21):

```ts
const ce = new ComputeEngine();
const e = ce.box(['Mod', { num: '81129638414606663681390495662081' }, ['Sqrt', 2]]);
e.evaluate().toString();
// 81129638414606663681390495662081 - 57367317478180994538678159693372sqrt(2)  (exact, correct)
e.evaluate().N().toString();   // 9500000000                (expected 1.05464095093706286692…)
e.N().toString();              // 1.05464095093706286692    (correct)
```

The dividend is `(2^53 − 1)^2`. The same value comes from
`ce.box(['Mod', ['Multiply', 'n', 'n'], ['Sqrt', 2]]).subs({ n: 9007199254740991 }).evaluate().N()`
with `n` declared `integer`: the route of the slice's oracle and of a host that
substitutes and then evaluates. The expected value was computed with 80-digit
decimals (Python `decimal`): `a − ⌊a/√2⌋·√2 = 1.0546409509370628669…`, and
`⌊a/√2⌋ = 57367317478180994538678159693372`, the coefficient of the exact form.

## Impact

A wrong finite value with no error, for an input of its declared type. The
result is outside the range of `Mod` (the sign of the divisor, smaller than the
divisor in magnitude), so a program that relies on the range (an index, an
angle reduced to a period) gets a value of 10^10. The witness is crafted: the
dividend has 32 digits, more than the working precision.

## Notes

The cause is the numeric evaluation of a difference of two terms of about
8·10^31 at 21 digits, not the remainder: `.N()` of the `Mod` node takes another
route that is right. A fix can give `evaluate()` of `Mod` a numeric value when
the exact quotient has more digits than the working precision, or make `.N()`
of such a difference raise its precision. The round 2 report of the slice named
`Mod(Mod(1e300, e), e)` for this defect; at this base that program gives
1.2507130926793243528, in range.

## A fix that was undone

Commit `dc584a240b0a99e6e0a7e6e67c582973586bfcc1` (CE-1311) made `.N()` of an
`Add` of exact real operands whose sum lost 3 or more digits compute the sum
again at a raised precision. It fixed this witness, but it changed values that
six tests pin, and it was undone before the release that followed 0.189.0:
`Floor(s).N()` of a sum near 5·10⁹ became `5000000000` where the exact floor is
`4999999999` (`round-tie-rule.test.ts`), the float of
`1/(√(10⁴⁰ + 1) − 10²⁰)` became finite where `~oo` is documented
(`rounding-complex-infinity.test.ts`), `N(x, p)` with a precision goal for 0
took 10 working precisions instead of 3 (`core.test.ts`), and three tests
(`exact-ordering-ties.test.ts`, `false-exact-values.test.ts`) pin values
that are now more accurate. Doing it again changes the documented behavior of
`.N()`, so it needs a user decision.

## Decision

User decision 2026-11-14: do it again, corrected. `.N()` of an `Add` of exact
real operands whose sum lost digits computes the sum again at a raised
precision, with two changes to `dc584a240b0a99e6e0a7e6e67c582973586bfcc1`:
(1) `Floor`, `Ceil`, `Round`, `Truncate`, `Mod` and the other operators whose
result jumps keep using the exact operand, so `Floor(s).N()` of the sum of
`round-tie-rule.test.ts` stays `4999999999` at machine precision; (2) when the
sum still cancels at the raised precision, the precision is not raised again
(the value is 0 or the working-precision result), so the precision-goal test of
`core.test.ts` keeps its 3 evaluations. The four tests that pin a value which
lost digits are changed to the correct value: cos(10⁻²⁰) − 1 and
cos(10⁻⁷⁰) − 1 in `exact-ordering-ties.test.ts`, 2√(1+10⁻³⁰) − 2 in
`false-exact-values.test.ts`, and the `~oo` float in
`rounding-complex-infinity.test.ts` (with its comment). When this lands, remove
the guard of CE-1311 in `library/calculus.ts` (the arm that reads
`unstableClosedForms` and keeps a definite integral above degree 8 inert), so
`evaluate()` gives the exact closed form again and `.N()` of it is correct, and
check `∫₀²⁰ x¹⁰⁰·e⁻ˣ dx` under `.N()` (6.4321579720555e120). Run the full
`npm test` before the commit.
