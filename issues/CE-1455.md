Expanding a stored formula inside a function uses the function's argument in place of a variable of the same name in the formula.

## Witness

MathJSON, evaluated in order:

```
["Assign", "y", ["Sin", "x"]]
["Assign", "f", ["Function", ["Expand", "y"], "x"]]
["f", 2]                      → ["Sin", 2]   (expected ["Sin", "x"])
```

The `x` of `y`'s formula is the global `x`, not the parameter of `f`. The
same function with `["Add", "y", 0]` or `["Simplify", "y"]` as its body gives
`["Sin", "x"]`. `TrigExpand` and `TrigToExp` give `Sin(2)` the same way, and a
`Block` that declares a local `x` does too: with `x := 1` assigned after
`y := Sin(x)`, `Block(Declare(x, integer), Assign(x, 2), TrigToExp(y))` gives
the exponential form of `Sin(2)`, while `Block(…, y)` gives `Sin(1)`.

`Expand` has done this for a long time. `TrigExpand`, `TrigReduce` and
`TrigToExp` do it since CE-1410 (`662e243cbf83e20823c1be843e586eef1cadf56c`,
not released), which gave them the same operand reduction as `Expand`.

## Cause and options

`resolveBoundSymbols()` (`src/compute-engine/boxed-expression/utils.ts`),
called by `reduceTransformerOperand()`, replaces a symbol by its value and
then resolves the symbols of that value by name with
`expr.engine.lookupDefinition(name)`, in the scope where the transformer is
evaluated. A symbol of a stored value must be read with the binding it had
where the value was stored (docs/SCOPING-MODEL.md), not with the scope of
the caller.

Options: (a) resolve each symbol of a stored value through the binding of
that symbol occurrence, keeping the binder shielding the function has now;
(b) stop resolving symbols inside a stored value (resolve one level only),
which no longer expands a value that names another symbol that holds a
value. Option (a) is in
the binding area, which is paused (see the post mortem
`docs/plans/2026-11-15-binding-workstream-post-mortem.md`); it waits for the
user's decision on that workstream.
