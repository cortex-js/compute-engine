A compiled loop that adds to list elements runs about 3 times slower than the same JavaScript written by hand, because each update calls two checking helpers.

## Witness

```
let L = H
for k in 1..n {
  const c = 1 + floor(1000 * fract(0.618034 * k))
  L = replaceAt(L, c, L[c] + 1)
  L = replaceAt(L, 1001 - c, L[1001 - c] + 1)
}
L
```

Each update compiles to `_SYS.replaceAtInPlace(L === _tv1 ? L : (_tv1 =
_SYS.ownedCopy(L)), c, _SYS.atNumeric(L, c, "number") + 1)`. On 0.182.0,
`n = 1000000`: 10.4 ms, against 3.0 ms with `L[c - 1] += 1`; same list.
Tycho's Buddhabrot step (2 to 6 updates per point): 1.40 → 0.72 ms with
direct writes; direct reads alone: 1.04 ms.

## Cause and options

Likely: the rest parameter of `replaceAtInPlace` (an array per call) and
`listPosition` per write. Option: for one update of a local that the loop
owns, emit `L[i - 1] = v` after an inline index check (or none when the
index is proved in range); keep the helper for several updates.

Tycho half on adoption: run Tycho's Buddhabrot probe of 2026-11-07 that
times the generated step against WASM (generated-vs-wasm), and record the
new times in section 8.7 of the Buddhabrot code study and in ROADMAP row IB.

## Fix

The main cause was not the write helper. The `_SYS` bundle of each compiled
function got its own helpers by `Object.assign`, which put it in V8
dictionary mode, so each `_SYS.name` read was a hash lookup. The bundle is
now one object literal with `SYS_HELPERS` as its prototype, and
`replaceAtInPlace` writes one update at an index in `1..length` of a plain
array with no other work. The emitted code does not change. The witness
(`n = 1000000`, Node 26): 15.0 ms before, 3.5 ms after; the hand-written
loop takes 1.1 to 1.6 ms.

## Tycho reading on CE 0.184.0 (2026-11-08): not verified

The instrument reads `NOT READY: the checked update costs more than 30 %`
twice: rounds 1.32, 1.33, 1.42 (two agents running, load about 3), then 1.31,
1.42, 1.41 (load 3.1 on 18 cores; generated 3.45 to 3.72 ms against direct
2.62 to 2.64 ms for n = 1,000,000). The Buddhabrot step that 0.184.0
generates (`2026-11-07-buddhabrot-codegen-dump.mts`, timed by
`2026-11-07-buddhabrot-generated-vs-wasm-probe.mjs` in one loop with the
0.182.0 dump) takes 1.33 to 1.45 ms per firing against 1.40 to 1.53 ms for
0.182.0, about 5 % faster; it still has 7 checked writes
(`replaceAtInPlace`, `ownedCopy`, `atNumeric`) and 3 `countLoopPass`, and
WASM scalar is about 4.1 times faster than it.

## Decision

User decision 2026-11-08: Let's investigate the cause of the slowdown and consider options. If the option is simple, implement it. Otherwise, return with options and recommendations.

## Fix 2 (2026-11-08)

The remaining cost was the ownership test at each update. A local declared with a value, whose other writes are
in-place updates, one in a loop, is now copied at its declaration
(`let L = _SYS.ownedCopy(_.H)`), and each update is
`L = _SYS.replaceAtInPlace(L, c, ...)` (`ownedFromDeclaration()` in
`compile-blocks.ts`). The instrument, with its pattern changed to this form,
reads `READY`: 1.23 to 1.25 (1.32 to 1.44 before).

Tycho half: the instrument's pattern matches only the old form, so it
prints `READY` untimed. Change it to
`L = _SYS.replaceAtInPlace(L, X, _SYS.atNumeric(L, X, "number") + 1)`, and
the direct form's `let L = _SYS.ownedCopy(_.H);` to `let L = _.H.slice();`.
