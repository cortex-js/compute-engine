In a notebook code cell, `c.rotate(` on a figure shows no help, or shows a
signature without its description, and `rotate(c, ` shows parameters of
unknown type.

## Witness

Tycho's drawing prelude (`src/graph-paper/notebook/drawing/prelude.ts`,
version 23) declares `protocol Drawable` with a `///` comment on each member
and its parameter types, and `type Figure = tuple<…> is Drawable { … }`. The
prelude runs with `executeEpsil` on the engine that answers the editor; the
editor calls get the cell's text and the options `typeNames: ["Figure",
"PlotView"]`, `protocolNames: ["Drawable"]`. On CE 0.200.1 (instrument,
part B):

```
B unannotated c.rotate(: none
B annotated c.rotate(: rotate(self: Figure, angle: real, about: any = figureDefault) -> Figure; documentation null
B rotate(c, : rotate(self: any, angle: any, about: any = ProtocolDefault) any -> unknown; documentation "Protocol member `rotate` (`Drawable`); dispatches on the runtime type of its fir"
B hover Drawable: null
```

The control holds: with `let c: Figure = …`, signature help and member
completion (`c.st` offers `stroke`, `strokeWidth`) work.

Expected:
(a) the receiver's type comes from the result type of an engine function:
`let c = circle(…)` (`circle` returns `Figure`) gives the same help as the
annotated `let`; also a call receiver, `circle(…).rotate(` (signature today,
no documentation);
(b) the signature help, completion and hover of a member give the `///`
comment of the member of a protocol that the engine defines;
(c) `rotate(c, ` gives the member's declared signature (`angle: real`,
`about: any = figureDefault`) and its comment, not the dispatcher's;
(d) hover on `Drawable` gives the protocol and its comment.

## Cause and options

Per compute-engine-85 (2026-11-23, main `1cb549e1f`): hover and signature help
read the documentation of protocols of the source only, and the receiver type
of an unannotated `let` comes from the source only (the constructor of a
nominal type of the source, `receiverTypeOf`). Related: CE-1729 (completion
of engine definitions).

## CE answer

CE (2026-11-23): P2 confirmed (the table value for `confidence`, `high`).
Disposition: pool, for the board, after CE-1729 (the same reading of the
engine's definitions). For (c), the help of `rotate(c, ` can choose the
member's implementation by the static type of the first argument, as the
compile-time dispatch of CE-1652 (plan section 4.5) does: one edge whose
target is a supertype of that type; otherwise it shows the protocol member's
declared signature, never the dispatcher's. Workaround until then: with the
options `typeNames` and `protocolNames`, which Tycho now passes, an annotated
receiver (`let c: Figure = …`) gets the signature and member completion; the
`///` comments and an unannotated receiver have no workaround.

## Fix

CE (2026-11-23, `46750e54169fba18f90ff3373411a7367882a681`): the parser
carries the `///` comments of a `protocol` and of its members in an optional
fourth operand of `DeclareProtocol`, and the engine keeps them in the protocol
record (a host passes `description` and `memberDescriptions` to
`ce.declareProtocol()`). `epsilHover` on a protocol gives its comment; the
signature help and the completion of a member give the member's comment.
`rotate(c, ` shows the member's declared signature, `Self` read as the static
type of the first argument, not the dispatcher's. `let c = circle(…)` has the
declared result type of the engine function, so `c.rotate(` needs no
annotation. On the instrument, part B: READY. Tycho can drop the annotation
workaround once it adopts the release.
