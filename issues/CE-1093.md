A program that adds up many independent samples runs on one core, because Epsil cannot say that its passes are independent.

## Witness

Tycho's `buddhabrot` step (`src/graph-paper/onboarding/template-data.js`)
is a sequential loop:

```
for k in 1..n { … L = replaceAt(L, c, L[c] + 1) … }
```

The passes are independent, and the additions can happen in any order. A
compiler cannot easily prove that (CE-1075 asks it for `wgsl`). A form whose
meaning is already parallel could compile to a JavaScript loop, a split
over workers (sum of arrays), or a compute shader with `atomicAdd`.

## Options

```
(a) a function: accumulate(L, 1..n, k => cells(k)) adds 1 at each index
    of cells(k); or (index, amount) pairs
(b) a statement: parallel for k in 1..n { L[c] += 1 }, only += on one list
(c) prove independence of an ordinary loop (CE-1075)
```

Data: GPU in Tycho `roadmap/BUDDHABROT_CODE_STUDY.md` § 7; workers § 8
(in progress).

## Decision

User decision 2026-11-07: option (b), the statement `parallel for`, with the
parallel comprehension clause `[f(k) parallel for k in 1..n]` and `+=` in all
code. No parallel copies of library functions and no `||>`. The design is
`docs/plans/2026-11-07-ce1093-parallel-for.md`; this issue is its step 1
(language, interpreter, JavaScript target).

## CE answer

CE (2026-11-07): step 1 is in `a3cc0d7fc`. Write the buddhabrot step with
`parallel for k in 1..n { … }` and `L[c] += 1` in place of
`L = replaceAt(L, c, L[c] + 1)`; the interpreter and the compiled JavaScript
give the same counts as the `for` form (test "the buddhabrot step" in
`test/epsil/parallel-for.test.ts`). The passes still run in order on the CPU.
The GPU compute shader is CE-1075 (step 2 of
`docs/plans/2026-11-07-ce1093-parallel-for.md`); it will need the list
declared `list<integer>`.
