A dependency list omits the outer variable that a same-named block local reads in its initializer.

## Witness

```js
const ce = new ComputeEngine();
ce.declare('d', 'real');
ce.declare('n', 'real');
ce.assign('d', 10);
ce.assign('n', 2);
const json = [
  'Block',
  ['Declare', 'd', "'unknown'", ['Add', 'd', 'n']],
  ['Multiply', 'd', 2],
];
ce.box(json, { form: 'raw' }).references; // ['n'], expected ['d', 'n']
const expr = ce.box(json);
expr.references; // ['n'], expected ['d', 'n']
expr.evaluate().json; // 24, using outer d = 10
```

Verified on `bef64cf00`. The same expression gives 24 under `N()` and
compiled JavaScript with inputs `{d: 10, n: 2}`. The public dependency API
promises the in-edges even after their values are assigned. The omission
can leave a consumer's invalidation graph without the edge from `d`.
Tycho's lexical collector already includes it for this initialized-block
shape, so its current path has a workaround.

## Cause and options

The reference walk filters explicit Block locals across all statements.
Its declaration target and an initializer read of the outer binding
have the same spelling. Account for the initializer's binding when
filtering reads. Keep the existing availability rule for later
declarations and the body. Check both raw and canonical expressions.

A grouped function initializer has the same omission in canonical form.
With an outer `f(m) = m + 10`, the block
`Block(Declare(f, "unknown", Delimiter(Function(f(m), m))), f(2))`
evaluates to 12. Both raw and canonical `.references` return `[]` on
`2752e60e9`. The canonicalizer binds the grouped body under the outer
name, then removes the delimiter. A later walk cannot recover that
choice from the final head `Function` alone.
