A function that passes a list computed from its own arguments to a second function gets back a list whose sum, length and elements stay unevaluated, although the elements can be listed one by one.

## Witness

Working tree of main at `3b0b23f414e90ada33e633cb641cd9a8fb3c8ef6`:

```ts
const ce = new ComputeEngine();
// clean(l) := Map(i ↦ l[i], Range(1, Length(l)))
ce.assign('clean', ce.box(['Function',
  ['Map', ['Function', ['At', 'l', 'i'], 'i'], ['Range', 1, ['Length', 'l']]], 'l']));
// R(p, q) := clean([p[k] + q for k in 1..Length(p)])
ce.assign('R', ce.box(['Function',
  ['clean', ['Comprehension', ['Add', ['At', 'p', 'k'], 'q'],
    ['Element', 'k', ['Range', 1, ['Length', 'p']]]]], 'p', 'q']));
const call = ['R', ['List', 10, 20, 30], 1];

ce.box(['ListFrom', call]).evaluate().json; // ["ListFrom", ["Map", …"p"…"q"…]], expected [11, 21, 31]
ce.box(['Sum', call]).evaluate().json;      // ["Sum", ["R", ["List", 10, 20, 30], 1]], expected 63
ce.box(['Length', call]).evaluate().json;   // ["Length", ["Map", …]], expected 3
ce.box(['At', call, 2]).evaluate().json;    // ["At", ["Map", …], 2], expected 21

const v = ce.box(call).evaluate();
[...v.each()].map((x) => x.json);           // [11, 21, 31]
v.count;                                    // undefined
v.unknowns;                                 // ["p", "q"]
ce.box(['ListFrom', call]).N().json;        // ["List", 11, 21, 31]
```

The neighbouring forms give `[11, 21, 31]`, 63, 3 and 21:

- the argument listed first, `R(p, q) := clean(ListFrom([…]))`;
- the callee lists its result, `clean(l) := ListFrom(Map(…))`;
- an argument that is not a lazy list, `R(p, q) := clean(p + q)`;
- no second function, the comprehension written in the `Map` of `R`.

With a bound that is a number (`clean(l) := Map(i ↦ l[i], Range(1, 3))`) or
with `clean(l) := Take(l, Length(l))`, the count is 3, `ListFrom` gives
`[11, 21, 31]` and `Sum` gives 63.

Corpus: `neyret/nqfechxzqp`, `R(l, r) = c_lean([… for i = [1...length(l)·(length(r)−1)]])`
with `c_lean(l) = l[l = l]`. With `c_lean` a named function whose body is the
mask of the dump (`Map(i ↦ At(l, i), Filter(Range(1, Length(l)), i ↦ At(l, i)
≤ At(l, i)))`), `R` with the parameters `ceArg_1` and `ceArg_2`, and
`D = R(L, [p_op, p_op, n_ull])`: `ListFrom(D)` and `Length(D)` stay
unevaluated and name `ceArg_1` and `ceArg_2`, `Length(D).N()` is 7 and
`[...D.evaluate().each()]` has the 7 elements. With `c_lean` applied in place
(Tycho's inlined program 0 of the dump), every read gives the value.

Tycho saw, in node, with the mask of row MK: "Filter predicate must return
True or False. Unknown symbols: ceArg_2, ceArg_1". That message did not
reproduce (three forms of the mask, typed and untyped parameters, named and
in-place `c_lean`, both precisions); the names it reports are the two that
stay in the value here.

## Cause and options

As far as read:

- The value of `R(…)` is the `Map` that the call of `clean` made. It still
  names the parameters `p` and `q` of `R`: the comprehension is a lazy list
  that keeps the activation it was made in (`docs/SCOPING-MODEL.md`, "Callable
  resolution"), and the end of a call leaves alone the nodes that another
  call made (`bindingKeyedSubs()`, `function-utils.ts`). A read through the
  view (`each()`, `at()`) runs in that activation and finds the values.
- The count does not. The bound of `Range(1, Length(l))` is read by
  `operandNumericValue()` (`library/collections.ts`), which answers `NaN`
  for a bound that has unknowns, tested by name (`op.unknowns.length > 0`),
  without the activation. The `Range` then has no count, the `Map` no count
  and no known finiteness, and `ListFrom`, `Sum`, `Length` and `At` do not
  walk a list that is not known to be finite.
- The JSON of the value names `p` and `q`, which mean nothing outside the
  call: boxed again from its JSON, the value lists no element (measured on
  the corpus form).

Options, none chosen:

- (a) The facet readers of `Range` (and the other views that read a bound)
  read the bound in the activation that the view recorded, and call a name
  unknown only when it has no value there. Size M.
- (b) At the end of the call of `R`, the parameters that `R` does not write
  are replaced by their arguments also in the nodes that an inner call made
  from an argument of `R`. Size M; the rule that keeps the nodes of other
  calls exists for closures that write a parameter, and must keep working.
- (c) An eager reader that finds no count walks a view that records an
  activation, up to `ce.iterationLimit`. Size S; a view of an endless source
  would be walked to the limit before the reader gives up.

## CE answer

CE (`ce-compiler`, 2026-11-16): P3 (no value where one is expected, with a
workaround). Disposition: backlog. It is a defect of the interpreter, not of
Tycho's rewrite: the form of the dump shows it too when `c_lean` is called
by name.

Workaround, on 0.192.0: list the lazy argument before the call
(`clean(ListFrom([…]))`), or list the result in the callee
(`ListFrom(Map(…))`); both give the values above. Tycho's inlining of
`c_lean` at the call site also avoids it.

## CE progress (2026-11-19)

Reproduced on main 367c1236e: `ListFrom(R([10,20,30], 1))`, `Sum(R(…))`,
`Length(…)` and `At(…, 2)` stay unevaluated; `[...v.each()]` gives
`[11, 21, 31]` while `v.count` is `undefined` and `v.unknowns` is
`["p","q"]`. The lazy `Comprehension` keeps the activation of `R`'s call,
and the end of the call does not substitute into nodes another call made
(`bindingKeyedSubs()`, `src/compute-engine/function-utils.ts`); the count
reader `operandNumericValue()` (`library/collections.ts`) treats a name with
an activation as unknown. Options (a) and (b) change how activations are read
or how a call ends, the binding area; (c) walks an endless source to the
iteration limit. Recommended: (a).

## Decision

User decision 2026-11-19: (a)

## Decision

2026-11-19, the user: (a). Only the readers that ask for a count look at the
activation that the lazy value keeps; the call-end substitution rule does not
change.
