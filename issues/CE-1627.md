A program that declares a type gets an error that says the declaration is not at the top level when the host runs it in a scope of its own.

## Witness

```epsil
type Pt = tuple<x: real, y: real>
let p = Pt(1, 2)
p.x
```

Run with `executeEpsil()` after `ce.pushScope()`, as Tycho runs a notebook
code cell (`ce-notebook-evaluator.ts`, the run after `pushScope`): the value
is right (`1`), and the diagnostics hold `invalid type declaration: Type
declarations must be at the top level of a program, not inside a block or
function body`. The same program at the global scope, and `checkEpsil()` in
the pushed scope, report nothing. A second pushed scope then reads `Pt`
(`Pt(3, 4).x` is `3`, no diagnostic), and `Pt` is still a type name of the
engine after both scopes are popped. That second part is the documented
contract, not a defect: type and protocol declarations are engine-global
(`docs/TYPE-SYSTEM.md`, "Declarations and the global registry"). `protocol`
and `type … is …` statements give the same diagnostic
(`protocol-scope-invalid`).

The Program spec (`docs/plans/2026-11-12-program-operator-spec.md`, section
2, item 2) says that the direct statements of a `Program` are the top level,
and that the test is the position in the form, not which scope is current.

## Cause and options

`notAtTopLevel()` (`src/compute-engine/library/core.ts`) returns false for a
program statement (`isProgramStatement()`), and otherwise compares the
current lexical scope with the global one. The diagnostic shows that the
type statement reaches this test outside the program-statement marker on the
run route (likely the boxing of the statements before the first runs, P2 of
the Program spec; not verified), and the declaration is then made anyway,
in a scope that is not the pushed one.

Whether types should follow scopes is not part of this issue: it would change
the documented contract of the type and protocol registries. Tycho's notebook
proposal (code cells that publish no name) states that a code cell's types and
protocols are engine-global.

## Fix

The diagnostic came from the evaluate handlers of `DeclareType`,
`DeclareSumType`, `DeclareProtocol` and `DeclareConformance`, not from the
boxing: the boxing of a program statement is marked (`withProgramStatement()`),
but the evaluate pass ran `notAtTopLevel()` again without the marker and fell
back to "the current scope is the global scope". `notAtTopLevel()`
(`src/compute-engine/library/core.ts`) now also accepts the evaluation of a
statement by the run driver (`inProgramStatement`) when the current scope is
the scope the program run started in (`UnitEnvironment.startScope`, a new
getter in `src/compute-engine/binding-unit.ts`). A `type` in a block or a
function body still gets the diagnostic. Tests: `test/epsil/declare-type.test.ts`
(direct `type` in a pushed scope; a `type` in a block in a pushed scope),
`test/epsil/protocols.test.ts` (protocol and conformance in a pushed scope).
