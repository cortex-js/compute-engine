A pipe into a `std::` call has no static type, and signature help does not mark its piped parameter when the program has a function of the same name.

## Witness

At `bc7d8f7875aa0d1450f297269b85b8c08689c5e3`:

- `Pipe(xs, Apply(Module(Take), 2))` with `xs: list<integer>` is typed
  `unknown`; `Pipe(xs, Take(2))` is typed `list<integer>`. The value is
  right (`[1, 2]`), so a type error in a later stage of a `std::` chain is
  not reported before the run. The same for `Map` and `Sum`.
- `function take(a, b, c) { a }` then `xs |> std::take(▮`: signature help
  shows the library signatures with the active parameter 0 (`xs`); the run
  puts the piped value in `xs`, so the active parameter is `count`.

Workaround: write the placeholder (`xs |> std::take(_, 2)`).

## Cause and options

CE-1699 taught `pipeStageWithImplicitTopic()` (`library/core.ts`) the stage
`Apply(Module(name), …)`. The type of a pipe comes from
`pipeImplicitTopicCallType()`, which does not know that stage; and
`markPipedTopic()` (`src/epsil/signature-help.ts`) is skipped for a `std::`
call whose name the program binds (the guard
`!(std && context.visible.has(head))`), because `namedCallee()` resolves the
name in the program. The fix: read the `Module` stage in
`pipeImplicitTopicCallType()` as `pipeStageWithImplicitTopic()` does, and
resolve the callee of a `std::` call in the library in `pipedTopicSlots()`.
