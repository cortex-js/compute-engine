A function written in place, with a parameter that takes a whole list, gives a type error for a list at a parameter declared as a number, while the same function given a name maps over that list.

## Witness

At `13b23c071005b1115a2aaf9e71c67ce27bf84cff`:

```js
const D = ['Function', ['Add', ['At', 'p', 1], 'x'], 'p', ['Typed', 'x', "'real'"]];
ce.declare('gd', 'function');
ce.assign('gd', D);
ce.box(['gd', ['List', 1, 2], ['List', 10, 20]]).evaluate().json;
// ["List", 11, 21]
ce.box(['Apply', D, ['List', 1, 2], ['List', 10, 20]]).evaluate().json;
// ["Error", ["ErrorCode", "'incompatible-type'", "'real'", "'vector<integer^2>'"], …]
```

In Epsil, `let f = (p, x: real) => p[1] + x` then `f([1, 2], [10, 20])` is
`[11, 21]`; `((p, x: real) => p[1] + x)([1, 2], [10, 20])` is the error.

Workaround: assign the literal to a name and call it.

## Cause and options

`p` is typed `tuple<number>` by its use `p[1]`, so it binds its argument
whole. The evaluation of `Apply(literal, …)` maps a list beside such a
parameter only at a parameter typed `unknown` (`literalMappedParameters`,
`library/core.ts`), while a named call maps at every scalar parameter beside
it (`pointListParamSlots`). The check of the arguments when the call is boxed
(`validatedLiteralApplicationOperands`, `boxed-expression/box.ts`) follows the
evaluation, so the two agree on the error. The fix: map at a declared scalar
parameter beside a whole-bound one in `applyLiteralMapped`, as the named
route does, and then admit the list in the check of the arguments.
