A function whose body defines a helper with `let` or `=` and calls it is applied to each element of a list argument, and gives errors in place of its value.

## Witness

Checked 2026-11-07 at `61447c29ee222e9ddac51466aebdd21f626b2c22`, Epsil:

```
function f(xs) { let h = (t) => count(t)
h(xs) }
f([1, 2])
  → [Error(incompatible-type, collection, 1, "while applying 'f' element-wise …"),
     Error(incompatible-type, collection, 2, …)]
  expected: 2
```

The type of `f` is `(xs: unknown) -> unknown`. The same error comes with a
chain `let q = (a) => h(a)` then `q(xs)`, and with that chain written
`h = …` and `q = …` in place of `let`. With `function h(t) { count(t) }` in the
body, the value is `2` and the type of `f` is
`(xs: collection<any>) -> integer | signed_infinity`.

## Cause and options

The signature of `f` is derived when `f` is defined, before its body runs.
The call `h(xs)` in the body is bound to the body-local placeholder of `h`,
which has no definition at that time, so `wholeCollectionParameterType()`
(`effects-inference.ts`) finds no evidence that `xs` takes a whole list.
A nested `function` declaration is a definition when the body is boxed,
so it gives that evidence.

Option: when the walk of the body meets a local assigned a function literal
(`Assign(h, t ↦ …)` or the `Declare` of `let h = …`), record the slot types
of that literal, and read them at a later call `h(xs)`, as the walk already
follows a local alias (`let ys = xs`). Workaround: define the helper with
`function`.
