In a function body, a helper declared with `let` that calls another `let` helper is applied to each element of a list argument, and gives errors in place of its value.

## Witness

Checked 2026-11-08 at `86ad36c444f8e6832ceb53573a7664624fd746ca`, Epsil:

```
function f(y) { let h = (t) => count(t)
let q = (a) => h(a)
q([1, 2]) }
f(0)
  → [Error(incompatible-type, collection, 1, "while applying 'q' element-wise …"),
     Error(incompatible-type, collection, 2, …)]
  expected: 2
```

The same program with `h = …` and `q = …` in place of `let` gives `2`. At
the top level of a program, the two `let` statements give `2`.

## Cause and options

The body of `f` is boxed once, when `f` is defined. The call `h(a)` in the
literal of `q` is bound to the body-local placeholder of `h`, which has no
value then. A `let` with a function literal value keeps `q` as a value that
holds that literal, and a call of `q` reads the slots from the type of the
literal. That type is computed in the static view of the bindings
(`withStaticTypingView()`), where the call `h(a)` resolves to the
placeholder, so `wholeCollectionParameterType()`
(`src/compute-engine/boxed-expression/effects-inference.ts`) finds no
evidence that `a` takes a whole list. An `Assign` instead installs an
operator definition for `q` when it runs, and derives its signature then,
when `h` has its definition (`afterFunctionAssignment()`,
`src/compute-engine/function-utils.ts`).

Option: when the canonical handler of `Declare` sees a function literal as
the value of a block local, record the literal on the placeholder of the
local (as it records `_initializerAlias` for a symbol), and let the walk of
`wholeCollectionParameterType()` read the slot of that literal at a call
bound to the placeholder.

Workaround: define the helpers with `function` or with `=`.
