A notebook debugger that follows a cell cannot tell in which cell a statement was written when the cell calls a function of an earlier cell: it gets offsets with no source.

## Witness

```ts
executeEpsil(ce, `let a = 0
let b = 0
function f(t) scope {
  a = a + t
  b = b + 1
}`);
await executeEpsilAsync(ce, 'f(1000)', { debug: { beforeStatement } });
```

`beforeStatement` is called with `range [0,7]`, `callDepth 0` (the statement
`f(1000)` of the run), then with `range [44,53]`, `callDepth 1`: the
statement `a = a + t`, at its offsets in the source of the EARLIER run. In the
source of the run, `'f(1000)'.slice(44, 53)` is `""`. Tycho read the same on
0.195.1 for a timer callback (`t => do { a = a + t; b = b + 1 }`, defined in
one cell, applied by a later run) and for the functions of its drawing
prelude (ranges such as `[37946,37972]`). The instrument prints these calls.

The documentation says something else. `EpsilDebugStatement.range`
(`src/compute-engine/types-debug.ts`): "The offsets of the statement in the
source of the run: the statement is `source.slice(start, end)`".
`EpsilDebugHooks`: "called for each statement written in the source of the
run". `src/epsil/docs/implementation.md`, "Debugging", says the same.

What the host gets wrong today: it highlights `[44,53]` of the cell that
runs, and a breakpoint of that cell at the same offsets stops at a statement
of another cell. Only a statement at `callDepth 0` is known to be in the
source of the run.

## Cause and options

`evaluateStatementsAsync()` (`src/compute-engine/function-utils.ts`) calls
the hooks for every statement whose `sourceOffsets` is set. A boxed
expression keeps `sourceOffsets` and nothing that names its source
(`sourceUrl` exists only in the MathJSON attributes,
`src/math-json/types.ts`).

- (a) Keep the calls and add the identity of the source to
  `EpsilDebugStatement`, for example `source`: the `url` option of the run
  that parsed the statement (`ExecuteEpsilOptions.url`), and a value the
  host can test when the run had no `url`. A debugger then steps into a
  function of an earlier cell and shows it in that cell, and ignores a
  source it does not show (a prelude). The documentation of `range` changes
  to "in the source that `source` names". Recommended.
- (b) Call the hooks only for the statements of the source of the run, as
  the documentation says now. A debugger cannot step into a function of
  another cell. It needs the same record as (a), to compare.
- (c) Change the documentation only. The host still cannot tell the source.

Tycho also proposed a filter option (`debug.sources`); with (a) the host
filters in its hook.

## Decision

User decision 2026-11-20: (a)

## Design, measured

A prototype (ce-debugger, 2026-11-20, on
`af8263034fb9f22add3c3621ab48458acac2dec6`, not landed; patch with its two
check scripts: `~/dev/compute-engine-recovery/ce1624/prototype-on-af8263034.patch`)
checked a design that changes no site that copies offsets. Size S, not M.

- Every site that copies the offsets of a node passes the same
  `sourceOffsets` array on (32 sites, for example `{ metadata: { sourceOffsets:
  op.sourceOffsets } }`); none makes a new array. The array is therefore the
  identity of a place in a source.
- After the parse, `executeEpsilSteps()` (`src/epsil/execute-epsil.ts`, after
  `resolveLibraryNames()`) walks the MathJSON once and records, in a module
  `WeakMap` keyed by each `sourceOffsets` array, the source of the run: its
  text and its `url` option. `debugStatementOf()`
  (`src/compute-engine/function-utils.ts`) reads the map.
- The public fields, in the MathJSON names (`src/math-json/types.ts`):
  `EpsilDebugStatement.sourceContent: string`, the text of the source in
  which the statement was written, so `sourceContent.slice(...range)` is the
  statement; and `sourceUrl?: string`, the `url` option of that run. A host
  that passes no `url` (Tycho today, `ce-notebook-evaluator.ts`) compares
  `sourceContent` with the text of its cell; `url` tells apart two cells of
  the same text. The documentation of `range` changes to "in
  `sourceContent`".

Results of the prototype:

- Nine cases, each in two or three cells run in order on one engine: a named
  function, a function literal, a function-typed parameter whose argument is
  a literal of the later run, a closure returned by a function, a loop and
  an `if` in a function, a chain of three cells, two cells of similar text,
  a function redefined in a later cell, a loop of the run that calls an
  earlier function. Each of the 35 hook calls named the cell in which its
  statement was written. The function-typed parameter (a literal rebuilt on
  each application) keeps the source of its own run.
- `test/compute-engine/debug-hook-async.test.ts` (18 tests) and
  `debug-pause-time-limit.test.ts` (22 tests) pass; all 871 hook calls of
  these tests found a source.
- The walk takes about 1 ms for a source of 35,000 characters (12,801 nodes
  with offsets); `executeEpsil()` of the same source takes about 380 ms.

The work: the walk and the map (in `src/common/debug-hook.ts`, below the
engine), the two fields, the documentation of `EpsilDebugStatement`,
`EpsilDebugHooks` and `src/epsil/docs/implementation.md` ("Debugging"), the
page in `~/dev/cortexjs.io/docs/compute-engine/` that describes the hooks if
one does, tests for the nine cases, and the CHANGELOG. The synchronous hook
(`setDebugStatementHook`, the VS Code debugger) can read the same map; it
runs one program per engine, so it needs no change now.

A statement whose node is rebuilt without its offsets calls no hook at all,
so it never reports a wrong source: CE-1625 and CE-1626 are such cases. A fix
of either must pass on the same array, not a copy, or the statement calls
the hook with no source.
