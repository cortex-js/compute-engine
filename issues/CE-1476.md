In complex mode, a function whose parameter has no stated type no longer compiles when it is called with a complex argument.

## Witness

`x, y: real`; `f` declared `function`, then `f(w) \coloneq w^2` evaluated;
`compile(Arg(f(x + i·y)) + f(x), { to: 'javascript', mode: 'complex', inputs: { x: 'real', y: 'real' } })`.

0.193.0: compiles; at x = 0.5, y = 0.3 it gives 1.3308390005411683, the
interpreter's value. 0.194.0: declines, "an argument of f that is not real".

Workaround: declare `f` as `(complex) -> complex` (then it compiles and
gives the same value), at the cost of the complex lane for the real call.

## Cause (Tycho's reading)

`signatureTypes()` (`ir/lower-functions.ts`, about line 280) calls
`inputType(t)`, not `inputType(t, wide)`. The comment of `inputType()` says
that a scalar of type `unknown` or `number` is wide, a complex in
`mode: 'complex'`; the IR README ("User functions") says `real` when
unknown.

## Expected

Such a parameter takes the lane of its argument (one compiled copy per lane,
as 0.193.0 did on GLSL with `_fn_f_complex`); the case compiles and gives the
interpreter's value.
