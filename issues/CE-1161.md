A sum with two ranges, where the first has no upper bound and the second has one, gives the upper bound to the first range when its LaTeX is parsed again.

## Witness

```
const s = ce.box(['Sum', ['Multiply', 'i', 'j'],
  ['Limits', 'i', 1, 'Nothing'], ['Limits', 'j', 1, 3]]);
s.latex                 ->  \sum_{i=1, j=1}^3ij
ce.parse(s.latex).json  ->  ["Sum", ["Multiply", "i", "j"],
                             ["Limits", "i", 1, 3], ["Limits", "j", 1, "Nothing"]]
(probe 2026-11-08, on 262aad9c2a18de7755bfa0d83b9c4598150f7f46 with the fix of CE-1126)
expected  ->  the parse gives ["Limits", "i", 1, "Nothing"], ["Limits", "j", 1, 3]
```

Neither sum has a value: a range with no upper bound stays unevaluated. So
the defect changes the form, not a result. The same occurs for a clause with
an upper bound and no index and no lower bound before a range:
`Sum(j, Limits(Nothing, Nothing, 5), Limits(j, 1, 3))` is written
`\sum_{j=1}^{5, 3}j` and parses as `Limits(j, 1, 5)`.

The witness is `crafted`: a user who writes two ranges gives each an upper
bound, and the parser gives a range with no upper bound only for LaTeX such
as `\sum_{i=1, j=1}^{3}`, which already reads as `i` from 1 to 3.

## Cause and options

`serializeBigOp()` (`definitions-arithmetic.ts`) writes one superscript item
for each clause that has an upper bound, and no item for a range that has
none. `getIndexes()` gives the superscript items, in order, to the ranges
whose subscript item has no upper bound, so it cannot tell which range the
serializer left out.

- (a) When a range with no upper bound comes before a clause with one, write
  the clauses as nested operators, `\sum_{i=1}\sum_{j=1}^{3}ij`. The parse is
  then a `Sum` of a `Sum`, which has the same meaning and a different form.
- (b) Leave it: no value changes, and the LaTeX that the parser reads is not
  affected.
