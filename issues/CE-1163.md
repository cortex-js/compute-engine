The Buddhabrot showcase computes its picture on one core for half a second while the other cores of the device are idle.

## Witness

Tycho's `buddhabrot` showcase (`src/graph-paper/onboarding/template-data.js`)
computes its picture in one prelude statement, `const H_1 = step(H_0, 1200000)`:
1.2 million samples, about 28 million inner passes, accumulated into a list of
90,001 integer counts, compiled to JavaScript and run once in the prelude
worker. On 0.184.0, Apple M5 Max, through Tycho's prelude runner:

```
for form (the entry):   route=compiled  runMs=291  wallMs=469
parallel for form:      route=compiled  runMs=284  wallMs=377   counts equal
```

The `parallel for` form (CE-1093) runs the passes in order on the
JavaScript target, so it gains nothing today. The passes are independent: the
same step split by hand over Web Workers, each on a private zero list, the
lists added at the end (Tycho `roadmap/BUDDHABROT_CODE_STUDY.md` § 8.4,
500,000 samples, Chromium): one thread 74 to 77 ms, 8 workers 11.6 to
15.1 ms.

Owner decision 2026-11-08 (Tycho row IB): WebGPU is not the direction; the
JavaScript target gains workers and `parallel for` on several cores. CE-1158
was cancelled.

## Request

1. **`runAsync(inputs)` on a JavaScript compiled result**, next to `run()`:
   a promise of the same value. When the program holds a `parallel for` with
   a large range and the engine has a pool (`ce.workers`), the passes of that
   loop run on the workers; otherwise it runs as `run()` does. `run()` stays
   synchronous and in order.
2. **The pool route of a `parallel for`.** The range is split into one
   sub-range per worker; each worker runs the body on a private copy of each
   accumulator set to zero (a list element or a scalar), with the `k` of its
   sub-range, and the copies are added to the accumulator in sub-range order.
   A pass that reads an accumulator (rule 2 of CE-1093) runs in order.
   Fallback to the in-order run: no pool, a result that is not `shippable`,
   a small range, a worker failure.
3. **A query before the run**, like `willUsePool(cells)`: whether
   `runAsync()` would use the pool, so that a host can choose the thread. It
   must see a `parallel for` inside a called function (the witness's loop is
   inside `step`).

Not requested: the loop as a kernel of `broadcastAsync()`; the statements
around it (`let L = H`, `L[90001] = r + n`) stay in the program.
`broadcastAsync()` and the kernel worker can be the mechanism underneath.

Workaround: a host compiles `step`, calls it on sub-ranges in its own workers
and adds the lists. It works for this step only because the step reads its
sample offset from the list.

Tycho half on adoption: the prelude runner awaits `runAsync()` for every
value statement; the `buddhabrot` step takes its `parallel for` form; the
prelude worker gets a pool (`ce.workers`) and the lanes test compares the
counts with the `for` form.

READY (the instrument's reading): a compiled result has a `runAsync`
function. The instrument then also prints both forms' run times.
