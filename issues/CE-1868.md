A read of one channel by its name from a cell of an array of pixels gives an error in the interpreter when the pixel type is declared with `type alias`, although the type of the cell names the channel.

## Witness

At commit `df73dced7475dd51facea15ab07625f9eba33b23`, with
`npx tsx src/cli/epsil.ts <file>`:

```
type alias Byte = integer<0..255>
type alias Rgba = tuple<r: Byte, g: Byte, b: Byte, a: Byte>
let img = arrayFrom(repeat((0, 0, 0, 255), 4), "Rgba")
img[2] = (9, 8, 7, 6)
img[2].g
```

The result is ``Runtime error: expected `dictionary | object | record |
tuple`, got `tuple<integer, integer, integer, integer>` at `(9, 8, 7, 6)` ``;
the expected value is `8`. No static error is reported. With `img[2][2]` in
place of `img[2].g` the result is `8`.

Compiled code gives `8` for the read by name: with the four lines above run
by `executeEpsil()`, `let k1 = (i: integer) => img[i].g` compiles on
`javascript` and `run(2)` is `8`, and `Field(At(S, i), "g")` with `S`
declared `array<tuple<r: integer<0..255>, g: integer<0..255>, b:
integer<0..255>, a: integer<0..255>>>` compiles on `glsl`.

`plausible`: the documentation of arrays (`src/epsil/docs/evaluation.md`)
declares `Byte` with `type alias` and `Pixel` with `type`, one word apart, and
a program that writes both with `type alias` gets this error at its first
read of a channel.

Workaround: declare the pixel type with `type` (`Pixel(9, 8, 7, 6)`, then
`img[2].g` is `8`), or read the channel by its position.

## Cause and options

Not investigated. The reading: the store accepts a tuple with no names for a
cell whose type has names, and a read gives a tuple with no names, so the
field has no element to read. For a variable the same value is refused at the
declaration (`let p: tuple<r: integer, g: integer> = (1, 2)` is the static
error `incompatible-type`), and Epsil has no literal for a tuple with names
(`(r: 9, g: 8)` is a syntax error).

Options:

1. A read of a machine tuple cell gives a tuple that carries the names of the
   cell type, so the interpreter gives the value that compiled code gives.
2. `arrayFrom` refuses a cell type that is a tuple with names and is not a
   declared type, with a message that names `type`. The specification of
   arrays says "named or not" for the tuple cell
   (`docs/plans/2026-11-25-mutable-arrays-spec.md`, section 3), so this
   changes it.
