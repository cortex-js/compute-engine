The type shown for a function that inserts its argument into a range, or writes it over one element, says it returns a list of integers, and it returns a list that holds the argument, which can be any number.

## Witness

At `4efc10ad5dcf6f606f971cadb6b48327dc6b3129`:

```ts
ce.assign('ins', ce.box(['Function', ['Insert', ['Range', 1, 'u'], 1, 't'], 'u', 't']));
ce.box('ins').type.toString();            // (u: unknown, t: unknown) -> list<integer>
ce.box(['ins', 2, 0.5]).evaluate();       // [0.5, 1, 2]

ce.assign('rep', ce.box(['Function', ['ReplaceAt', ['Range', 1, 'u'], 1, 't'], 'u', 't']));
ce.box('rep').type.toString();            // (u: unknown, t: unknown) -> list<integer>
ce.box(['rep', 2, 0.5]).evaluate();       // [0.5, 2]
```

The type of each call, with its arguments, is right (`list<real>`). The same
operators with a value of type `unknown` that is not a symbol
(`Insert(Range(1, u), 1, g(u))`) are typed `list<unknown>`, which is right.

## Impact

No value is wrong. A reader of the function's type is told that the list
holds integers. This is the `Insert` and `ReplaceAt` twin of CE-1363, which
fixed `Append`.

## Cause and options

Not investigated in depth. The signatures are
`(indexed_collection<T>, integer, T) -> list<T> where T: any`. At
canonicalization, the operand `t` (a parameter with no inferred type) is
given the type `integer`, the binding of `T` from the source; the type
handler then sees `integer`, not `unknown`. The function's signature still
shows `t: unknown`. The inference of a symbol's type from a repeated type
variable must not narrow it to the other operand's type: the value can be any
value that `T: any` admits. Check `Append`'s `appendResultTypeD` and
`storedElementType` (`collections.ts`) for the result rule once the operand
keeps `unknown`.
