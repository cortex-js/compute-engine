Defining three functions that call each other in a cycle, each declared with an open signature, takes many seconds and the last definition does not finish.

## Witness

CE-1515's four definitions with each head declared `(unknown) -> unknown`
instead of `function`: `assign('c_2')` takes about 8 s and `assign('d_2')`
does not finish in 60 s, on 5b9f88cf5 as well as on main (older than
CE-1515).

Measured again on 2ec7511f8cce32d7474fccf61cebdd11ebb86ecf (2026-11-20):
`assign('c_2')` takes 4.5 s; `assign('d_2')` runs out of memory after
several minutes (exit 134). Two heads that call each other and themselves
(`h_0(n) = If(n ≤ 0, 1, h_1(n − 1) + h_0(n − 1))`, `h_1` the same with the
roles swapped, `d(x) = h_0(3) + x²`) do not finish in 60 s either.

## Cause and options

Cause: a signature derivation that reads the provisional signature of a
function whose derivation runs below it is "tainted" and is not memoized
(`noteReentrantSignatureRead`), and an untainted one is checked against the
type of the literal, which is computed again at each read. So each read of
a head inside the cycle derives its signature again, with the reads of its
own callees: during `assign('c_2')`, 1 derivation of `c_2` ran 208
derivations of `a_2` and 5,646 of `b_2`. The work grows by a factor at
each level of the cycle.

Options:

- **(a) Keep each derived signature in the frame of the derivation below
  it** (the parent), for the current pass of the parent, with a key of the
  identities and versions that the derivation reads (recommended, with
  the limit below stated). The patch is in the worktree
  `/tmp/wt-cebatch-1516` (copy: `/tmp/cebatch-1516/ce1516-option-a.patch`,
  src +190 −6, `declared-parameter-result.ts`, `boxed-value-definition.ts`,
  `boxed-operator-definition.ts`, and two tests). The witness then takes
  0.3 s (`d_2(1)` is 8, type `number`), the pair of heads 18 ms, a cycle of
  6 heads 2.3 s. The CE-1515 and signature tests pass (18 files, 427
  tests). Limit, from the Claude review: a kept signature can read the
  earlier value of a type cell in flight, or another stack-dependent answer
  (`_typeStackDependent` types, the call-result memo of
  `call-result-type.ts`, effects in flight). Such a state can change between
  two reads in the same pass of the parent, and a later read gets the
  result derived before the change. No program was found that shows it; the
  memo of the definition (`_signatureMemo`) already keeps an untainted
  derivation that read such answers. Also with (a): after
  `ce.box(['a_2', 'm']).type`, `ce.box(['b_2', 'm']).type` is `any`, not
  `number`, and stays `any` (the fixpoint iteration of
  `verifiedListHypothesis` stores `any` in `fixpointMemo`; the values are
  correct). There is no earlier answer to compare with, since the program
  does not finish without (a).
- **(b) (a), and a time for each stack-dependent answer**, so that a
  signature is kept only when every state that answered it last changed
  before the pass of the parent started. A start of this
  (`/tmp/cebatch-1516/ce1516-option-b-clock-attempt.patch`) times the
  re-entrant serves of `cache.ts`; the witness is still slow, because most
  answers come from the sources listed in (a), which have no time. Each of
  them needs the same time tracking. Size L, on the hot paths of the type
  cache.
- **(c) Leave it**: the hang stays, for a program that Tycho's
  signature-analysis scope can reach (it declares heads
  `(unknown) -> unknown`).
