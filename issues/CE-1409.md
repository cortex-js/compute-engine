Sorting a computed list of more than 10,000 elements whose values change at each evaluation computes every element twice, and some operations on such a list give no result.

## Witness

`Tick` is a host operator declared `pure: false` that returns 1, 2, 3, … at
its successive calls; `M(n)` is `Map(Function(Tick(), k), Range(1, n))`.
On `2b64e14ccfb4aeca5c563bd1c8198b52ea2173b6`, with the default
`maxCollectionSize` of 10,000:

| Program | n = 10000 | n = 10001 |
| --- | --- | --- |
| `First(Sort(M(n)))` | 1, 10,000 evaluations | 10001, 20,001 evaluations |
| `Length(Unique(M(n)))` | 10000 | unevaluated |
| `Mean(M(n))`, `Max(M(n))` | right, n evaluations | right, n evaluations |

Seen by the reviewer with it, at any size, same cause not confirmed:
`Sinc(Repeat(Tick(), 3))` evaluates the value twice per element;
`ArgMax(Repeat(Tick(), 3))` makes 12 evaluations;
`ce.box(['Complex', ['Repeat', ['Tick'], 3]])` makes 3 evaluations when the
expression is built, before any evaluation.

The witness is `crafted`: a value that counts its evaluations. With a draw
(`Random()`) the sorted list is still sorted, and the difference shows only
in the sequence of a seeded frame.

## Cause and options

Not read. Above the limit a `Map` stays a lazy collection, and a consumer
that reads it more than once (`Sort` seems to read it to compare and again
to build its result) evaluates the body again at each read. Options: a
consumer of a lazy collection whose element is not pure materializes it
once into a list before it works on it (the limit then bounds a list in
memory, not the number of evaluations); or each such consumer is checked
for one read per element. `Unique` above the limit needs its own look.
