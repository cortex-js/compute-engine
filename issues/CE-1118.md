A formula made before the user defines a function with the name of a built-in function, and evaluated after that definition, uses the user's function in place of the built-in one.

## Witness

At commit `5408577629d05c0bd64ad5caf56aafeb47b7d322`, and with the uncommitted
CE-1109 changes:

```ts
const sum = ce.box(['Add', 'x', ['Sin', 'x']]);   // the library Sin
ce.pushScope();
ce.declare('Sin', 'function');
ce.assign('Sin', ce.box(['Function', ['Add', 't', 100], 't']));
const r = sum.evaluate();
r.json                    // ["Add", "x", ["Sin", "x"]], and that Sin is the user function
ce.popScope();
r.subs({ x: 1 }).N()      // 102; must be 1 + sin 1 = 1.8415
```

The same happens to the terms of a derivative evaluated in such a scope:
with a library `x·Sin(x)` boxed first, `D(x·Sin(x), x)` evaluated in the
scope gives `x·D(Sin(x), x) + Sin(x)` with the second `Sin` bound to the
user function (101.54 at x = 1 after the scope ends; must be 1.3818).

`crafted`: the formula is boxed, then a user function with the capitalized
name of a library function is declared in a pushed scope, and the formula is
evaluated there.

## Cause and options

`docs/SCOPING-MODEL.md`, "Callable resolution": a callable name denotes the
binding selected where the call was created. The evaluation of `Add` (and of
`Multiply`) builds its result again by name in the current scope, so an
operand that stays symbolic is bound again to the definition the current
scope gives the name. A rebuild that keeps the binding of each call
(`withCallableBinding()` or `_withLibraryBinding()`, `boxed-function.ts`)
where the arithmetic evaluation rebuilds an unchanged operand is the
candidate fix. Related: CE-1114 (a library rule names another shadowed
function in its result), CE-1109.5 (a call bound to a given definition
without a borrowed scope).
