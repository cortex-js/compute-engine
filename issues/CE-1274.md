A host that wants to offer a fix for an Epsil error cannot tell which error it has without reading the text of the message, and for a read before a declaration it does not get the position of the name.

## Witness

CE 0.188.0 from the npm package, `checkEpsil(ce, source).diagnostics[0]`:

| Program | `message` | Text of `range` |
| --- | --- | --- |
| `let a = 1` / `x1 = 2` | `["static-type-error", "`x1` is not declared: write `let x1 = …`", "x1 := 2", "assignment-to-undeclared-variable"]` | `x1 = 2` |
| `let a = b1 + 1` / `let b1 = 2` | `["static-type-error", "`b1` is used before the statement that declares it in this block", "let a = b1 + 1", "read-before-declaration"]` | `let a = b1 + 1` |

The first element of the message is `static-type-error` for both; the exact code is the last element. The range of the second is the whole statement.

The instrument prints both diagnostics and `CE-1274: READY` when the first element of each message is the exact code and the range of the read is the name `b1`.

## What it must give

The exact code where a host reads the code of a diagnostic (the first element of the message, or a `code` field), and for `read-before-declaration` the range of the name that is read. The position of the exact code can be another one than the first element, if it is stated as part of the API.

## Why Tycho needs it

Tycho shows these errors in the prelude cell and attaches an edit that inserts `let` to `assignment-to-undeclared-variable` (user decision). It reports `read-before-declaration` under its own code with the range of the name.

## Cause and options

Not investigated.

## Tycho half on adoption

`refineCheckDiagnostics` in `src/plot-core/prelude-runner.ts` reads the last element of the message and searches the statement for the first read of the name. On adoption: read the code where the engine puts it, use the engine's range, and delete the search.

## CE answer

CE (2026-11-13, session ce-desk): P4 confirmed, in the pool; not started. The request is sound: a diagnostic carries its code as a field and the range of the name it is about. Workaround: the one in the issue (the code is the last element of the message).
