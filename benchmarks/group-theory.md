# Group theory capabilities and benchmarks

This record connects the native group kernels, their resource bounds, and the
workloads used to measure them. It is a developer capability ledger, not a claim
of complete GAP compatibility. The public user guide belongs in the
`cortex-js/cortexjs.io` documentation repository.

## Integration and representation contracts

The optional `@cortex-js/compute-engine/group-theory` entry exports
`loadGroupTheory`, `GroupTheoryLoadOptions`, and `GroupTheoryLoadReport`.
Loading is synchronous and idempotent for an engine with the same effective
options. Group operations are not part of the default library.

The expression adapters decode MathJSON into validated values and dispatch to
representation-specific kernels:

- Permutation groups use finite-support permutations and a declared action
  domain. Products act on the right: `ab` applies `a` and then `b`.
- Matrix groups use invertible square matrices over the rationals or a prime
  field. Vectors multiply matrices on the right. Field and dimension are part of
  the domain.
- General finite algorithms use a complete multiplication table with identity
  index zero. User tables receive an exhaustive associativity check; tables
  derived from validated exact group operations inherit associativity.
- A finite polycyclic generating sequence supplies a subnormal cyclic series and
  unique coordinates `g1^e1 ... gr^er`. Its ambient descriptor and sequence are
  mathematical data; resource settings are not stored in the value.
- A collected `PcGroup` describes a tower of verified finite cyclic extensions.
  Its bigint coordinates and arithmetic do not enumerate group elements.

A group descriptor records generators and a domain. Different generator lists
can describe the same subgroup; structural descriptor equality is not a group
equality algorithm. Kernels are internal implementation APIs. Shared public
operations select a suitable backend rather than exposing table indices. The
specialized `PcGroup`/`PcElement` types remain separate from the general
`GroupDescriptor` union: generic structural operations do not yet dispatch to
the collected presentation backend.

## Maps, quotients, and sifting

A homomorphism carries its source and target. Equal table sizes are insufficient
to identify domains. MathJSON maps transport complete element/image pairs so
that changing an enumeration order cannot silently change the function.
Composition matches the actual intermediate elements before composing indices.

An arbitrary image table is checked against all products in O(|G|²).
Generator-image construction propagates images along the Cayley graph and checks
every traversed edge; path independence establishes a homomorphism in O(|G| d)
table operations for d supplied generators.

A quotient G/N retains its source, normal kernel, quotient group, and surjective
projection. For a numerator inside a larger ambient table, source indices and
ambient indices require an explicit correspondence. A lift chooses a
representative and satisfies `project(lift(q)) = q`; it need not preserve
multiplication. For example, a representative of order four in C4 can lift the
nonidentity element of its quotient C2.

For an induced polycyclic sequence of H, sifting keeps a residue in the right
coset Hx and returns identity exactly when x belongs to H. It stops when the
leading coordinate cannot be eliminated. Sifting does not define a unique
representative of a nonnormal coset. Canonical reduction is a separate operation
that scans Hx for the least parent coordinate vector.

A full vector action of an invertible finite-field matrix group is faithful. A
projective action can have a scalar kernel. The order of the projective image
alone therefore does not establish the order of the original matrix group.

## Collected presentation contract

The public constructor is
`PcGroup(relativeOrders, powers, conjugates, inverseConjugates)`. All four lists
use the outermost-generator-first order. For generator i, `powers[i]` is a
coordinate vector in the later generators, and each row of `conjugates[i]` or
`inverseConjugates[i]` gives the image of one later generator in that same tail.
Four empty lists describe the trivial group.

For each extension of a collected tail H, the new generator g has relative order
m, relation g^m=t, and right conjugation phi(h)=g^-1 h g. Construction checks
that the supplied forward and inverse maps preserve H's defining power and
conjugation relations, compose to identity, fix t, and satisfy phi^m(h)=t^-1 h
t. These conditions establish unique normal forms g^e h with 0 <= e < m.
Collection uses

```text
(g^a u)(g^b v) = g^r t^q phi^b(u) v
a + b = q*m + r
```

Automorphism powers use binary composition; direct products use componentwise
modular arithmetic. Neither path needs a multiplication table.

`PcElement(group, coordinates)` binds the canonical coordinates to their
presentation. The initial interface consists of `PcGroupOrder`,
`PcRelativeOrders`, `PcIdentity`, `PcGenerators`, `PcCoordinates`, `PcMultiply`,
`PcInverse`, and `PcPower`. Arithmetic requires the same presentation domain; it
does not attempt an isomorphism between two different presentations of the same
abstract group.

The kernel accepts up to 64 generators, relative orders at least two, and
coordinate/relative-order/power-exponent inputs of at most 4,096 bits. The group
order is the exact product of relative orders and can exceed 4,096 bits. A
conservative estimate caps stored relations and recursive collection scratch
space at 1,000,000 bigint coefficient slots. This is a logical storage bound,
not a guarantee about JavaScript allocator or garbage-collector memory.

## Resource policy

| Loader ceiling          | Per-call option | Default and maximum           |
| ----------------------- | --------------- | ----------------------------- |
| `maxFiniteElements`     | `maxElements`   | 256                           |
| `maxFiniteWork`         | `maxWork`       | 50,000,000 logical work units |
| `maxMatrixActionPoints` | `maxPoints`     | 100,000                       |

Per-call named options can lower the installed ceiling. They are execution
controls and do not change a group's mathematical identity. An element bound is
at least one; work and point limits may be zero. Existing permutation loader
ceilings separately control degrees, generator storage, closures, orbits, and
chains, including permutation values returned by other representations.

The table bound applies when an operation builds a complete finite model.
Permutation stabilizer-chain queries and matrix order through a faithful finite
action can operate on groups whose orders exceed 256. Collected `PcGroup`
operations also avoid the table bound and accept only the per-call `maxWork`
option, under the same `maxFiniteWork` loader ceiling. A larger order does not
permit a larger table implicitly.

Nested finite algorithms share one work ledger and the engine deadline.
Exhaustion is an error, not a negative membership answer, a proof of
nonsolvability, an infinite-order result, or an incomplete list. Logical work
counts are algorithmic limits, not milliseconds or a uniform measure of bigint
CPU cost.

Homomorphism payloads, including an entire automorphism list, are preflighted
against a 1,000,000-unit expanded storage bound before rendering. Repeated
descriptors and element images count each time they appear in serialized
MathJSON; large exact coefficients are weighted by decimal width. Encoded
elements are shared in memory, but sharing does not remove the serialization
bound. Exceeding it produces `group-map-output-limit`, even if the kernel can
compute the maps themselves.

Additional kernel bounds include the 4,096-subgroup lattice cap, bounded
automorphism enumeration, matrix dimension at most 32, bounded exact coefficient
sizes, and explicit storage limits for permutation images and actions. Keep the
kernel definitions authoritative when changing these bounds.

## Reproducing performance measurements

Use Node 26 for these measurements. This does not change the package's supported
Node versions or require contributors to change their default runtime. The
commands below assume `node` resolves to the intended Node 26 executable and
dependencies are already installed.

The runner bundles all five benchmark families to ES2022, executes them
sequentially with the current Node executable, writes records under
`benchmarks/results/`, and removes its temporary bundles. TypeScript loading is
outside the timed process, and native private fields retain their modern runtime
behavior.

```sh
node --version
node benchmarks/run-group-theory.mjs
```

Specific families can be selected without changing any project runtime setting:

```sh
node benchmarks/run-group-theory.mjs matrix polycyclic
node benchmarks/run-group-theory.mjs presentation api
```

Each workload uses three warmups followed by nine measured samples. Records
include runtime/platform/CPU metadata, elapsed-time summaries, and logical work
where applicable. The runner also records V8, esbuild, ES2022 target, base Git
commit, and whether the source was a working tree. A base commit in a
working-tree record is not an assertion that the measurement used only committed
sources.

Minimize other CPU activity and compare construction and query phases
separately:

- The finite benchmark separates exhaustive table validation from queries on an
  existing table. Queries create a fresh session and work ledger.
- The matrix benchmark separates group construction from order/actions, forms,
  finite table conversion, and a rational invariant-lattice calculation.
- The polycyclic benchmark separates table validation, sequence construction,
  quotient-section construction, coordinate roundtrips, section roundtrips, and
  action validation with orbit/stabilizer calculation.
- The presentation benchmark measures consistency validation separately from
  collected arithmetic on groups whose orders are far beyond table limits.
- The API benchmark uses a fresh engine for each sample. Engine construction and
  library loading are separate from boxing plus evaluation, preventing previous
  expression or stabilizer-chain caches from hiding first-query cost.

Kernel measurements exclude Compute Engine parsing, boxing, MathJSON decoding,
and output serialization. The API measurements exercise boxing and evaluation,
but do not include an Epsil parser or a UI. Logical-work reductions corroborate
algorithmic improvements when elapsed times vary with JIT compilation, garbage
collection, or competing processes.

## External GAP comparison

The independent [GAP script](group-theory-gap.g) runs with GAP 4.15.1 and
packages disabled (`gap -q -A -b benchmarks/group-theory-gap.g`). The recorded
run uses `ghcr.io/gap-system/gap:4.15.1-bare`, with its exact image digest in
the result metadata, inside a Linux container limited to two CPUs and 1 GiB of
memory. CE runs on Windows under Node 26.12.1 on an Intel Core Ultra 7 165U.
Both use three warmups and nine samples, with fresh GAP groups per query sample.

GAP's recorded timer is `gettimeofday`, with 1,000 ns resolution; GAP reports it
as nonmonotonic and not reliable. The harness rejects negative durations, but
wall-clock adjustments remain a limitation. Platform, container limits,
representations, allocation, and timing facilities differ. The comparison is a
diagnostic reference, not an overall CAS ranking or a controlled language
performance comparison. These are shared development-machine measurements;
background activity is not controlled. Preserve the raw sample ranges and
compare repeated runs before treating a timing change as a regression.

The following medians are milliseconds from the linked matrix, polycyclic, and
GAP records. All paired queries verify the same mathematical result:

| Workload                      | CE kernel median ms | GAP median ms | Representation note                                                                          |
| ----------------------------- | ------------------: | ------------: | -------------------------------------------------------------------------------------------- |
| GL(4,2) order, 20,160         |               7.176 |         1.262 | Generic prime-field matrices with adjacent transvections; CE builds a faithful vector action |
| GL(5,2) order, 9,999,360      |              17.774 |         4.989 | Same generator construction; group construction excluded                                     |
| GL(6,2) order, 20,158,709,760 |              57.125 |        16.833 | Same generator construction; group construction excluded                                     |
| S4 polycyclic sequence        |               0.628 |         0.113 | CE starts from a validated table; GAP starts from permutation generators                     |
| C2^7 polycyclic sequence      |               1.094 |         0.329 | CE starts from a validated table; GAP starts from a regular permutation action               |

The matrix constructors do not attach a precomputed named-GL order. GAP's D128
automorphism workload converts fresh regular permutations to a pc group outside
the query timer, measures that conversion separately, then materializes all
2,048 automorphisms as complete images. CE's corresponding kernel uses a finite
table. Descriptor construction, table validation, conversion, and query costs
must therefore remain separate when interpreting those results.

No external GAP measurement currently covers the specialized collected
presentation benchmarks. The GAP comparison is a development tool; GAP is not
required by the package or its runtime.

## Algorithm and capability references

The implementation uses native exact arithmetic, finite closures, Cayley-graph
propagation, Schreier stabilizer chains, finite table algorithms, and subnormal
cyclic coordinates. GAP is a reference for capabilities and mathematical
conventions, not a parser, runtime dependency, or imported implementation.

- [GAP Chapter 39: Groups](https://gap-system.github.io/gap/doc/ref/chap39.html)
  outlines general group, subgroup, structure, and construction operations.
- [GAP Chapter 43: Permutation Groups](https://gap-system.github.io/gap/doc/ref/chap43.html)
  outlines natural actions, representations, recognition, and stabilizer chains.
- [GAP Chapter 44: Matrix Groups](https://gap-system.github.io/gap/doc/ref/chap44.html)
  outlines matrix domains, actions, classical groups, forms, and related
  methods.
- [GAP Chapter 45: Polycyclic Groups](https://gap-system.github.io/gap/doc/ref/chap45.html)
  outlines generating sequences, coordinates, induced sequences, and sections.

Further work depends on finite extension fields and field embeddings; infinite
polycyclic factors and collection/completion of more general presentations;
specialized large-group homomorphisms and subgroup algorithms; representation
recognition and reduction; and algorithms for infinite rational/integral matrix
groups. Those dependencies should be tracked separately from the bounded
capabilities listed above.
