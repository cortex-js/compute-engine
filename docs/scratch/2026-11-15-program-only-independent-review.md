# Independent Program boundary review

Recommendation: stop and recost the checker integration before production edits. The source establishes a real gap in the proposed 55–75-line checker adapter; it does not establish that Program is infeasible or that a broader prepared-type bridge is necessary. No candidate patch was supplied or reviewed.

The decisive distinction is between an observer that reads the shared canonical result and a checker that independently decides what a later statement's callee or assignment means. `registerPinnedSignature` (static-diagnostics.ts:2494–2701) does the latter: it selects replace/retain rules for let, const, annotated assignments and earlier-cell functions; changes definitions with `_infer`; and supplies `_staticPinnedCallees` to later call boxing. `applyAssignmentTypeEffect` (758–950) installs annotations and last-assignment evidence onto definitions and `_staticAssignmentEvidence`. Moving those mutations into a sequence callback would remove a loop but retain a second implementation of statement binding/type transitions. Renaming that callback an observer does not meet §4.4.

Minimum existing-test witnesses (read, not executed):

- `test/epsil/static-lambda-callee-arguments.test.ts:43`: `let k = (n: integer) => n + 1; k(1.5)` must produce an argument diagnostic at the call. Core `Declare` canonicalization only calls `typeFunctionTarget` for the literal; that helper preserves/introduces the wildcard function type, not the installed literal signature (core.ts:4336, 8580). Ordinary boxing deliberately does not apply the checker's stricter inferred-callee rejection (box.ts:3282–3310).
- Same file:209: after `let k = (n: integer) => n + 1; k = (s: string) => s`, `k("a")` is clean and `k(1)` is rejected. At :221 a const retains the original signature instead. Those different transitions are binding semantics, not source anchoring or a typo lint.
- Same file:340: `let g = k` copies the signature in force at that point, including a preceding replacement. Final binding metadata alone does not describe that alias.
- Same file:114: `let k = (n: integer) => n + 1; let x = 1.5; k(x)` must reject the concrete evidence. Core `joinAssignmentEvidence` / `joinEvidenceOnBinding` (core.ts:4185, 4581) retain widened joined evidence and re-read assignments across the complete sequence. The checker currently records raw literal/last-write evidence. They are observably different inputs to validation, even where they share a binding identity.

A pure raw diagnostic pass can safely retain typo, source-range, presence and authored-error/provenance analysis. It can also retain per-use facts if an authoritative shared service supplies those facts. The current source exposes no such complete sequential callable/evidence output. Computing the four transitions above independently in that raw pass would remain another analysis of the bindings; avoiding engine writes alone would not remove the duplicated semantic rules.

An overstatement to avoid: `installAssignedLiteralBeforeClause` is not independently decisive. Approved P2 sorts top-level function statements ahead of const/let/assignment statements. Its within-program assignment-before-clause and const-before-clause controls are intentionally reordered by this contract, so much of that helper may disappear. Likewise staticDeclarations/shared hoisting already handles several pieces of applyAssignmentTypeEffect (annotations, library-name shadows, tuple leaves). Counting every existing helper as necessarily retained overstates the gap.

Smallest credible direction for a revised proposal: first remove portions made obsolete by P2/shared hoisting, then identify one authoritative implementation of literal binding replacement/retention/alias handling (prefer existing assignment machinery), plus the minimal diagnostic evidence view needed at each use. The checker can validate that view without preparing another environment. This is a concrete design/cost exercise spanning core declaration/assignment, call validation, checker metadata and rollback tests, rather than a 55–75-line consumption adapter. A simple shared transition extraction might be enough; these source reads do not justify a new general prepared-type bridge or registry framework.

I cannot honestly assign a bounded line interval without designing that extraction. Recost the changed transition/validation responsibilities and all callers, counting moved bodies neutrally; do not accept the original aggregate 448 ceiling on the strength of helper relocation. If diagnostics are intentionally weakened instead, that is a contract decision with the witnesses above, not an implementation shortcut.
