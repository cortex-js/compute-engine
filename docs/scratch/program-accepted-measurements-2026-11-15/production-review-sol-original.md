## Findings

1. **P2, introduced — refused declarations contaminate the retained binding's type and constness.** `staticDeclarations()` reads every raw declaration before the shared refusal pass; the later filter accepts names rather than declaration identities. Its type map/constant set therefore still contain a refused second declaration, and duplicate entries are hoisted repeatedly. Original target: `src/compute-engine/library/control-structures.ts:4203` and `:4501`. Executed witness: `executeEpsil(ce, 'let x=1; const x=2; x=3; x')` returns `1`, leaves x constant, and reports an extra constant-assignment. P7 requires the first mutable declaration to stand, so the final assignment must succeed and the result must be `3`. `let x=1; let x="a"; x` additionally leaves value `1` with public type `string`. Fix direction: derive metadata from accepted declaration statement objects and hoist each accepted binding once. The coordinator accepted this finding and assigned the fix while review continued.

2. **P1, introduced — direct Program cancellation disables the enclosing host budget.** `programFailureValue()` temporarily clears `_deadlineFrame` on a timeout/step-budget failure, but the original `PROGRAM_DEFINITION` handlers restored only `_epsilBatchId`. The execute adapter already restored the budget in its outer finally; direct evaluation did not. Original target: `src/compute-engine/library/control-structures.ts:398` / async twin, with the clearing writer in `src/compute-engine/function-utils.ts:3682`. Executed deterministic witness: prebox Program(5), then inside `ce.withStepBudget({steps:0}, ...)` evaluate it and inspect `ce.stepBudgetSpent` and the entry frame identity. Direct evaluation returns the step-budget Error but reports `false` and a different/missing frame; executeEpsil returns the same Error with `true`, the original frame and stepsLeft -1. Subsequent work in the same host span is consequently unguarded. Fix direction: restore the entry frame in both Program handlers after diagnostic construction. A fix was already appearing in source at the end of this original review; it has not been delta-reviewed here.

3. **P2, introduced — a typed const function's initializer fails on a second evaluation of the same Program.** The typed-function declaration path temporarily makes a const writable only when its stored value is undefined, an activation-era test that does not hold for a persistent Program declaration on another run. Original target: `src/compute-engine/library/core.ts`, typed-function initialization inside `declareSteps()` (approximately original line 15090). Executed witness: box `const k:(integer)->integer=(n)=>n` once and call `evaluate()` twice. The first result is Nothing; the second is constant-assignment(k). Controls `const c=1` and `const k=(n:integer)=>n` both return Nothing twice. This is declaration initialization, not a user assignment. Preserve ordinary const-write refusal while letting the Program initializer run again.

4. **P2, introduced — the new result hook serializes an arbitrary value outside the retained walk guard.** `const redeclared = errorCode(value.json)` at `src/epsil/execute-epsil.ts:528` now serializes every top-level result before the guarded `walkValue()` paths. A host operator returning a 2,000-level nested List in `Deep();5` throws RangeError to the host there, so the valid sibling does not run. The depth-10 control completes both statements and returns 5. The old runner path completes the deep case with a walk diagnostic; its relevant runner/boxed-expression implementation is unchanged by unrelated main-tree library work. The candidate stack explicitly points to result hook line 528 and evaluateStatements line 3649. The existing comments at the guarded walk helper already promise this backstop. Fix direction: derive the duplicate marker through the guarded error walk or inspect only the small structural marker; do not eagerly serialize every ordinary value outside the guard. No extra execution mechanism is needed.
