A follow-up for 0.178.0, the language release. Two of its changes touch the `bigint` mode (CHANGELOG, "The compile mode `'auto'` is removed" and "Compiled code calls only a function it can see"):

**No escalation to `bigint`.** The escalation of a compilation to `bigint` when a run-time value passes 2^53, which you suggested on 2026-10-30 and which the 0.176.0 reply put on the roadmap, will not be added. 0.178.0 removes the `auto` compile mode and with it every escalation: a compilation runs in the mode it is given, and `bigint` is used only when requested with `compile(expr, { mode: 'bigint' })`. A counting definition that can pass 2^53 is compiled in `bigint` from the start; the mode declines anything outside the integer lane with the diagnostic code `bigint-lane`, as before.

**Compiled code calls only a function it can see.** A call compiles when the callee is a defined function, a declared function with a value, or a function literal at the call site, and the callbacks of `Fold`, `Reduce`, `Map`, `Filter` and `Sort` compile when they are such a callee. A curried call or a partial application, a function value stored in a variable or passed through a parameter, and a function returned from a call now decline the compilation and run on the interpreter. The programs this issue describes, a `Fold` over a `Range` with a literal callback and user functions with integer parameters, compile as before. If one of your definitions applies a function partially or passes a function as a value, it now runs on the interpreter: say so here, with the form, and we look at it.

One smaller change in the `bigint` mode: a supplied `NaN` or `null` at a parameter that has a default throws the entry `TypeError` of a value that is not an integer; only a left-out argument takes the default.
