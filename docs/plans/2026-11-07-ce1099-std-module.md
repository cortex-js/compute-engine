# CE-1099: read the library definition of a name that a local definition shadows

**Status:** design approved by the user 2026-11-07 (`std::name` in Epsil,
`["Module", name]` in MathJSON, `super` stays reserved). Implemented
2026-11-07, with the qualified-call design of section 4 chosen by the user
after the review (the three forms (a), (b), (c)); `Module` cannot be bound
(`module-binding`). The ROADMAP entry CE-1099 was removed when the work was
done; CE-103 is closed.
**First user:** issue CE-103.
**Related:** the Epsil import system draft,
`docs/plans/2026-09-05-epsil-import-system.md` (section 7 below).

## 1. The problem

A local definition hides the library definition of the same name, and a
program or a serialized result has no reliable way to name the hidden one.

- **MathJSON (CE-103, witness `crafted`).** In a scope where `Pi` is declared
  and assigned `3`, `Sum(1/n², n, 1, ∞)` evaluates to `["Divide", ["Power",
  "Pi", 2], 6]`, and its value is 1.6449 (correct). `ce.box()` of that JSON in
  the same scope gives 1.5, because the bare name `Pi` reads the local.
- **Epsil (CE-716, CE-835).** When a program binds `floor`, the library
  function stays reachable as `Floor`. When the program also binds `Floor`
  (`function Floor(x) { … }`, which CE-835 keeps legal), nothing reaches the
  library function.

## 2. What the engine does today (measured 2026-11-07 on the working tree)

| Probe, in a scope that shadows the name | Result |
| --- | --- |
| Library `Pi` and local `Pi` (=3) in one expression: `isSame` | `false` |
| `Add(library Pi, local Pi)`: `.N()` | 6.1416 (correct) |
| The same expression, compiled to JavaScript | 6.1416 (correct) |
| `.json` of that expression | `["Add", "Pi", "Pi"]` (the binding is lost) |
| A call `Floor(x)` made before the shadow `Floor := y ↦ 100`, at `x = 2.5` | interpreter 2.25 (correct); compile declines with a message, falls back to the interpreter |
| `ce.box()` of the `.json` of that call, at `x = 2.5` | 100.25 (wrong: reads the local) |
| `ce.box("Super:Pi")` | the **string** `'Super:Pi'` |
| `ce.box({sym: "Super:Pi"})` | `["Error", "'invalid-symbol'", …]` |
| `ce.lookupDefinition("Module")`, `("std")` | `undefined` (both names are free) |
| Epsil `std::pi` | parse error `unexpected-symbol "::"`: the parser accepts the token nowhere |
| Epsil `let x = 1; function f() { let x = x + 1; x }; f()` | `2`: the right side of a `let` already reads the outer `x` |

So the engine already keeps the two bindings apart in an expression. Only the
serialized text loses the difference. The design adds one spelling for "the
standard-library definition of this name" and makes the serializers write it
when the bare name would read another definition.

## 3. Decisions

**D1. A qualified name names one fixed definition.** `std::pi` is the
definition of `Pi` in the system scope, where the standard library and the
libraries of the constructor's `libraries` option are installed. Its meaning
does not depend on where the text is read, so a JSON round trip is stable. It
does not nest, and it cannot name a user variable.

The other meaning, the next binding outward (`super`), is a separate feature
with no request today. `super` stays reserved for it (`reserved-words.ts`,
not in use). An Epsil `let x = x + 1` already reads the outer `x`.

**D2. The Epsil syntax is `std::name`.** `std` is the name of the standard
library, not a keyword, and `::` is the qualified-name operator. The name
before `::` is always a library name, never a variable: `let std =
standardDeviation(xs)` stays legal, and `std::pi` still reaches the library in
that program. `.` keeps its two meanings, field access and protocol member
access.

**D3. The MathJSON form is `["Module", name]`.** A function head is a symbol
in MathJSON, so a call is `["Apply", ["Module", "Floor"], "x"]`, as
`["Apply", ["InverseFunction", "Sin"], "x"]` is today. A reader that does not
know `Module` sees an unknown function and keeps the expression symbolic. A
symbol spelling such as `"Super:Pi"` was rejected: `:` is not a valid symbol
character (`isValidSymbol()`, `src/math-json/symbols.ts`), and a reader that
does not know the rule reads a string with no error, as the engine does today.

The form reads "the name `Pi` in a module"; with one operand, the module is
the standard library, which the import draft also treats as a module (`std:`
specifiers, section 7). A second operand, the name of a module, is reserved
for later (`["Module", "Sq", "'mine'"]` for a library loaded with
`ce.loadLibrary()`, `["Module", "x", "'./geometry.epsil'"]` for an Epsil
module). It is not implemented, and a `Module` with two operands is an arity
error until then.

The user chose `Module` over `Library` and `Qualified` on 2026-11-07.
Mathematica uses the name `Module` for another construct, local variables
(`Module[{x, y}, body]`, which is the `Block` of this engine). The naming
policy (`docs/MATHEMATICA-NAMES.md`) lets a Mathematica name that is already
an operator with another meaning keep the meaning of this engine, so `Module`
can never be an alias of that construct. A translated Mathematica
`["Module", ["List", "x"], body]` gives an error (the first operand is not a
symbol), never a wrong value.

**D4. A serializer writes the form only when the bare name would read another
definition** in the scope where the serializer runs: the node is bound to the
system-scope definition of its name, and `ce.lookupDefinition(name)` in the
current scope gives another definition. Outside such a scope, the output does
not change.

**D5. LaTeX has no spelling.** `["Module", "Pi"]` writes `\pi`, and a call
writes its usual LaTeX. A parse of `\pi` in a scope that shadows `Pi` reads the
local, as today. This limit is documented.

**D6. Compilation adds no lowering.** The canonical form of
`["Module", "Pi"]` is the symbol `Pi` bound to the library, and constants
already compile correctly (table above). A library-bound call whose name a user
definition shadows keeps today's decline, which gives the interpreter's value.
To lower such a call by its binding is a separate task.

## 4. Specification

**MathJSON `Module`.**

- `["Module", s]` takes one symbol. Its canonical form is the symbol `s`
  bound to the definition of `s` in the system scope (`ce.contextStack[0]`).
  There is no new kind of boxed node.
- `s` is not defined in the system scope: the canonical form is
  `["Error", "'not-a-library-name'", s]` (a new error code).
- The operand is not a symbol, or there is not exactly one operand: the usual
  arity and type errors of the operator.
- A qualified call `["Apply", ["Module", f], …args]` has one of three
  canonical forms, chosen before the arguments are canonicalized:
  - (a) `f` reads the library definition where the call is boxed (no binding
    of the program shadows it, by the rule that binds a call head, parameters
    included): the plain call `[f, …args]`, built by the normal route. This is
    the usual Epsil case, where only the lowercase `floor` is shadowed.
  - (b) `f` is shadowed there, and the library operator is an ordinary
    function (not lazy, no held operand, no bound variable) called with no
    named argument: `Apply(<symbol f bound to the library>, …args)`. No rule
    that recognizes a call by its name matches it. Evaluation goes through
    the `Apply` route, which reads the binding of the callee and builds the
    library call from the evaluated arguments. The call is not simplified
    symbolically.
  - (c) `f` is shadowed there, and the library operator is lazy, holds an
    operand or binds a variable, or the call has a named argument:
    `["Error", "'qualified-call-shadowed'", f]`. A lazy operator needs its
    operands unevaluated, which the `Apply` route cannot give.

  A call built in form (a) keeps its library binding when it is later
  evaluated or serialized in a scope that shadows `f`; serialized there, it is
  written `["Apply", ["Module", f], …]` and boxes again to form (b) or (c).

  Correction made during the implementation (2026-11-07, user decision): the
  first version built a call bound to the library in every case, by
  canonicalizing it with the library definition and rebinding the node. Three
  review rounds found that many canonical steps recognize a call by its name
  (the `Not(Not(x))` and idempotent folds, the flattening of `Add`, the
  statement checks of `If`, the `shadowsLibraryName()` tests), so that a user
  call of the same name inside the arguments was folded into the library
  call: with `function Not(x) { x }`, `std::not(Not(false))` gave `false`.
  Making each of those steps compare definitions instead of names is a
  separate change across the engine.

  Possible limit, not reproduced: the `Apply` route builds the library call by
  name in a scope where the name reads the library, so an argument whose value
  is still an expression holding a user call of the same name (a function
  value, a held expression) could be rebuilt with the library binding. The two
  attempts with a user `Floor` did not show it:
  `Apply(Module(Floor), Hold(Floor(2.5)))` stays unevaluated, and
  `Apply(Module(Floor), Function(Floor(z), z))` gives `incompatible-type`. No
  issue is filed without a witness.
- The structural and raw forms keep `["Module", s]` as written.
- `isSame` and the hash compare a call by its name, so a library call and a
  shadowing call with the same operands stay `isSame`. This is the limit that
  the user accepted on 2026-10-30 (`docs/SCOPING-MODEL.md`, "Callable
  resolution"). For a symbol, the two are not `isSame` (table above).
  Note (2026-11-07): CE-1109.4 replaced this limit. `isSame` now compares the
  binding of the head of a call as it compares a symbol, so a library call
  and a shadowing call with the same operands are not `isSame`; the hash is
  still by name (`docs/plans/2026-11-07-ce1109-4-match-and-same-spec.md`).

**Serialization (`.json` and `toMathJson()`).** A symbol node writes
`["Module", name]`, and a call writes `["Apply", ["Module", name],
…operands]`, when the condition of D4 holds. To keep the cost low, the test
first reads whether the node's definition is in the system scope (one
comparison), and does the scope walk only then. The result: `ce.box(e.json)`
in the scope where `.json` was read gives the value of `e`. In the CE-103
witness, the JSON is `["Divide", ["Power", ["Module", "Pi"], 2], 6]`, and
boxed in the block it gives 1.6449.

**Epsil.**

- `std::name` takes either spelling of a library name (`std::pi`,
  `std::Pi`) and parses to `["Module", "Pi"]`. `std::floor(2.5)` parses to
  `["Apply", ["Module", "Floor"], 2.5]`.
- `std` is not a reserved word and not a binding. Only `std` may stand before
  `::` in this item; another name there is the error `unknown-module`, which
  the parser reports (new diagnostic, with an explanation in
  `error-explanations.ts`).
- Static errors: `std::x` where `x` is not a library name
  (`not-a-library-name`), `std::` with no name, and `std::a::b`.
- The serializer writes `["Module", "Pi"]` as `std::pi`, and a bare name as
  before. A bare `Pi` in MathJSON reads what `Pi` reads where the text is
  read, and the engine writes `["Module", "Pi"]` when it means the library
  definition and a local hides it, so a bare name is never qualified.
  Correction made during the implementation (2026-11-07): this design first
  also wrote `std::pi` for a bare `Pi` when the program binds both `pi` and
  `Pi`. That changed the meaning of the text (the bare name names the local),
  and the REPL, whose `isBound` reports every library name as bound, printed
  `Sin(x)` as `std::sin(x)` after `let sin = 3`.
- The glyph `∷` is not an input form of `::`: the lexer reads it as an error
  token, although `characters.ts` lists it.
- The editor support (`highlight-js-mode.js`, the VS Code grammar) shows
  `std::` as a qualified name.

**Compilation.** No change (D6). Tests pin that `["Module", "Pi"]` compiles to
the library value in a scope that shadows `Pi`, and that a shadowed library
call still declines with the interpreter's value.

**CE-103.** The serializer change fixes it. Its witness becomes a test, and the
issue closes with this item.

## 6. Steps and tests

1. `Module` operator in `library/core.ts` with its canonical handler; tests
   for a constant, a function through `Apply`, a name that is not in the
   library, two operands, and the structural form.
2. The serializer condition (D4) in the `.json` getter of `BoxedSymbol`
   (`boxed-symbol.ts`, which writes the name with no scope test today), in the
   `.json` of a call, and in `serializeJsonSymbol()` and
   `serializeJsonFunction()` (`serialize.ts`); the CE-103 witness and the
   `Floor` round trip (2.25, not 100.25) as tests. Measure the serialization
   time on `benchmarks/` before and after, and report it.
3. Epsil lexer and parser (`::`), static checks, serializer, highlighter;
   tests in `test/epsil/`.
4. Compilation tests (D6); documentation (section 5).

Size: M. The snapshot changes are expected only in tests that serialize inside
a scope that shadows a library name; they are counted and reported.

## 7. Relation to the Epsil import system

The draft `docs/plans/2026-09-05-epsil-import-system.md` (not implemented)
touches this design in three places. This item does not implement modules;
it keeps their options open.

- **Shadowing by an import.** The draft lets an import shadow a
  standard-library name (its section 5: an imported `sin` is called instead of
  the library `sin`). `std::sin` is then the way back to the library function.
- **Namespace imports.** The draft defers them, with the candidate spelling
  `from "./geometry.epsil" import all as geometry`, and leaves member access
  open. With this design, the consistent spelling is `geometry::circleArea`:
  `::` reads a name of a module that is fixed when the program is checked,
  and `.` reads a field of a value. A namespace value that a future dynamic
  import returns is a value, so `.` reads its members. The draft also
  reserves `std:` specifiers for its resolver (section 6,
  `from "std:statistics" import …`); this design uses the same name `std`.
- **MathJSON persistence of module-owned symbols.** The draft lists as an open
  requirement how a symbol that a module owns prints and survives a MathJSON
  round trip (its sections 5 and 11). The reserved second operand of
  `Module` is the representation to propose to that design:
  `["Module", "x", "'./geometry.epsil'"]`.

## 8. If the item is not done

CE-103 stays `needs-design`: a JSON round trip inside a scope that shadows
`Pi` keeps giving the local value, and an Epsil program that binds both
`floor` and `Floor` cannot call the library function.
