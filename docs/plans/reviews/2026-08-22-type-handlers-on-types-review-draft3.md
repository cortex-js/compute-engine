# Spec review — docs/plans/2026-08-22-type-handlers-on-types.md (third draft)

Dual review (Claude on Sonnet + Codex at high), 2026-08-22. Focus: ready to
implement?

**18 findings — 1 critical, 7 high, 8 medium, 2 low · 3 flagged by both reviewers · 0 open questions (every item is a defect or gap in the spec, not a decision)**

1. [CRITICAL] [Both] [feasibility] §5.1 "the type-level application is then `def.type(argTypes, { …, ops: [] })`"; §5.2 step 4 `Map`; §5.3 — **The type-level application as specified cannot reproduce application typing.** Calling `def.type` directly bypasses what `boxed-function.ts:type()` does around the handler: signature fallback when there is no handler, overload resolution, generic instantiation, missing-value absorption, result parsing, broadcast result shaping. With `ops: []` it cannot invoke the §5.3 structural handlers at all — and a mapped body that is a `Block` or a nested `Map` recurses into exactly those. `Map` cannot pass one `elementTypes` entry per *source*: body operands may reorder/repeat parameters or be constants, so the entries are per body *operand*. Collection `elttype` has no types-based counterpart. (Spot-check: `Tuple`'s handler reads only `op.type.type` and arity, so it does not belong in §5.3's list.) → Specify a pure engine-level `deriveApplicationType(operator, argTypes, argFacts, structural?)` that runs the whole pipeline and conservatively declines when structure is unavailable; build `Map`'s entries per body operand; define the `elttype` counterpart; re-verify each §5.3 example against what it reads.

2. [HIGH] [Both] [completeness] §4.4 steps 1–3 — **Static admission and runtime conformance are not separated, and the runtime check is unspecified for the hard cases.** `validateArguments` is reused at runtime on evaluated lambda arguments (`function-utils.ts` `apply()`), so extending its deferred-overlap branch globally makes the *runtime* validation defer the same mismatch instead of rejecting it. "Before an evaluate handler" misses value-definition function application and says nothing about async, lazy/held operands (CLAUDE.md's `lazy` landmine), overloads, generic instantiation, optional/variadic, per-cell broadcast routes, effectful handlers (double evaluation), or an operand that stays symbolic after evaluation (must not error, per the arithmetic precedent). "§D6.2" is not in the current `docs/COLLECTIONS-MODEL.md`. → Define two modes (static admission: overlap; runtime conformance: concrete value vs the instantiated/selected parameter type, symbolic values left alone), list every insertion point, and add route-parity tests (built-ins, lambdas, lazy, overloads, generics, optional/variadic, broadcast).

3. [HIGH] [Codex] [feasibility] §4.2 / R4 — **Moving `_reviseInferredType` to the assignment site loses dependency-driven revisions.** The code's own comment (`boxed-value-definition.ts:650-664`, verified) says the revision happens on read because the refuting event is a write to a *different* definition (the dependency), which cannot reach this one at its own write site without a dependency graph the engine does not keep. The state-event pins check notification timing, not that the revised type is still produced. → Ruling R4 needs a replacement mechanism, not a relocation: track and invalidate dependents, store a conservative type at assignment, or compute a live type on read without writing. Add the test: `a` assigned an expression over `b`; `b` later redefined incompatibly; `a.type` gives the revised answer with no state write.

4. [HIGH] [Codex] [consistency] §5.1 `context.engine`, `context.ops`; "a handler that does so is not pure and must say why" — **The API still permits the mutation the design forbids.** A handler still receives the full `ComputeEngine` and live `Expression`s; a comment is not an enforcement, and user-defined handlers get no comment at all. → Either a restricted pure context plus a read-only structural operand view, or a runtime guard (dev/test) that detects version changes, construction and evaluation during a type callback; if trusted built-ins stay exempt, narrow the §1 invariant and state the policy.

5. [HIGH] [Codex] [testability] §5.4 — **The success criterion does not exercise or detect the claimed invariant.** The 219 pin drives the nested-`Map` path only — not `Pipe`, `Dot`, `Set`, `JacobianMatrix`, `Sqrt` or the two `elttype` handlers. `_anyVersion` drift detects selected engine writes only; it cannot see evaluation, canonicalization, allocation or memo writes that leave that axis alone, and warm reads hide cold-read effects. The per-handler shim and the run logs live in a session scratchpad, not a reproducible harness. → Cold and warm targeted tests per audited offender with counters for canonicalization, evaluation, declarations, scope changes and every state event; check the shim in (or replace it with a harness) and define the "byte-identical" command and comparison format.

6. [HIGH] [Codex] [scope] §5.1 `argFacts.sgn`; §7 "The `sgn` handlers … separate document" — **The `sgn` handler graph is an in-scope prerequisite, not a non-goal.** Computing `argFacts` via `op.sgn` dispatches the operator's `sgn` handler (on a function expression) and writes the `_sgn` memo; §2.5 audited type handlers only. → Audit and pin the sign-extraction path before `argFacts` depends on it, or restrict extraction to pure leaves (number literals, direct symbol assumptions) without dispatching function `sgn` handlers.

7. [HIGH] [Claude] [testability] §5.2 step 3 "the §2.2 shim, rerun per handler, byte-identical" — **The per-handler acceptance test is not defined for the new signature.** The shim proxies `ops` on the *old* call; a flipped handler no longer receives `ops` in the channel that matters. → State the comparison: run each flipped handler via the old ops-based call and via the new call built from the same real operands, over the suite, and assert the type strings match; say what "byte-identical" is diffed against.

8. [HIGH] [Codex] [completeness] §5.2 step 3 "`ops[i].type.type` → …; `ops[i].sgn` → …; `ops[i].isConstant` → …" — **The "mechanical" flip omits most operand predicates.** Handlers read `isFinite`, `isReal`, `isInteger`, `isNaN`, `isSame`, `isLess`, tuple/collection predicates; a `Type` has none of them, and the three rewrites don't give tri-state replacements. → An exhaustive conversion table for every read the audit found, with pure helpers and exact true/false/undefined semantics; reclassify any read not derivable from `argTypes`/`argFacts` as a precision-loss rewrite with its expected result.

9. [MEDIUM] [Claude] [completeness] §4.3 "`argTypes[i]` is `0` or `1`" — **Literal types on input reach all 213 handlers uniformly and can break exact comparisons.** A handler comparing `ops[i].type.type === 'finite_integer'` silently stops matching when the operand is a literal `0` arriving as `'0'`; the flip is then not mechanical. → Either widen `0`/`1` on input too (which defeats §4.3) or require the flip to audit every exact-string/structural type comparison against `argTypes[i]`.

10. [MEDIUM] [Both] [scope] §6 "Open items — none blocks §4; each has a stated default" — **O2 and O3 are required investigations, not open choices.** Neither has a default; O2 is explicitly a precondition of §5.2 step 2, and O3 leaves two unexplained baseline rows whose behavior change during migration could not be told apart. → Move O2/O3 to numbered prerequisite tasks with concrete trace artifacts and acceptance tests; keep "open items" for genuine decisions (O1, O4).

11. [MEDIUM] [Codex] [ambiguity] §4.1 — **The `Pipe`/`Dot` fixes still leave design decisions to the implementer.** `Pipe` offers two materially different implementations without a choice or a retention-safety proof; `Dot` names no helper and has no before/after table; `Pipe` is lazy, so CLAUDE.md requires box- and parse-route coverage the pin does not mention. → Rule on the `Pipe` approach and its retention invariant; include the `Dot` table and helper mapping; require function/box/parse route tests for `Pipe` including placeholder shadowing, throw cleanup and retained-scope cases. (The implementer brief dispatched today covers the route and table points; the spec should record the choice once made.)

12. [MEDIUM] [Codex] [ambiguity] §4.3 "walking structural nodes only (`list`, `tuple`, `union`, `signature`, …)" — **Widening is not specified over the full type AST, nor is `0`/`1` eligibility.** Intersections, sets, dictionaries, numeric ranges, aliases/references, generic constraints, recursive types and signature adjuncts are left to the ellipsis; `-0`, alternate exact representations, and symbols bound to `0`/`1` are undefined; parse/reduce/widen ordering is unstated. → An exhaustive Type-kind transformer mapping `0`/`1` to `finite_integer`, identity-preserving where required, cycle-guarded, with the ordering stated and tests for nested intersection/signature/alias and negative zero.

13. [MEDIUM] [Codex] [architecture-fit] §4.1, §5.2 step 4 "return the sound wider type" — **Widening lacks the signature-contract ceiling.** `types-definitions.ts` requires a handler result to be a subtype of the declared signature result; the plan only forbids narrowing. → Add the invariant `derivedResult <: instantiatedSignatureResult`, define the fallback when a proposed result violates it, and make it an assertion per migrated handler.

14. [MEDIUM] [Claude] [consistency] §5.1 `argFacts.literal` "facts the type does not carry" vs §4.3 — **`argFacts.literal` duplicates `argTypes[i]` being `0`/`1`.** For exactly these two values the type does carry the fact. → Drop `argFacts.literal`, or state why both channels exist and fix the framing.

15. [MEDIUM] [Claude] [consistency] §4.4 point 2 "through the existing `admissionOf` value-membership path … for value-component parameter types" — **Cites the wrong branch.** `finite_integer` has no value component; the refutation of `1.5` comes from `admissionOf`'s concrete-value branch (`value-membership.ts:71-100`), which works for any literal independent of the `0`/`1` scope. → Point at that branch and say the refusal does not depend on §4.3.

16. [MEDIUM] [Claude] [completeness] §5.1 `argFacts` — **Contents for collection-shaped, absent (`missing`-stripped) and `unknown`-typed operands are unspecified.** → `argFacts[i]` fields are `undefined` when not applicable; state what `argTypes[i]` is for an absent operand (the `operandTypes` override, precisely); confirm the `unknown` → `number` widening is preserved in `argTypes` once traced.

17. [LOW] [Claude] [ambiguity] §4.4 point 1 "every parameter kind" — arrow-typed parameters already admit by Design E compatibility (`arrowSlotAdmission`); say they stay on that path, or how the two admission rules reconcile.

18. [LOW] [Claude] [consistency] `docs/COMMENTING-GUIDELINES.md` "Type assertions in tests" cites "§2.5 and §3" — after the third draft's renumbering the pin measurement is §2.3. → Fix the cross-reference.
