# CE-349: speed of the benchmark cases against 0.73.0, measure of 2026-11-06

This document holds the measure that the session `cebatch-349` made for issue
CE-349 ("six benchmark cases are still slower than in version 0.73.0"), and the
options for the board.

## How it was measured

- Code: commit `87047b072fb302623160693eae84d21c791b6480`, production build
  (`npm run build production`) in a linked worktree.
- Runner: `CE_LOAD_PACKS=0 CE_PUBLISHED_BUNDLE=<bundle> node
  benchmarks/runners/run_ce_rubi.mjs`, which times the current bundle and the
  older bundle in one warm process. Median of five runs for 0.73.0, one run for
  each other release.
- Older bundles: `benchmarks/.competitors/ce-<version>/` for 0.73.0 to
  0.162.0, and `npm pack @cortex-js/compute-engine@<version>` in `/tmp` for the
  later releases.
- The box lock was held (load 2.7 at the start, 4.0 at the end, 18 cores).
- Control: the build against a copy of itself gives speed ratios of 0.89 to
  1.20 for every case but one (S05, 1.72). A ratio far below 0.8 is not noise.

The speed ratio is (time of the older release) / (time of the current build):
0.5 means that the current build takes twice as long.

## Result against 0.73.0

51 of the 53 cases have a speed ratio less than 0.95. Only S07 (1.22) and CS1
(1.24) are faster, and these two give a different result form than 0.73.0.

0.167.0 to 0.176.0, the speed ratio of CE1 is 0.64, 0.60, 0.66, 0.58, 0.77,
0.82, 0.72, 0.79, 0.90, 1.03: each release costs a few percent.

## Profiles

CPU profiles of the source (`node --import tsx --cpu-prof`) do not show one
cause.

- CE3 (`∫₁² 1/x dx`, 477 µs from source): the antiderivative takes about 10 %
  of the time. The boxing of intermediate expressions during the evaluation
  takes about 38 % (repair frames, the rebinding of binders, the canonical form
  and the signature of a function literal), the type of a function node about
  19 %, and the effect inference about 10 %.
- D01 (`d/dx sin x`, 54 µs from source): the time is spread over boxing,
  scopes and differentiation. `hasPointProductOperands()` in
  `src/compute-engine/boxed-expression/arithmetic-mul-div.ts` takes 7.6 %,
  most of it the first computation of the operand types, which the product
  reads again later.

The slowdown since 0.73.0 is the sum of the costs of the features added since
then (scopes, binders, effects, static types, the absence model, the checks
for points), not one defect that a change can remove.

## Options for the board

The goal of the issue, "every case at 0.95 times the speed of 0.73.0 or
faster", needs CE3 to become 14 times faster. No fix can do that.

- **(a) Close CE-349 (recommended).** The baseline 0.73.0 is no longer a goal.
  The release baseline of `benchmarks/README.md` already compares each release
  with the one before it, and CE-351 stays open for the cost of the type of a
  function node. Example: CE3 stays at 311 µs; a release that makes it 400 µs
  shows in the release comparison. Cost: none.
- **(b) A performance target against a recent release.** Replace the witness
  with the measure against 0.167.0 and the goal "CE1 to CE4 at 0.9 times or
  faster". Example: CE1 must go from 156 µs to about 110 µs. Cost: a
  profile-driven project of size L across boxing, binders and type inference,
  with no known lever today. These changes were measured as unprofitable in
  July 2026; do not try them again without a new profile: a memo of
  `isSubtype`, a scan of the simplify history, a memo of `bignumRe`, a cache of
  `.json`, the two differentiation changes of the July performance review, and
  a fast route in `.mul()`. Read CE-351 before you change `derivative.ts` or
  `sortProductOperands` for speed. The bundle size at cold start is CE-884
  (closed).
- **(c) A ROADMAP workstream for the cost of boxing during evaluation.** A
  design that boxes fewer intermediate expressions in `evaluate` (CE3: 38 % of
  the time). Cost: size XL, a design document first.

If nothing is decided, the issue stays in the board list, and no batch session
takes it.
